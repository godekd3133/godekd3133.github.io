Runtime Lab과 GS Unity: 빌드 통과 다음의 검증

직접 만든 런타임 재현 도구와 동료가 만든 Unity 제어 도구를 워크플로의 검증 단계에서 어떻게 쓰는지 정리했습니다.

스킬 흐름의 마지막 층은 런타임 검증입니다. 코드와 데이터 검사를 통과해도 화면에서 연출이 맞게 나오는지는 별개이기 때문입니다. 이 간격을 메우는 데 쓰는 도구가 둘 있습니다. 하나는 제가 만들었고, 하나는 동료가 만들었습니다.

도구 만든 사람 제 몫
Runtime Lab 저 설계, 구현, 이후 수정
GS Unity 동료 활용, 실사용 논의 제기, 작은 수정

문제 제기

특정 스핀 결과나 복잡한 상황을 Unity에서 재현하려면 원하는 조건이 나올 때까지 직접 플레이해야 했습니다. 에이전트도 같은 시나리오를 실행하지 못하면 검증을 맡길 수 없었습니다.

배경과 분석 틀

검증을 층으로 보면 위로 갈수록 비용이 크고 말할 수 있는 범위가 넓어집니다. Martin Fowler의 테스트 피라미드 글도 비슷한 구분을 합니다. 제 경우에는 여기에 증거의 범위를 함께 적어야 했습니다.

정적 검사고정 입력 회귀Editor 재현빌드 플레이실제 환경

근거 자료

9월에 쓴 테스트 자동화 설계는 AI 판단과 기계 판정을 나눕니다. 설계 단계의 문서이고, 당시 기준으로 새 명령과 세션은 구현 전이었습니다. 결과 형식은 이렇게 제안했습니다.

verdict: PASSED / FAILED / BLOCKED / NOT_RUN
validity: CURRENT / STALE / UNVERIFIED
cleanup: COMPLETED / REQUIRED / NOT_REQUIRED
evidence: source / generated / Unity / wallet 각각

success: true 하나로 만들지 않은 이유는, 예전에 성공한 기록이나 생성 파일이 있다는 사실로 최신 코드 검증을 인정하면 안 되기 때문입니다. 같은 문서에서 정한 나머지 규칙입니다.

규칙 이유
지금 연결 구조와 기대 동작을 분리 틀린 구조를 읽어 정답을 만들면 테스트도 함께 틀림
첫 행동 전에 관측기를 붙임 같은 프레임에 끝나는 동작을 놓치지 않음
관측기를 켜고 끈 결과를 비교 관측이 게임 상태를 바꾸지 않는지 확인
기대값을 결과에 맞춰 자동 수정하지 않음 틀린 결과가 정답이 되는 것을 막음

9월 설계에서 찾은 주의점도 일반적인 교훈이 있습니다. 실행 중인 하위 그래프는 원본의 복제본이라 원본만 구독하면 실제 실행을 놓칠 수 있습니다. 같은 프레임에 시작하고 끝나는 동작은 사후 조회로 놓칠 수 있습니다. 관측하려고 ID를 읽는 코드가 객체를 바꾸는 경우도 있어서, 관측 전후 결과가 같은지 보기로 했습니다.

Runtime Lab: 제가 만든 것

2026년 7월 31일에 만들기 시작했습니다. 같은 날 에이전트용 명령줄 클라이언트와 런타임 버그 재현 스킬도 추가했습니다.

녹화한 서버 응답 재생게임 상태를 규칙으로 판정정해진 구간을 프레임 단위로 캡처

경계도 정했습니다. 시나리오를 명시적으로 켜야만 재생되고, 끄면 평소 경로 그대로입니다. 재생 결과는 개발 환경의 증거일 뿐, 실제 서버나 결제, 실기기 검증을 대신하지 않습니다. Unity는 한 번에 한 작업만 쓸 수 있어서, 상태를 바꾸기 전에 다른 작업이 점유 중인지 먼저 확인합니다.

GS Unity: 제가 쓰고 조금 고친 것

GS Unity는 에이전트가 Unity 2022.3 Editor를 제어하는 Rust CLI입니다. 동료가 만든 도구입니다. 기존 브릿지가 실무에서 정말 쓸 만한지 팀에 논의를 제기한 것이 제 시작이었고, 개발은 동료가 주도했습니다.

  • 플레이 검증 스킬의 진입, 스핀, 상태 확인 절차를 이 CLI 기준으로 썼습니다.
  • GS App과 벤치마크의 런타임 경로에도 붙였습니다.
  • 복제 과정에서 폰트를 불러올 때 저장할 수 없는 하위 에셋이 수정된 것으로 표시되어 작업이 거부됐습니다. 이 항목만 검사에서 빼고, 다른 변경은 계속 거부하게 했습니다. 벤치마크 시작 상태를 만들다가 발견한 문제입니다.

판단이 바뀐 지점

2026년 9월에 검증 파이프라인을 조정하면서 팀 채널에 적은 말이 있습니다.

검증 파이프라인을 에디터 플레이보다 로컬 Mac 빌드 플레이 실행하여 검증하게 튜닝하니까 좀더 자연스러웠음

같은 달 구상에서는 무엇을 실행하고 어떤 조건이면 통과하는지는 코드와 고정된 테스트 데이터가 정하고, AI는 의도 해석과 테스트 초안, 실패 분석을 맡도록 역할을 나눴습니다.

AI가 맡는 것

작업 의도 해석, 코드 탐색, 테스트 초안, 수정과 실패 분석.

코드와 데이터가 정하는 것

무엇을 실행하는지, 어떤 조건이면 통과인지.

지금 플레이 검증은 GS Unity로 Editor를 다루고 Runtime Lab으로 상황을 재현하는 식입니다. 벤치마크 런타임 경로에서는 실제 진입과 스핀, 영상까지 확인했습니다. 10월 말에는 캡처를 정상 종료했는데도 점유 표시가 남아 다른 작업을 막는 문제를 찾아 고쳤습니다.

Runtime Lab의 위치는 이후에도 바뀌었습니다. 한때 폐기하기로 했다가 2026년 11월 2일 팀에 다시 살리겠다고 적었습니다. 이유는 벤치마크와 제작 스킬 실증 과정에서 에이전트가 이 도구를 적극적으로 써서 디버깅하는 모습을 봤기 때문입니다.

처음 범위

재생, 판정, 구간 캡처까지 한 도구에서 처리합니다.

11월의 계획

영상 촬영, 즉석 디버그 스핀, E2E 테스트 실행 경로만 남기고, 촬영은 GS Unity 쪽으로 흡수합니다.

도구 소유권을 명시한 이유도 적어 둡니다. 이력서나 글에서 쓴 도구를 모두 제 것처럼 말하면, 읽는 사람은 제가 무엇을 할 수 있는지 잘못 판단합니다. 그래서 표에 만든 사람과 제 몫을 나눴습니다. 이 구분은 글을 위한 것만은 아닙니다. 문제가 났을 때 누구와 상의할지, 어디에 수정을 보낼지도 여기서 정해집니다.

고찰

한 도구를 버렸다가 다시 살린 일을 저는 실패로 보지 않습니다. 다만 폐기 판단이 틀렸다는 사실은 남겨야 합니다. 에이전트가 이 도구로 디버깅하는 장면은 폐기를 정한 뒤에 봤습니다. 사람에게 불편한 도구도 에이전트에게는 쓸 만할 수 있다는 것은 제 해석이고, 사례는 아직 적습니다.

동료 도구 위에 절차를 올린 결정에도 한계가 있습니다. 동료 도구의 변경에 제 절차가 영향을 받고, 제 기여는 작은 수정에 그칩니다. 그래서 GS Unity 자체를 제 성과로 말하지 않습니다.

영상 공유도 효과를 잰 것은 아닙니다. 11월 메모에 턴마다 작업물을 직접 확인하는 것보다 영상이 빠를 것이라고 적었지만, 시간을 비교한 측정은 없습니다. 게다가 영상은 빠르게 볼 수 있어도 원하는 상황이 찍혔는지는 사람이 판단해야 합니다. Anthropic 글에서도 자동화가 볼 수 없는 화면 요소는 놓친다고 적습니다.

로컬 Mac 빌드 쪽이 자연스러웠다는 9월 메모도 관찰입니다. Editor와 빌드의 차이를 어떤 항목에서 줄였는지 표로 재지는 않았습니다. 빌드 실행은 Editor보다 시간이 오래 걸리므로, 모든 수정에 적용하면 왕복 비용이 늘어납니다. 어느 층에서 멈출지는 위험도에 따라 정해야 하는데, 이 기준은 아직 글로 다 정리하지 못했습니다.

일반화한 교훈

직접 만들 것과 동료 도구를 쓸 것을 나눈 결과, 저는 Editor 제어 대신 그 위의 검증 절차에 집중할 수 있었습니다. 재현 도구의 증거에도 범위를 적어야 했습니다. 개발 환경에서 맞았다는 것과 실제 환경에서 맞았다는 것은 다른 말입니다.

자동 검증 결과에는 통과 여부뿐 아니라 무엇을, 어느 버전에서, 어느 환경에서 확인했는지 함께 적어야 합니다. 관측 도구 자체가 결과를 바꾸지 않는지도 시험 대상입니다. 그리고 도구의 쓸모는 쓸 주체를 바꿔 다시 봐야 합니다.

다음 단계

Runtime Lab을 계속 유지할지는 2026년 10월에 팀에서 다시 논의했습니다. 절차를 바꿔도 결과가 좋아졌는지 재는 일은 벤치마크로 넘어갑니다.

설계한 결과 형식과 세션 수명 관리를 실제 게임 하나에 적용해 보는 것이 남았습니다. Unity Test Framework의 명령줄 실행과 결과 파일을 기반으로 재사용할 수 있는지도 확인할 항목입니다.
