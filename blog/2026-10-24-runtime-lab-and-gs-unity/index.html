Runtime Lab과 GS Unity: 빌드 통과 다음의 검증

직접 만든 런타임 재현 도구와 동료가 만든 Unity 제어 도구를 워크플로의 검증 단계에서 어떻게 쓰는지 정리했습니다.

코드와 데이터 검사를 통과해도 화면에서 연출이 맞게 나오는지는 별개이기 때문입니다. 이 간격을 메우는 데 쓰는 도구가 둘 있습니다. 하나는 제가 만들었고, 하나는 동료가 만들었습니다.

Runtime Lab: 제가 만든 것

Runtime Lab은 개발 환경 전용 Unity Editor 도구입니다. 2026년 7월 31일에 만들기 시작했고, 이후 수정도 제가 이어 왔습니다. 같은 날 에이전트용 명령줄 클라이언트와 런타임 버그 재현 스킬도 추가했습니다.

하는 일은 세 가지입니다.

  • 녹화한 서버 응답을 재생해 같은 상황을 다시 만듭니다.
  • 게임 상태가 기대와 맞는지 규칙으로 판정합니다.
  • 정해진 구간을 프레임 단위로 캡처합니다.

경계도 정했습니다. 시나리오를 명시적으로 켜야만 재생되고, 끄면 평소 경로 그대로입니다. 재생 결과는 개발 환경의 증거일 뿐, 실제 서버나 결제, 실기기 검증을 대신하지 않습니다. Unity는 한 번에 한 작업만 쓸 수 있어서, 상태를 바꾸기 전에 다른 작업이 점유 중인지 먼저 확인합니다.

GS Unity: 제가 쓰고 조금 고친 것

GS Unity는 에이전트가 Unity 2022.3 Editor를 제어하는 Rust CLI입니다. 동료가 만든 도구입니다.

제 몫은 활용과 작은 수정입니다.

  • 플레이 검증 스킬의 진입, 스핀, 상태 확인 절차를 이 CLI 기준으로 썼습니다.
  • GS App과 벤치마크의 런타임 경로에도 붙였습니다.
  • 복제 과정에서 폰트를 불러올 때 저장할 수 없는 하위 에셋이 수정된 것으로 표시되어 작업이 거부됐습니다. 이 항목만 검사에서 빼고, 다른 변경은 계속 거부하게 했습니다. 벤치마크 시작 상태를 만들다가 발견한 문제입니다.

함께 쓰는 방식

지금 플레이 검증은 GS Unity로 Editor를 다루고 Runtime Lab으로 상황을 재현하는 식입니다. 벤치마크 런타임 경로에서는 실제 진입과 스핀, 영상까지 확인했습니다.
