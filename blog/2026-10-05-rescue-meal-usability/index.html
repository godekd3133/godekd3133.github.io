작업일지: Rescue Meal 사용 흐름 개선

홈, 식단, 장보기 흐름을 사용 순간별로 고친 날의 기록입니다.

Rescue Meal은 먼저 써야 할 재료부터 알려 주는 식재료 관리 앱입니다. 수업용 결과물을 고도화한 프로젝트이고, 대상은 등록이 번거로워 관리 앱을 포기한 1~2인 가구입니다. 이 날은 사용 순간별로 불편한 곳을 고치고 TestFlight 릴리즈 흐름을 정리했습니다. GS App을 띄워 점검한 일처럼, 기능 목록보다 쓰는 순서를 기준으로 봤습니다.

그날의 맥락

이 날 쓴 문서의 첫 문장은 서비스의 약속입니다. 매일 모든 식품을 관리하게 하지 않고, 오늘 필요한 결정을 돕는다는 내용입니다. 그래서 기능별이 아니라 네 질문의 흐름으로 화면을 봤습니다.

집에 무엇이 있지?무엇을 만들 수 있지?무엇만 더 사면 되지?얼마나 썼지?

한 일

사용 순간 고친 것
첫 등록 영수증 없이 이름, 수량, 보관 위치만 입력
홈 냉장, 냉동, 실온 개수를 누르면 해당 목록이 바로 열림
식단 고르기 시간 상한을 엄격하게. 전에는 10분을 골라도 더 오래 걸리는 메뉴가 나옴
추천 점수 같은 재료를 나눠 등록하면 충족률이 100%를 넘던 계산을 레시피 재료 단위로 수정
구매 등록 보관 선택 전에는 저장 불가, 1000.5g 같은 소수도 그대로 저장

막힌 것

엄격해진 시간 조건 때문에 과거에 저장한 식단의 장보기 재계산이 실패했습니다. 저장된 같은 메뉴를 다시 계산할 때는 저장된 실제 조리시간을 허용해 해결했습니다. 별도 검토에서 재고 최신성과 이 호환 문제를 지적받아 고친 뒤 재검토를 통과했습니다.

새 추천

시간 상한을 엄격하게 지킵니다.

저장된 식단 재계산

이미 고른 메뉴이므로 저장된 실제 조리시간을 허용합니다.

확인한 것

추천, 식단, 장보기, 입고 흐름의 테스트와 새 화면 회귀 테스트를 돌려 이번 변경을 확인했습니다. 구매 경로는 실제 요청과 상세 화면으로 확인했습니다. 더 넓은 API 테스트에 남은 기존 실패는 이번 변경과 분리해 따로 처리하기로 했습니다.

표에 다 적지 못한 변경

이 날의 문서에는 앞의 표 외에 다음 항목이 더 있습니다.

사용 순간 이전의 부담 바꾼 것
메뉴를 고른 다음 저장과 조리 방법을 찾으려면 긴 화면 이동 재료 요약 아래로 이동. 저장은 수량을 바꾸지 않고 조리 완료 때만 차감
재료를 장보기에 추가 집에 있는 수량을 놓치기 쉬움 같은 정규화 이름의 기록을 수량, 위치별로 표시
장보기 중 다른 기기 변경 예전 재고량을 현재처럼 안내 새로고침에 재고도 갱신, 실패 시 보유량 안내 숨김
체험판 게스트가 실제 계정처럼 보임 체험 중 표시와 초기화 안내

마지막 두 항목이 “맞는 정보만 보여 준다”는 약속과 직접 이어집니다. 재고를 불러오지 못했을 때 옛 값을 보여 주는 대신 안내 자체를 숨겼고, 그 사이에 쓰던 입력 초안은 유지했습니다. 화면 기록도 고치기 전과 고친 뒤를 나눠 남겼습니다. 다만 모두 로컬의 별도 테스트 API와 데이터베이스에서 확인한 결과입니다.

판단 기준으로 삼은 것은 사용자가 그 순간 해야 하는 결정 하나입니다. 예를 들어 홈의 보관 위치 숫자는 이전 검색어와 필터를 초기화하고 그 위치만 보여 줍니다. 앞서 설정한 필터가 남아 있으면 숫자와 목록이 달라 보이기 때문입니다. 저장과 조리 완료도 나눴습니다. 저장한 메뉴를 안 만들 수 있으므로, 수량은 실제 조리 완료 때만 차감합니다. 반론이 있다면 입력이 한 번 더 필요하다는 점입니다. 관리 앱을 포기한 사람이 대상인데 단계가 늘면 약속과 부딪힐 수 있습니다. 이 긴장은 실제 사용자로 시험하기 전에는 판단할 수 없습니다.

정리하면 이 날의 결과는 사용 순간별 수정과 관련 테스트 통과, 그리고 TestFlight 릴리즈 흐름 정리입니다. 넓은 API 테스트의 기존 실패는 해결한 것으로 적지 않았습니다.

이 판단은 다음 실기기 확인 때 함께 보려고 합니다.

판단 근거와 결과

문서에는 사용 순간마다 완료 기준을 적었습니다. 예를 들면 요청 10분에 15분 메뉴를 돌려주지 않는 것과, 같은 총량을 나눠 등록해도 점수가 부풀지 않는 것입니다. 통과한 테스트 수는 다음과 같습니다. 막대는 63건을 100%로 맞췄고, 종류가 달라 많고 적음이 품질을 뜻하지는 않습니다.

프론트 함수 9
API 연결 브라우저 회귀 5

유사한 이름을 같은 상품으로 단정하지 않고 단위를 임의로 합치지 않기로 한 것도 이 날의 판단입니다. 합쳐서 보여 주면 편하지만, 틀렸을 때 사용자가 알아채기 어렵습니다. 다만 이 편이 실제로 덜 번거로운지는 사용자 테스트를 하지 않아 모릅니다. 이 평가는 제 해석입니다.
