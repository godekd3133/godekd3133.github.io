Reactor Rush를 만들며 배운 것

적탄을 붙잡아 되쏘는 조작을 구현하면서, 자동 검사로 확인되는 것과 사람이 해 봐야 아는 것을 나눠 적었습니다.

Reactor Rush는 Three.js로 만든 싱글플레이 3D 액션 원정 게임입니다. 공중섬과 폭풍 발전소에서 세 구역을 지나 보스를 쓰러뜨립니다. 이틀 전 개인전을 접은 뒤 이 게임에 시그니처 조작을 만드는 일이 남았습니다. 제품 문서에 처음 적은 시그니처는 퍼펙트 회피로 탄막을 탈취하는 것이었고, 직접 조작하는 기술로 확장한 것이 자력 포획입니다. Q나 포획 버튼으로 다가오는 적탄을 모았다가 다시 눌러 되쏩니다.

문제 제기

조작을 하나 넣는 것은 쉽습니다. 플레이어가 그 조작을 굳이 쓰게 만드는 것이 어렵습니다. 그리고 AI와 자동 검사로 빠르게 만들수록, 돌아간다는 사실과 재미있다는 평가를 섞어 적기 쉽습니다. 이 글은 자력 포획을 사례로 두 문제를 봅니다.

배경과 분석 틀

조작을 세 단계로 나눠 봤습니다. 입력(누른 것이 사라지지 않는가), 규칙(쓰면 무엇이 달라지는가), 판단(언제 쓸지 고민하게 되는가)입니다. 앞의 둘은 코드와 검사로 확인할 수 있고, 마지막은 사람의 플레이가 필요합니다. 근거는 소스 코드와 저장소의 확인 범위 문서입니다.

근거 자료

코드에 있는 포획 수치입니다.

항목 값
포획 반경 3.4
필드 지속 1.5초
재사용 대기 7초
최대 저장 12발
리턴 코일 조건과 환급 3발 이상, 3초

빠른 탭이 사라지던 문제의 수정은 다음 클래스로 끝났습니다.

/** A quick press must survive until the game can actually accept a volley. */
export class RogueFireIntent {
  private pending=false;
  request(){this.pending=true;}
  shouldFire(held:boolean){return held||this.pending;}
  accepted(){this.pending=false;}
  cancel(){this.pending=false;}
}

기록된 원정 시간은 다음과 같습니다. 막대는 44초를 100%로 맞췄습니다. 빌드와 규칙이 서로 달라 비교 지표로 쓸 수 없고, 어떤 기록인지 보여 주려고 나열했습니다.

수동 입력 보스 클리어 44초
신규 상태 실제 입력 39.6초
자동 사격 돌진 조합 33초

무엇을 시도했나

  • 필드를 연 채 이동하며 최대 12발까지 모읍니다. 다시 누르면 반격하고, 1.5초가 지나면 자동으로 발사합니다.
  • 리턴 코일 진화는 3발 이상 모아 반격했을 때만 재사용 대기를 3초 줄입니다. 빈 포획이나 1~2발에는 보너스가 없습니다.
  • 스톰아이의 방패는 일반 사격에 20%만 피해를 받고, 포획이나 회피 반격으로 빼앗은 탄에는 온전한 피해를 받습니다.

보스 방패와 진화 규칙을 포획에 묶어, 이 조작을 쓸 이유를 전투 안에 넣었습니다.

적탄이 다가옴필드를 열고 모음되쏘기방패에 온전한 피해, 재사용 대기 감소

검사와 재미를 나눠 적기

개인전에서 검사 통과가 재미를 말해 주지 않는다는 것을 겪었기 때문에, 무엇을 어디까지 확인했는지 표로 나눠 관리합니다. 자동 컨트롤러가 약 33초 만에 깬 기록은 사람의 클리어 시간이나 재미의 증거로 쓰지 않습니다. 실제 브라우저에서 입력만으로 끝낸 신규 플레이어 원정은 따로 기록했습니다.

확인한 것

실제 브라우저 입력으로 끝낸 신규 플레이어 원정, 320×568까지의 구도.

아직 미확인

그래픽이 좋다는 사람의 평가, 재미와 재방문, 물리 기기의 멀티터치, 오디오, 성능.

로비도 같은 시기에 바꿨습니다. 전투 섬에서 분리된 전용 캐릭터 쇼케이스와 실제 획득 무기 보상 트랙을 쓰고, 정산한 원정 횟수로 세 편대 배치가 순환합니다. 공중섬 첫 탈환 등으로 얻는 외형을 3D로 미리 본 뒤 장착하는 수집도 넣었습니다.

배운 것

조작을 넣는 것과 그 조작을 쓸 이유를 만드는 것은 다른 일이었습니다. 또 이번에는 자동 플레이 기록이 빠르게 나올수록 사람의 경험과 혼동하지 않도록 따로 적어야 했습니다. 이 구분은 커리어센터에서 AI 페르소나 인터뷰를 실제 사용자 검증으로 치지 않는 판단과 이어집니다.

근거 수준을 나눠 적은 표

저장소의 확인 범위 문서는 항목마다 어떤 증거로 확인했는지 적습니다. 그 일부입니다.

항목 근거 수준
빠른 공격, 기본 회피 입력 보존과 회피 거리 검사, 실제 전투 자동과 수동
네 전투 경로 두 조합 실제 승리, 네 조합 시뮬레이션 일부 수동
로비와 모바일 구도 실제 화면 관찰과 수정 수동 관찰
재방문 없음 미확인

신규 플레이어 원정 기록도 절차로 남겼습니다. 0승 상태에서 실제 입력만으로 공중섬에 출전해, 진화를 두 번 고르고, 39.6초에 끝냈습니다. 결과는 27처치, 퍼펙트 회피 5회, 포획 11발, 피해 78입니다. 재접속 뒤 저장 값이 유지되는지도 봤습니다. 다만 이것은 만든 사람의 입력이어서, 처음 하는 사람의 행동을 대신하지 못합니다.

작은 화면 문제는 수치로 적어 둔 덕분에 다시 확인하기 쉬웠습니다. 왕관 외형이 미션 패널과 겹친 문제는 쇼룸 카메라 거리를 기본 14.5, 왕관 16.8, 폭풍 15.4로 나눠 해결했고, 360×740과 320×568에서 봤습니다. 그 변경 뒤에는 회귀 검사 60개를 전부 다시 돌리지 않았고, 문서에도 그렇게 남겼습니다. 어디까지 돌렸는지까지 적어야 다음 판단에 쓸 수 있다고 생각합니다.

방패 규칙도 조정 여지가 있습니다. 강화 포대는 체력 120, 방패 60으로 중간 구역에 넣었는데, 첫 구역과 보스 재대결은 바꾸지 않았습니다. 새 적을 어디에 넣을지 범위를 정한 판단입니다. 이것이 난이도에 어떤 영향을 주는지는 사람 평가가 있어야 압니다.

입력 수정도 사람이 쓰는 순서에서 나왔습니다. 입력이 없을 때 회피는 적에게서 멀어지는 쪽으로 가고, 벽에 막히면 측면으로 바뀝니다. 터치에서는 첫 조작에 집중하도록 자동 사격을 기본으로 켰습니다. 이런 기본값은 검사로 동작을 확인할 수 있어도, 초보자가 알아서 잘 쓰는지는 확인할 수 없습니다. 그래서 문서의 미확인 칸이 줄지 않습니다. 저는 이 칸을 채우려고 자동 검사를 더 만들기보다 다른 사람의 플레이 기록을 받아야 한다고 판단했습니다.

다음 평가를 받을 때는 포획을 언제 처음 눌렀는지와 방패 앞에서 무엇을 했는지를 먼저 보려고 합니다.

고찰

확인 범위 문서에는 그래픽 평가, 재미와 재방문, 물리 기기, 오디오가 미확인으로 남아 있습니다. 최근 빌드의 데스크톱 프레임 표본도 있지만 한 환경의 짧은 측정이라 휴대전화 성능의 근거로 쓰지 않습니다.

보스 방패와 진화 규칙이 포획을 쓸 이유를 만든다는 말은 제 해석입니다. 규칙이 그렇게 작동한다는 것은 코드로 확인되지만, 플레이어가 실제로 그렇게 느끼는지는 모릅니다. 오히려 일반 사격 피해를 20%로 줄인 규칙은 포획을 강제하는 벌칙으로 받아들여질 수도 있습니다. 게임 필(game feel)을 다루는 논의도 조작의 감각을 수치만으로 판단하기 어렵다고 봅니다.

자동 플레이가 깬 기록은 게임이 끝까지 진행된다는 증거입니다. 난이도나 재미의 증거로는 쓰지 않습니다.

일반화한 교훈

  • 조작은 입력, 규칙, 판단으로 나눠서 어느 단계까지 확인했는지 적습니다.
  • 입력 처리에서는 눌렀다는 의도를 처리 가능한 시점까지 보관합니다.
  • 자동 측정값 옆에는 무엇을 증명하지 않는지 함께 적습니다.

다음에 할 것

이 게임은 아직 사람의 플레이 평가를 받아야 하는 상태입니다. 10월 9일에 직접 플레이하며 현재 빌드를 검토했고, 그다음 순서는 다른 사람의 평가입니다.
