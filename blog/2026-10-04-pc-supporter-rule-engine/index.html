PC Supporter 규칙 엔진: 모르면 모른다고 답하기

호환성 규칙 엔진이 판정 근거와 정보 부족을 어떻게 결과에 담는지, 실제 코드와 검증 결과로 설명합니다.

문제 제기

PC Supporter는 다나와 부품 카탈로그로 PC 견적의 호환성을 검사하는 서비스입니다. 맞다, 틀리다만 알려 주면 믿고 사기 어려워서, 판정마다 근거를 붙이는 구조로 만들었습니다. 개발 문서의 첫 원칙도 “호환성 판정과 데이터 신뢰도·가격·실제 조립 검증을 한 상태로 뭉개지 않습니다”입니다. 엔진은 shared/domain/engine.ts에 있습니다.

배경과 분석 틀

규칙 엔진의 답은 네 가지입니다. 호환, 주의, 장착 불가, 확인 필요입니다. 다치 논리처럼 참과 거짓 사이에 모름을 하나의 값으로 둡니다. 이렇게 하면 품질 문제도 세 곳으로 나눠 볼 수 있습니다.

엔진

입력이 맞을 때 판정이 맞는가. 무작위 표본과 독립 판정으로 봅니다.

파서

상품 문구에서 값을 맞게 읽었는가. 단위 테스트와 사례로 봅니다.

데이터

필요한 값이 있는가. 채움 비율로 봅니다.

근거 자료

10월 2일 테스트의 표본은 부품 선택기에서 고를 수 있는 1,828개, 전체 카탈로그는 7,380개입니다. 난수 seed를 고정해 같은 부품셋을 다시 뽑을 수 있게 했고, 핵심 규칙 7개를 원본 스펙으로 따로 판정해 비교했습니다. 엔진과 파서 단위 테스트 233개도 통과했습니다.

그런데 조건을 맞춰 뽑은 fit 방식 100건의 결과는 사용자 입장에서 좋지 않았습니다.

1차 확인 필요 82건
2차 확인 필요 56건
1차 호환 8건
2차 호환 9건
fit 100건 1차 2차
장착 불가 10 35
확인 필요 82 56
호환 8 9

장착 불가가 늘어난 것은 나빠진 값이 아닙니다. 2차의 35건 가운데 25건은 데스크톱 보드에 노트북 메모리를 고른 경우로, 고친 뒤 제대로 막은 사례입니다.

시도

규칙은 결과를 finding으로 남깁니다. 규칙 ID, 심각도, 영향받는 부품, 판정 사실, 사용자가 할 수 있는 행동이 함께 들어갑니다. 심각도는 blocker, warning, info, unknown으로 나눕니다. 정보가 없을 때 쓰는 addUnknown은 누락된 필드를 판정 사실로 넣고, 스펙을 확인하라는 행동을 붙입니다.

완전 호환 판정은 unknown까지 없어야 나옵니다.

function isFullyCompatible(blockerCount: number, warningCount: number, unknownCount: number) {
  return blockerCount === 0 && warningCount === 0 && unknownCount === 0;
}

물리값이나 제조사 근거가 없으면 자동 통과로 올리지 않습니다. KBO Fans 위젯에서 모르는 값을 0으로 채우지 않은 판단과 같습니다.

판단이 바뀐 지점

엔진을 믿을 수 있는지부터 확인하려고 10월 2일에 배포 카탈로그에서 무작위 부품셋 300건을 돌렸습니다. 실행 오류, 결과 일관성 위반, 독립 판정과의 불일치는 0건이었습니다. 하지만 NVMe SSD를 장착 불가로 잘못 막는 사례처럼 문제는 다른 곳에서 나왔습니다. 문서의 결론은 이렇습니다.

남은 문제는 파서와 데이터 쪽입니다

엔진이 unknown을 정직하게 내면 데이터가 비었을 때 unknown이 많아집니다. 그래서 규칙을 느슨하게 하지 않고 데이터를 메우기로 했습니다.

무작위 300건으로 엔진 점검파서와 데이터 문제 분리제조사 원문으로 케이스 사양 보강장착 조건을 판정에 추가

10월 4일 작업에서는 파서를 고치고 제조사 원문으로 케이스 사양을 보강했습니다.

케이스 사양 보강 전 보강 후
위치별 라디에이터 지원 0/56 51/56
지원 PSU 규격 51/56 53/56
SSD 베이 1/56 56/56

장착 조건도 판정에 넣었습니다. 검증에서 H6 Flow의 27mm 라디에이터는 후면 I/O 설치 조건이 확인되지 않아 unknown, 31mm는 제조사 한도 30mm를 넘어서 blocker가 나왔습니다.

표본 추출 방식을 셋으로 나눈 것도 품질 판단에 중요했습니다. random은 아무 부품이나 뽑아서 엔진이 깨지지 않는지 봅니다. plausible은 그럴듯한 조합, fit은 규격까지 맞춘 조합입니다.

방식 (각 100건, 2차) 장착 불가 확인 필요 호환
random 96 4 0
plausible 51 40 9
fit 35 56 9

random만 봤다면 엔진이 대부분 잘 막아 주는 것처럼 보였을 것입니다. 사용자의 조합에 가까운 표본을 따로 두자 답하지 못하는 비율이 드러났습니다. VRM 규칙 실험에서는 확인 필요를 298건에서 30건으로 줄였지만 보급형 조합에도 경고가 나왔습니다. 비율만 낮춘다고 좋은 답이 되는 것은 아니었습니다.

엔진과 데이터의 일정도 다릅니다. 엔진 규칙은 코드 변경과 테스트로 빠르게 고칠 수 있지만, 제조사 원문 확인은 품목마다 시간이 듭니다. AI로 보강을 도와도 원문 확인을 건너뛰면 근거 없는 값이 판정으로 들어옵니다. 그래서 케이스 사양을 제조사 원문 근거 문서와 함께 정리했습니다.

고찰

오류 0건이라는 숫자는 조심해서 읽어야 합니다. 독립 판정을 저도 비슷한 이해로 만들었다면 같은 착오를 공유할 수 있습니다. 실제 조립 확인은 아닙니다. 그래서 문서에도 엔진 판정과 실제 조립 검증을 나눠 적었습니다.

unknown의 비용도 큽니다. 조건을 맞춘 조합의 절반 이상이 확인 필요로 나오면, 정직하지만 쓸모가 부족한 답입니다. 사용자는 결국 직접 찾아야 합니다. Martin Fowler는 규칙 엔진이 규칙 간 상호작용 때문에 이해하기 어려워질 수 있다고 경고합니다. 제 경우에도 규칙보다 데이터가 먼저 막혔지만, 규칙이 늘어나면 이 위험도 커질 것입니다.

그래도 규칙을 느슨하게 하지 않은 이유는 PC 부품 구매가 돌이키기 번거롭기 때문입니다. 잘못된 호환 판정 한 번의 비용이 확인 필요 여러 번보다 크다고 봤습니다. 다만 실제 사용자가 어느 쪽을 더 불편해하는지 조사한 적은 없으니 제 해석입니다. 무작위 표본 자체도 실제 사용자의 견적 분포와 다릅니다.

케이스 사양 표도 56개 케이스에 관한 값일 뿐입니다. 메인보드나 파워까지 같은 수준으로 채웠다는 뜻이 아닙니다. 보강값은 제조사 원문을 근거로 했지만 운영 데이터에는 아직 넣지 않았으니, 지금 사용자가 받는 답은 표의 보강 후 값과 다를 수 있습니다.

이 값들은 2026년 10월 초 기준입니다.

일반화한 교훈

규칙 엔진의 정확도와 사용자가 받는 답의 품질은 다른 문제였습니다. 엔진이 전부 맞아도 입력이 비면 답은 “확인 필요”뿐입니다. 그래서 문제가 나올 때 엔진, 파서, 데이터 가운데 어디인지 먼저 나눠 적습니다. 며칠 뒤 슬롯 일에서 쓴 서버, 표시, 빌드를 나눠 보는 습관과 같은 구조입니다.

판정 시스템은 모름을 정식 결과로 둡니다. 품질 지표도 정확도와 답할 수 있는 비율을 나눠 봅니다. 엔진 검사가 통과해도 입력이 비어 있으면 사용자에게는 답이 없는 것과 같습니다.

다음 단계

위 표에 비어 있는 케이스가 남아 있습니다. 운영 데이터베이스에는 아직 반영하지 않았습니다. 메인보드 전원부 규칙은 추정 계수의 근거가 약해 이틀 뒤 판정 방식을 바꿨습니다.

보강값을 운영 데이터에 반영한 뒤 같은 seed로 다시 돌려 확인 필요 비율이 실제로 줄어드는지 보려 합니다. 실제 견적 표본으로도 같은 테스트를 해야 합니다.
