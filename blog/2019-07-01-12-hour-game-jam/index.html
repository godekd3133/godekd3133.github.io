게임 개발2019.07.01

12시간 게임잼에서 배운 것

What Up Buddy의 뷰포트 분할을 중심으로, 12시간 안에 끝낸 게임들에 어떤 구현이 반복되었는지 정리했습니다.

(2026년에 돌아보며 쓴 글입니다.)

고등학교 때 자기소개서에 이렇게 적었습니다.

정해진 틀과 규칙 내에서 게임을 플레이하는 것에 대해 질리는 것과 동시에 나만의 게임을 만들어서 직접 플레이한다면 더 재밌을 것 이라는 호기심이 들었습니다.

그 호기심으로 게임 개발이 전공인 고등학교에 갔고, 앱잼, 하이톤, 대한민국 청소년 게임잼, 교내 게임잼에 꾸준히 나갔습니다. 3~4명이 12시간 안에 게임 하나를 끝내야 하는 자리였습니다. 같은 시기 기능반에서는 DirectX 9로 프레임워크부터 짜고 있었기 때문에, 게임잼은 Unity로 끝까지 만들어 보는 연습장에 가까웠습니다.

문제 제기

게임잼 기록을 다시 읽으며 던진 질문은 하나입니다. 12시간밖에 없을 때 무엇을 직접 만들고 무엇을 엔진에 맡겼는가입니다. 완성작 목록만 보면 이 질문에 답할 수 없어서, 작품별 제작 기간과 구현 항목을 나란히 놓았습니다.

배경과 분석 틀

자료는 포트폴리오에 적힌 구현 설명과 플레이 영상입니다. 이 시기 게임잼 작품의 소스는 공개 저장소에 없어서, 코드 수준의 재검토는 하지 못했습니다. 분석은 세 가지로 나눴습니다. 제약(시간과 인원), 선택(엔진 기능 또는 직접 구현), 반복(다음 작품에도 다시 쓴 방법)입니다.

  • 2018 교내 게임잼 3등
  • 2019 2회 대한민국 청소년 게임잼, 교내 게임잼, 18회 앱잼 게임 부문 참가
  • 2020 6회 하이톤 게임 부문 참가
  • 2021 스토브 인디 게임잼 참가
  • 2022 20회 앱잼 엔터테인먼트 부문 1등

짧은 작업의 제작 기간은 포트폴리오 기준으로 다음과 같습니다. 막대 길이는 20시간을 100%로 맞췄습니다.

산타가 늦잠 잤다! 렌더링과 입력 선물상자 배열, Object Pool

Unity 문서에 따르면 targetTexture를 지정한 카메라는 화면 대신 텍스처 전체에 그립니다. 그래서 텍스처를 화면에 보여 줄 카메라가 하나 더 필요합니다. 아래는 원본 코드가 아니라 당시 구조를 설명하려고 적은 스케치입니다.

leftCamera.targetTexture = leftTexture;
rightCamera.targetTexture = rightTexture;
// 메인 카메라는 두 텍스처를 붙인 면을 촬영합니다.

무엇을 시도했나

12시간 작품으로는 What Up Buddy, 산타가 늦잠 잤다!, 쿠키런 모작(개인 학습용)이 있습니다.

What Up Buddy(2019년 7월)는 쿼터뷰 협동 게임입니다. 한 게임을 두 명이 조작해야 해서 화면을 나눠야 했습니다.

플레이어마다 카메라 하나각 카메라의 Target Texture를 Left, Right 렌더 텍스처로 지정메인 카메라가 두 텍스처를 좌우로 놓은 장면을 촬영

그 밖의 구현도 단순하게 갔습니다. 보유 아이템은 열거형으로 관리해 사용 효과를 나눴고, CarSpawner는 자동차의 방향과 위치를 무작위로 정한 뒤 같은 자리에 겹쳐 나오지 않는지 확인하고 생성했습니다.

산타가 늦잠 잤다!(2019년 12월)는 횡스크롤 캐주얼 아케이드입니다. 선물상자를 배열 하나로 관리해 생성과 입력 처리를 같은 자료구조로 끝냈습니다.

어디서 판단을 바꿨나

처음 필요한 기능을 만날 때의 판단이 작품마다 비슷했습니다. 화면 분할은 직접 그리는 방법을 찾지 않고 렌더 텍스처라는 엔진 기능으로 풀었습니다. 쿠키런 모작에서는 카메라에 보이는 오브젝트만 업데이트해 성능을 챙겼고, 맵은 타일맵에 맡겼습니다. 같은 무렵 기능반에서는 obj 파일 파싱까지 직접 하고 있었으니, 도구에 따라 직접 만들 것과 맡길 것을 다르게 골랐던 셈입니다.

두 작품을 나란히 놓으면 비슷한 선택이 반복됩니다.

반복된 선택 쓴 곳
Singleton으로 게임 시스템 관리 What Up Buddy, 산타
Object Pool로 오브젝트 재사용 산타
배열과 열거형으로 데이터를 단순하게 유지 What Up Buddy, 산타

배운 것

시간이 정해지면 새 구조를 고민하기보다 아는 방법 몇 개를 빠르게 조합하게 됩니다. 이 무렵 제 코드를 다른 사람과 나눠 쓰는 경험도 쌓았습니다. 혼자 하는 기능반과 달리, 게임잼에서는 같은 프로젝트 안에서 코드를 합쳐야 했습니다.

같은 방식으로 시간을 조금 더 쓴 작품이 20시간 만에 만들어 2020년에 출시한 땅파서 돈나오냐?!입니다. 레벨 디자인을 여러 개로 나누고 끝부분을 이어 계속 스크롤되게 했습니다.

작품별로 다시 읽기

포트폴리오의 구현 설명을 작품별로 다시 읽으면, 각 게임에서 가장 먼저 풀어야 했던 문제가 다릅니다.

What Up Buddy에서는 두 사람이 한 화면을 쓰는 문제가 먼저였습니다. 화면 구성이 정해지지 않으면 협동이라는 규칙 자체가 성립하지 않기 때문입니다. 그다음이 도로 위 자동차였고, CarSpawner는 방향과 위치를 무작위로 정한 뒤 겹치는지 확인했습니다. 무작위 생성을 쓰면서 겹침 검사를 함께 넣은 것은 이후 Bright Burn에서 같은 맵을 다시 뽑지 않는 코드와 닮았습니다.

쿠키런 모작에서는 달리는 동안 오브젝트가 계속 늘어나는 것이 문제였습니다. 그래서 카메라에 보이는 오브젝트만 갱신했습니다. 비트맵 폰트로 점수 연출을 만든 것도 이 작품입니다. 비트맵 폰트는 뒤에 회사에서 잭팟 보드 성능 문제를 다룰 때 다시 만났습니다.

산타가 늦잠 잤다!는 입력에 맞춰 선물상자 줄을 처리하는 게임이어서, 줄 하나를 배열로 두면 생성과 입력 판정이 같은 인덱스로 끝났습니다. 자주 생겼다 사라지는 오브젝트에는 Object Pool을 썼습니다.

땅파서 돈나오냐?!는 시간이 8시간 더 있었던 작품입니다. 그 시간이 TrailRenderer로 땅이 파이는 효과와 ParticleSystem의 흙 잔해 같은 손맛 연출, 구글과 AdMob 연동으로 갔다는 점이 눈에 띕니다. 시간이 늘어났을 때 무엇을 먼저 더했는지 보여 주는 기록입니다.

쿠키런 모작 달리는 동안 늘어나는 오브젝트 보이는 것만 갱신

고찰

제 해석입니다. 12시간 작업에서 렌더 텍스처를 고른 것은 이미 만들어진 부품을 찾는 쪽으로 판단이 기울어 있었다는 신호로 보입니다. 다만 Unity에는 카메라의 rect로 뷰포트를 나누는 방법도 있고, 당시 두 방법을 비교했다는 기록은 남아 있지 않습니다. 그래서 더 좋은 선택이었다고 말할 근거는 없습니다.

반론도 있습니다. Singleton과 단순한 배열은 12시간 안에서는 빠르지만, 오래 유지하는 프로젝트에서는 의존 관계를 숨기기 쉽습니다. 게임 프로그래밍 패턴 책도 Singleton을 조심해서 쓰라고 다룹니다. 게임잼의 반복 선택을 일반 설계 원칙으로 옮기면 안 된다고 봅니다.

이 글의 한계는 자료가 제가 쓴 설명뿐이라는 점입니다. 함께한 팀원의 기억이나 소스가 있었다면 역할 구분이 더 정확했을 것입니다.

확인한 것은 작품별 구현 설명과 제작 기간입니다. 빠르게 만들 수 있었던 이유가 무엇인지는 제 해석입니다.

일반화한 교훈

  • 마감이 짧으면 새로 배울 항목을 하나로 줄이고, 나머지는 아는 방법으로 채웁니다.
  • 임시방편은 어떤 조건에서 쓴 것인지 함께 적어 둡니다. 조건이 바뀌면 다시 판단할 수 있습니다.
  • 다른 사람과 합칠 코드는 단순한 자료구조가 읽기 쉽습니다.

그다음

짧은 게임잼을 반복한 뒤 6달짜리 팀 프로젝트로 넘어갔습니다. 그 기록이 Bright Burn입니다. 게임잼은 그 뒤로도 이어져 2022년 20회 앱잼 엔터테인먼트 부문에서 1등을 했고, 회사에 들어간 뒤에도 사내 게임잼에 계속 나갔습니다.
