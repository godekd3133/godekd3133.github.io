2020 전국기능경기대회까지

기능반에 지원하려고 만든 슈팅 게임부터 2020년 전국기능경기대회 과제까지, DirectX 9로 만든 기록을 순서대로 정리했습니다.

(2026년에 돌아보며 쓴 글입니다.)

고등학교에 들어갔을 때의 저는 자기소개서에 “맨땅에 헤딩 하기란 매우 어려웠습니다”라고 쓸 만큼 게임 개발을 어디서 시작할지 몰랐습니다. 서울디지텍고등학교의 게임 개발 기능반은 DirectX 9로 게임을 만들어 기능경기대회 게임 부문에 나가는 동아리였고, 지원하려고 슈팅 게임을 만든 것이 지금 남아 있는 가장 오래된 기록입니다.

이 무렵 제 태도를 적은 문장이 있습니다.

오늘보다 발전한 내일의 나가 되자

문제 제기

Unity로 게임잼을 하면서 왜 DirectX 9로 프레임워크까지 짰는지가 이 글의 질문입니다. 대회 준비라는 이유 외에, 직접 구현이 무엇을 남겼는지 작품과 공개 코드로 확인했습니다.

배경과 분석 틀

기능반은 제한 시간 안에 게임을 완성하는 대회를 준비했습니다. 엔진이 없으므로 엔진이 해 주던 일을 하나씩 코드로 옮겨야 했습니다. 작품을 ’어떤 엔진 기능을 대신 만들었는가’로 분류했습니다. 근거는 포트폴리오와 공개 저장소이며, 2020년 전국대회 문제를 연습한 저장소 두 개가 남아 있습니다.

공개된 연습 저장소의 Delay입니다. 대기도 큐에 들어가는 함수 하나입니다.

void CScheduleAdmin::Delay(float _fTime)
{
	m_Schedules.emplace(
		[this, _fTime]()->bool {
		m_fTime += udt;
		if (m_fTime > _fTime)
		{
			m_fTime = 0.f;
			return false;
		}
		return true;
	}, _fTime);
}

코드를 읽으면 항목을 큐 순서대로 처리하는 구조입니다. 여러 연출을 동시에 돌리려면 큐를 여러 개 두어야 합니다. 경과 시간을 멤버 하나에 쌓으므로, 한 큐 안에서 앞 항목이 끝나야 다음 대기가 시작된다는 전제 위에서 동작합니다.

작품마다 연습하려는 것이 달랐습니다. 리스트 구현의 목표는 std::list에서 std::를 빼도 똑같이 동작하게 만드는 것이었습니다. Space Of Tank는 대회 유형에 맞춰 20시간 안에 만들었고, 맵 충돌은 픽셀 색으로 판정했습니다. DirectX의 이미지 로딩에 최대 크기가 있다는 것을 알게 되어 맵을 여러 개로 나눠 무작위로 스크롤되게 바꾸기도 했습니다. Under Watch에서는 obj와 mtl 파일을 직접 파싱하고 컴포넌트 기반 오브젝트 구조를 만들었습니다.

그사이에 서강대학교 평생교육원의 DirectX 9 게임 프로그래밍 과정 60시간과 교내 자료구조 방과후 수업도 이수했습니다.

어디서 막혔고 어떻게 바꿨나

전국대회 과제는 20시간 안에 캐주얼 액션 게임을 만드는 것이었고, 기획부터 구현까지 전부 맡았습니다. 엔진이 없으면 시간차 연출을 만들 때마다 타이머와 상태 변수를 직접 다뤄야 합니다. 그래서 Unity의 Coroutine과 비슷한 Schedule을 직접 만들어 함수를 큐에 넣고 차례로 실행하게 했습니다.

using Schedule = function<bool()>;

class CScheduleAdmin {
    queue<pair<Schedule, float>> m_Schedules;
public:
    void Add(Schedule _Schedule, float _fDuraction = 0.f);
    void Delay(float _fTime);
    void Update();
};

함수가 false를 돌려주거나 지정한 시간이 지나면 다음 항목으로 넘어갑니다. 덕분에 시간차를 둔 연출과 후처리의 제작 시간을 크게 줄였습니다.

배운 것

Schedule을 만들 때 참고한 것은 Unity의 Coroutine이었고, 컴포넌트 구조도 Unity의 스크립팅 구조를 참고했습니다. 게임잼에서 쓰던 엔진 기능을 엔진 없는 곳에 직접 옮겨 본 셈입니다. 자기소개서에는 이런 생각을 “다른 사람들이 오랜 시간 동안 만들어 놓은 길을 따라 올라가다 보면 언젠가는 저도 그 길을 이어 개척해 나가야 할 때가 올 것”이라고 적었습니다.

시간차 흐름을 다루는 관심은 뒤에도 이어졌습니다. 회사에 들어간 뒤 저는 Coroutine 대신 UniTask를 쓰자고 꾸준히 제안했고, 그 이야기는 슬롯 글에 있습니다.

연습 방식의 변화

작품을 시간순으로 보면 연습 단위가 달라집니다. 바다 밑 잭팟에서는 유도탄, 샷건, 레이저, nWay 같은 탄환 알고리즘과 방향 벡터 계산을 한 게임에 넣었습니다. Space Of Tank에서는 외곽 8개 점을 검사해 회전 가능 여부를 판단했고, 파일 입출력으로 순위를 저장했습니다. 대회 형식에 맞춰 메뉴와 점수까지 갖춘 완성품을 시간 안에 내는 연습입니다.

그 뒤의 LinkedList, A*, BSP 맵 생성은 게임이 아니라 작은 알고리즘 하나를 며칠에 끝내는 단위였습니다. 공개 저장소 설명에도 1인 작업과 연월이 적혀 있습니다. 완성품 연습과 부품 연습을 번갈아 했다고 정리할 수 있습니다. 2020년에는 지역별 문제를 푸는 연습 저장소가 나타납니다.

고찰

순위 변화는 표에 있는 대로이고, 지방 5위에서 전국 5위까지 간 과정에 직접 구현 연습이 얼마나 기여했는지는 측정할 수 없습니다. 제 해석으로는 Schedule 같은 도구를 대회 전에 미리 만들어 둔 점이 20시간 제한에서 도움이 됐다고 봅니다. 포트폴리오에도 제작 시간에 이점이 있었다고 적었지만, 없을 때와 비교한 수치는 없습니다.

반론도 분명합니다. 지금 엔진 없이 게임을 만들 일은 드물고, 직접 만든 Schedule은 예외 처리나 취소 지점이 UniTask 같은 라이브러리에 미치지 못합니다. 그래서 직접 구현을 계속 권하려는 것은 아닙니다. 제가 남긴 쪽은 구현물보다, 엔진 기능이 어떤 비용을 대신 내는지 짐작하는 감각입니다. 이 문장도 제 해석입니다.

당시 자기소개서의 "오늘보다 발전한 내일의 나가 되자"는 제 태도를 적은 글입니다. 실력의 근거로는 저장소와 대회 결과만 썼습니다.

한계도 있습니다. 공개 저장소는 대회 뒤까지 정리된 연습본이어서, 대회장에서 제출한 코드와 같다고 볼 수 없습니다.

일반화한 교훈

  • 쓰던 도구의 일부를 직접 만들어 보면 그 도구의 전제가 보입니다.
  • 시간 제한이 있는 일에 쓸 도구는 본 작업 전에 만들어 둡니다.
  • 직접 만든 도구에는 어떤 전제로 동작하는지 함께 적어 둡니다. 큐 하나에 대기 시간 하나 같은 전제가 그렇습니다.
