팀 업무를 스킬의 흐름으로 자동화하려던 시도

슬롯 개발 업무를 에이전트 스킬로 묶어 온 과정과, 스킬을 많이 만든 뒤 다시 줄인 이유를 정리했습니다.

저는 팀의 슬롯 개발 업무를 스킬의 흐름으로 자동화하고 싶었습니다. 팀에는 이미 동료들이 시작한 플러그인 저장소가 있었고, 저는 2026년 5월에 슬롯 개발 워크플로 플러그인을 추가했습니다. 목적은 README 첫 줄에 있는 대로, 신규 슬롯과 보너스 개발을 같은 기준으로 시작하는 것이었습니다.

흐름

지금 신규 슬롯 제작은 이런 순서입니다.

  1. 기획서를 구조화된 명세로 옮기고, 불명확한 점은 질문으로 확정합니다.
  2. 서버 로직과 수학 값을 기획서에서 새로 작성합니다.
  3. 시뮬레이션으로 수학 값을 확인합니다.
  4. 기본 게임의 클라이언트 모듈을 복제하고, 필요 없는 피처는 빼고 없는 피처는 가져옵니다.
  5. 서버 응답과 클라이언트 데이터 구조를 맞춥니다.
  6. 상태 그래프와 연출 컨트롤러를 만들고, 아트 자리에는 자리표시자를 둡니다.
  7. 아트가 들어올 때마다 차이만 장착합니다.
  8. 실제 플레이로 검증합니다.
  9. 레퍼런스 문서를 남깁니다.

왜 쪼갰나

처음에는 프로젝트에 있던 스킬을 거의 그대로 묶었습니다. 쪼갠 이유는 세 가지입니다.

  • 섞이지 않게: 제작 스킬은 순서와 통과 조건만 정하고, 방법은 각 단계 스킬이 맡습니다. 내용 복제는 금지입니다.
  • 맥락이 흐려지지 않게: 단계마다 서브에이전트를 쓰고, 그 단계의 스킬만 읽게 합니다. 문서와 실제가 어긋나는 일을 막기 위해서입니다.
  • 완료를 뭉뚱그리지 않게: 서버, Data Schema, 클라이언트 흐름, 프리팹, 런타임 검증, 인계를 나눠 보고하게 했습니다.

잘 안 된 것

8월에 제 피드백을 모아 회고했습니다. 후속 수정을 전부 에이전트 실수로 보지 않고 직접 오해, 사양 변경, 런타임에서 처음 드러난 결함, 증거 미완료로 나눴습니다. 정적 검사나 빌드 통과를 제품 완료처럼 보고한 사례도 함께 살펴봤습니다.

스킬 수도 문제였습니다. 10월에 제작 파이프라인 스킬 하나로 진입점을 모으면서 스킬을 통합하거나 없애 절반 수준으로 줄였습니다. 지금은 단계별로 어떤 스킬과 문서를 읽을지가 표로 정해져 있습니다.

통과 기록도 다시 봤습니다. 지금은 도구가 실행한 명령의 실제 실행 로그만 통과로 칩니다. 손으로 쓴 통과 표시는 인정하지 않습니다.

스킬이 실제로 결과를 좋게 만드는지는 이 단계에서 답하지 못했습니다. 그 질문은 벤치마크로 이어졌습니다.
