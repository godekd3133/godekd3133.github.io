팀 업무를 스킬의 흐름으로 자동화하려던 시도

슬롯 개발 업무를 에이전트 스킬로 묶어 온 과정과, 스킬을 많이 만든 뒤 다시 줄인 이유를 정리했습니다.

저는 팀의 슬롯 개발 업무를 스킬의 흐름으로 자동화하고 싶었습니다. 팀에는 이미 동료들이 시작한 플러그인 저장소가 있었고, 저는 2026년 5월에 슬롯 개발 워크플로 플러그인을 추가했습니다. 목적은 README 첫 줄에 있는 대로, 신규 슬롯과 보너스 개발을 같은 기준으로 시작하는 것이었습니다. 출발점은 피드백을 규칙으로 옮기던 일입니다.

무엇을 시도했나

지금 신규 슬롯 제작은 이런 순서입니다.

기획서를 명세로, 불명확한 점은 질문으로서버 로직과 수학 값 작성시뮬레이션모듈 복제와 피처 이식응답과 클라이언트 구조 맞추기상태 그래프와 연출아트 차이만 장착실제 플레이 검증문서 인계

처음에는 프로젝트에 있던 스킬을 거의 그대로 묶었습니다. 쪼갠 이유는 세 가지입니다.

이유 방법
섞이지 않게 제작 스킬은 순서와 통과 조건만 정하고, 방법은 각 단계 스킬이 맡습니다. 내용 복제는 금지입니다.
맥락이 흐려지지 않게 단계마다 서브에이전트를 쓰고, 그 단계의 스킬만 읽게 합니다.
완료를 뭉뚱그리지 않게 서버, Data Schema, 클라이언트 흐름, 프리팹, 런타임 검증, 인계를 나눠 보고합니다.

어디서 막혔고 어떻게 판단을 바꿨나

2026년 5월에 쓴 개발 회고에서 얻은 결론은 슬롯 작업이 한 층만 고쳐서는 끝나지 않는다는 것이었습니다. 서버 값 하나를 바꾸면 스키마, 클라이언트 데이터 경로, 연출, 시뮬레이션, 작업 기록까지 이어집니다. 스킬을 층별로 나눈 것은 이 때문입니다.

8월에는 제 피드백을 모아 다시 회고했습니다. 후속 수정을 전부 에이전트 실수로 보지 않고 네 갈래로 나눴습니다.

분류 뜻
직접 오해 에이전트가 요구를 잘못 이해
사양 변경 만드는 도중 요구가 바뀜
런타임에서 처음 드러난 결함 정적 검사로는 볼 수 없던 문제
증거 미완료 확인을 끝내지 않고 완료처럼 보고

정적 검사나 빌드 통과를 제품 완료처럼 보고한 사례도 함께 살펴봤습니다.

스킬 수도 문제였습니다. 만들수록 진입점이 여러 갈래가 됐습니다. 10월에 제작 파이프라인 스킬 하나로 진입점을 모으면서 스킬을 통합하거나 없애 절반 수준으로 줄였습니다. 지금은 단계별로 어떤 스킬과 문서를 읽을지가 표로 정해져 있습니다.

이전

스킬이 많고 시작점이 여러 개입니다. 통과 표시는 손으로 쓸 수 있습니다.

이후

진입점은 하나입니다. 도구가 실행한 명령의 실제 실행 로그만 통과로 칩니다.

배운 것

스킬을 많이 만드는 것이 자동화의 진척은 아니었습니다. 순서를 맡는 문서와 방법을 맡는 문서를 나누자 오히려 줄일 수 있었습니다. 그리고 절차를 글로 쓰는 일은 제 기준을 드러내는 일이기도 했습니다. 슬롯 작업에서 제가 반복해서 적은 피드백이 곧 규칙이 되었기 때문입니다.

다음에 할 것

스킬이 실제로 결과를 좋게 만드는지는 이 단계에서 답하지 못했습니다. 그 질문은 벤치마크로 이어졌고, 런타임 층의 확인은 Runtime Lab에 적었습니다.
