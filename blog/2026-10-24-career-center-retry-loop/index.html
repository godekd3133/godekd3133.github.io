커리어센터: 같은 질문에 다시 답하게 만들기

모의면접 결과에서 다시 답할 질문 하나를 고르는 규칙과, 그 이유 문장을 잰 값으로만 만드는 코드를 설명합니다.

문제 제기

커리어센터는 공고 고르기부터 면접 복기까지 잇는 취업 준비 앱입니다. MVP 때부터 비교 보고서가 있었지만 보고서는 읽고 끝나기 쉬웠습니다. 로드맵에 적어 둔 핵심 고리는 “모의면접, 보고서, 약점 지도 갱신, 약점 기반 재출제”입니다. 그래서 2026년 10월 24일에 다시 답하기를 결과, 오늘, 연습 화면의 첫 버튼으로 올렸습니다. 관련 규칙은 packages/core/src/retry.ts에 모았습니다.

배경과 분석 틀

면접 연습 앱의 가치를 저는 세 단계로 봅니다. 약한 곳을 아는가, 다시 해 보는가, 나아졌는지 비교할 수 있는가입니다. 처음 보고서는 첫 단계에 머물렀습니다. 인출 연습 효과 연구처럼, 읽기보다 다시 떠올려 답하는 행동을 앱의 첫 동작으로 올리려 했습니다.

답하기약한 곳 확인같은 질문에 다시 답하기첫 시도와 나란히 비교

근거 자료

retry.ts의 기준은 코드에 상수로 남아 있습니다.

/** 점수 중 하나라도 이보다 낮으면 다시 답할 만한 답으로 본다 */
export const RETRY_WEAK_BELOW = 80;
/** 오늘, 어제, 그저께에 한 면접 */
const RETRY_DAYS = 3;

모두 AI가 연기한 응답이라 가설입니다.

시도

pickRetryAnswer는 이미 받은 AI 평가로 하나를 고릅니다.

AI 정리가 고칠 점으로 집은 답변없으면 내용과 적합도 합이 가장 낮은 답변평가가 없으면 첫 답변

다시 답할지 권하는 기준은 상수 RETRY_WEAK_BELOW = 80이고, 사용자가 “이 평가 틀렸어요”를 누른 답은 권하지 않습니다.

판단이 바뀐 지점

“왜 다시 답해야 하나”를 AI가 지어내면 믿기 어렵습니다. 그래서 이유 문장은 측정값에서 만듭니다. 아래는 문장 부분을 줄여 옮긴 코드입니다.

export function retryReason(a: AnswerRecord): string {
  const top = fillersCount(a) ? [...a.metrics.fillers].sort((x, y) => y.count - x.count)[0] : undefined;
  if (top && top.count >= 3) return /* "음"이 5번 나왔어요 */;
  if (!a.typed && a.metrics.timeStatus === 'over') return /* 제한 시간 초과 */;
  // 전달력, 내용, 적합도 점수 순으로 확인
  return '';
}

AI가 집은 인용도 quoteOf에서 공백을 뺀 실제 답변에 들어 있을 때만 씁니다.

AI가 쓰게 두면

그럴듯한 이유가 나오지만 근거를 확인할 수 없습니다.

지금

잰 값으로 문장을 만들고, 잴 수 없으면 빈 문자열을 돌려줍니다.

말하기 지표는 speech.ts가 AI 없이 계산합니다. 브라우저 받아쓰기는 “음, 어”를 지워 버리는 경우가 있어서, 원문 그대로 받아쓴 결과일 때만 말버릇과 되풀이를 셉니다. 그렇지 않으면 wordsMeasured가 false가 되고 점수에도 넣지 않습니다.

다시 답하기를 첫 버튼으로 올리면 다른 기능의 자리는 줄어듭니다. 제가 이 고리를 앞에 둔 것은 기능 하나를 더 보여 주기보다 한 번의 연습을 끝까지 잇는 것이 낫다고 봤기 때문입니다.

보고서 중심

많은 내용을 알려 주지만, 다음 행동을 사용자가 정합니다.

다시 답하기 중심

질문 하나와 이유 하나를 주고 바로 말하게 합니다. 대신 다른 약점은 뒤로 밀립니다.

다시 답하기는 처음 답한 면접 결과 안에서 하도록 했습니다. 그래야 첫 시도와 나란히 비교되기 때문입니다. 인용을 공백까지 지운 원문과 대조하는 것도 같은 생각입니다. AI가 답변에 없는 말을 사용자의 말처럼 보여 주면 작은 실수여도 믿음을 잃습니다. 가상 인터뷰의 틀린 평가 의견은 이 판단과 같은 방향이지만, 앞서 말한 대로 근거로는 약합니다.

검증한다면 무엇을 볼지도 미리 적어 둡니다. 첫째는 사용자가 다시 답하기를 누르는지입니다. 둘째는 다시 답한 뒤 측정 지표가 달라지는지입니다. 셋째는 실제 면접을 앞두고 돌아오는지입니다. 첫째와 셋째는 행동이라 비교적 믿을 만하지만, 둘째는 익숙함의 영향을 분리하기 어렵습니다. 실력이 올랐다는 주장은 이 지표만으로 할 수 없습니다. 실제 면접 결과를 물어 비교할 수도 있지만 표본을 모으기 어렵고, 합격에는 다른 요인도 많습니다. 그래서 처음 목표는 실력 증명이 아니라 사용자가 다시 답할 만큼 이유가 납득되는지 확인하는 것으로 잡겠습니다.

고찰

80이라는 기준과 3일이라는 기간에 연구나 실험 근거는 없습니다. 제품을 만들며 정한 값입니다. 다시 답하기가 면접 실력으로 이어진다는 것도 지금은 기대입니다. 인출 연습 연구는 주로 학습 내용의 기억을 다루므로, 말하기 면접에 그대로 옮기면 안 됩니다.

약점 고르기의 일부는 아직 AI 평가에 의존합니다. 이유 문장은 잰 값으로 만들지만, 어떤 답이 약한지는 AI의 점수로 정합니다. 그래서 평가가 틀렸다고 누르는 버튼을 넣었습니다. 잴 수 있는 것만 말하겠다는 원칙에 경계가 있는 셈입니다.

AI 페르소나의 응답이 서로 비슷한 것도 위험합니다. 여러 명이 같이 말했다고 해서 근거가 늘어난 것은 아닙니다. 같은 모델이 비슷한 생각을 여러 번 말했을 수 있습니다. 저는 이 인터뷰가 질문을 만드는 데는 도움이 됐다고 보지만, 이것은 제 해석입니다.

재출제가 늘 좋은 것도 아닙니다. 같은 질문에 익숙해져 점수만 오를 수 있습니다. 첫 시도와 다른 날의 답을 함께 비교하게 한 것도 이 때문이지만, 충분한지는 모릅니다.

말버릇 계산을 끈 경우도 있습니다. 받아쓰기 원문을 받지 못하면 점수에 넣지 않는데, 그만큼 사용자에게 줄 수 있는 피드백이 줄어듭니다. 브라우저 환경에 따라 같은 사용자도 다른 범위의 피드백을 받습니다. 이것을 사용자가 이해하도록 설명하는 문제가 남아 있습니다.

일반화한 교훈

같은 날 추가한 과제 계획에도 같은 원칙을 썼습니다. 변경 기록에 “AI 없이 규칙으로 만들어서 지어낸 숫자가 들어가지 않”는다고 적었습니다. PC Supporter에서 모르면 unknown으로 답한 것처럼, 잴 수 없는 것을 세지 않는 것은 제품마다 반복되는 제 기준이 되었습니다.

가상 고객 인터뷰에서는 질문이 날카로울수록 점수가 올라간다는 응답이 여러 번 나왔습니다. 다만 AI가 연기한 페르소나의 의견이어서 가설로만 다룹니다.

AI가 쓰는 설명은 잰 값에 묶습니다. 값이 없으면 문장도 만들지 않습니다. 그리고 사용자가 평가를 고칠 길을 함께 둡니다. 측정과 생성의 경계를 코드에서 볼 수 있게 두면 나중에 고치기도 쉽습니다.

다음 단계

이 고리가 실제로 면접 실력을 올리는지는 아직 모릅니다. AI 가상 페르소나로 질문을 점검했고, 실제 사용자 검증은 아직 하지 않았습니다. 10월 31일에는 내 자소서 문장에서 면접까지 잇는 취업 매니저로 방향을 다듬었고, 다음 순서는 실제 인터뷰입니다.

실제 인터뷰에서는 다시 답하기를 눌렀는지, 면접이 잡힌 시점에 돌아왔는지부터 묻겠습니다. 그 전까지 80과 3일은 임시값으로 둡니다.
