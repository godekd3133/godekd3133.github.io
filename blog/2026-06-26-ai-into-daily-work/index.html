AI2026.06.26

업무 투입: 스킬과 서브에이전트, MCP를 쓰기 시작하다

2026년 3월부터 6월 사이 AI 도구가 실제 업무 흐름으로 들어왔습니다.

(2026년에 돌아보며 쓴 글입니다.)

도구를 시험하던 시기가 지나고, 2026년 봄에 AI를 실제 업무 안으로 넣기 시작했습니다. 2026년 4월 프롬프트 수는 Codex 719건, Claude 503건으로 1월의 66건, 147건보다 크게 늘었습니다.

문제 제기

2026년 2월에 기존 슬롯의 슈퍼 보너스를 AI와 함께 개발하고, 기획 분석부터 서버, 클라이언트, 리뷰까지 어떻게 진행했는지 보고서를 써서 팀에 공유했습니다. 3월에는 서버 개발 대화를 원문 그대로 남기게 해 제 의도와 피드백을 기록했습니다. 요청에 이렇게 썼습니다.

압축하거나 요약하지말고 프롬프트는 왠만하면 그대로 나의 의도를 파악하여 넣는게 중요

배경과 분석 틀

이 시기의 변화를 저는 피드백이 사는 장소로 봅니다. 대화에 있으면 세션이 끝날 때 사라지고, 파일에 있으면 다음 세션이 읽고, 플러그인에 있으면 팀이 함께 씁니다.

대화

이번 세션에만 남습니다.

규칙과 스킬

다음 세션이 같은 기준으로 시작합니다.

기준 내용
덮어쓰기 금지 규칙 파일 전체를 덮지 않고 관리 영역과 공유 문서만 추가
어긋남 확인 어긋남이 있을 때만 내용을 보고 덮어쓰기 옵션 사용
나눠 보고 서버 응답, 스키마, 상태 그래프, 프리팹, 런타임을 분리해 보고

같은 달 문서 제작 스킬 안내에는 수치를 임의로 보정하지 않고 원본에서 계산해 채운다는 기준을 넣었습니다.

프롬프트 수도 함께 봅니다. 2026년 1월과 4월을 비교하면 Codex는 66건에서 719건, Claude는 147건에서 503건으로 늘었습니다. 1월은 슬래시 명령 비중이 높아 대화량 비교로는 부족합니다.

시도

날짜 처음 쓴 기능
5월 13일 Claude 스킬
6월 16일 Codex 서브에이전트
6월 17일 MCP
6월 26일 Claude 병렬 에이전트
컨텍스트 파일로 세션을 잇기잘못된 가정을 즉시 교정피드백을 규칙으로 정리규칙을 스킬로 묶어 팀에 배포

2월 보고서에 남긴 패턴은 게임 레퍼런스와 컨텍스트 파일로 세션 사이를 잇는 것, 독립 작업은 병렬로 돌리는 것, 리뷰 결과를 바로 수정으로 잇는 것입니다. 잘못된 방향은 세 번 교정했는데, 그때 적은 교훈이 “AI가 잘못된 가정으로 진행할 때 즉시 교정하는 것”입니다.

판단이 바뀐 지점

3월 개발에서는 값 파일의 구조가 팀의 기존 코드와 달랐습니다. 저는 같은 실수가 반복되면 안 된다고 적고, 이렇게 피드백했습니다.

효율적인 코드도 좋지만 우리가 원래 만들던 코딩 스타일을 따라가는것도 많이 중요하단다

시뮬레이션에서도 비슷한 일이 있었습니다. 전체 수치만 보면 목표 근처였지만 세부 분포가 달랐고, 세부 지표를 추가해 대조하면서 구현 결함을 찾았습니다. 값을 먼저 고치지 않고 로직이 틀렸을 가능성부터 보는 원칙을 이때 세웠습니다.

이 피드백들을 대화에 흘려보내지 않고 규칙과 스킬로 옮겼습니다.

이전

같은 피드백을 세션마다 다시 말합니다.

이후

피드백을 교훈 표로 스킬에 넣고, 레퍼런스 문서가 없으면 실행을 막습니다.

6월에는 이 묶음을 플러그인으로 팀에 안내했습니다. setup은 규칙 파일 전체를 덮어쓰지 않고 관리 영역과 공유 문서만 추가하고, audit은 문서 상태를 OK, MISSING, DRIFT로 나눠 보여 줍니다. 슬롯 작업에 필요한 기준 문서도 함께 넣었습니다.

2월 보고서에는 의사결정 방식도 적어 두었습니다. AI가 옵션을 제시하면 제가 고르고, AI가 구현합니다. 용어가 틀리면 바로 고치고, 대안을 시도하기 전에 먼저 묻게 했습니다. 1월에는 실제 슬롯의 연출 기능 계획을 세우게 한 뒤 사람이 구현한다면 더 필요한 작업이 있는지 동료들에게 평가를 부탁하기도 했습니다.

이 시기에 적은 피드백을 묶어 보면 세 종류입니다. 코드 스타일처럼 팀의 관례를 알려 주는 것, 시뮬레이션처럼 판단 순서를 알려 주는 것, 용어처럼 잘못 이해한 것을 바로잡는 것입니다. 옮기는 곳도 달라야 했습니다.

피드백 종류 예 옮긴 곳
팀 관례 값 파일 구조를 기존 코드에 맞추기 스킬의 교훈 표
판단 순서 값을 고치기 전에 로직을 의심하기 시뮬레이션 절차
사전 조건 레퍼런스 문서 확인 없으면 실행 중단

시뮬레이션 사례가 이 구분을 잘 보여 줍니다. 전체 평균만 보면 목표 근처라 통과처럼 보였지만, 세부 분포를 대조하자 구현 결함이 나왔습니다. 값을 맞추는 쪽으로 고쳤다면 결함은 그대로 남았을 것입니다. 그래서 숫자가 맞더라도 어떤 경로로 맞았는지 보도록 절차를 적었습니다.

3월 대화를 원문 그대로 남기게 한 요청도 다시 볼 만합니다. 요약은 읽기 쉽지만 제 의도와 실수를 지웁니다. 원문을 남기면 나중에 같은 피드백이 몇 번 나왔는지 찾을 수 있고, 규칙으로 옮길 문장도 그대로 가져올 수 있습니다. 대신 기록이 길어지고, 민감한 내용이 함께 남을 수 있습니다. 그래서 원문을 그대로 공개하지 않고 작업 문서 안에서만 쓰는 것이 맞다고 봅니다. 또 슈퍼 보너스 보고서의 패턴이 다른 게임에도 통할지는 그때 알 수 없었습니다. 한 번의 프로젝트에서 나온 패턴이므로, 규칙으로 옮긴 뒤에도 가설로 다뤄야 했습니다. 제가 교정을 세 번 했다는 기록도 그만큼 사람이 구조를 알고 있었다는 뜻이어서, 구조를 모르는 사람이 같은 결과를 얻는다는 근거는 아닙니다.

고찰

사실은 피드백을 규칙으로 옮겼고 팀에 배포했다는 것까지입니다. 이 묶음이 동료의 시간을 얼마나 줄였는지는 재지 않았습니다.

공식 문서도 비슷한 구분을 합니다. Claude Code 모범 사례는 “If something has to happen every time, make it a hook”라고 적습니다. 지침은 지침일 뿐 어길 수 있다는 뜻입니다. 제가 레퍼런스 문서가 없으면 실행을 막은 것도 이쪽에 가깝습니다.

반론도 있습니다. 규칙은 쌓일수록 무거워지고, 지금 맞는 판단이 나중에 틀려도 계속 적용됩니다. 실제로 몇 달 뒤 저는 스킬을 절반으로 줄였습니다. 이때의 규칙 축적이 그 부담까지 함께 만들었다는 것은 제 해석입니다.

MCP와 서브에이전트를 도입한 날짜도 기록상 첫 사용일 뿐입니다. 언제 처음 눌렀는지와 업무에 자리 잡은 시점은 다릅니다. 표의 날짜를 이 시기에 기능을 모두 익혔다는 뜻으로 읽으면 과장입니다. 팀 전체가 얼마나 따라왔는지도 이 표에서는 알 수 없습니다. 설치 안내를 올린 것과 동료가 쓰는 것은 다른 일이기 때문입니다.

이 글의 수치와 날짜는 도구 사용의 변화를 보여 줄 뿐, 일의 품질을 보여 주지는 않습니다.

일반화한 교훈

질문하고 답을 받는 도구에서, 정해진 절차를 맡기고 외부 도구까지 연결하는 쪽으로 쓰임이 바뀌기 시작했습니다. 제가 할 일도 프롬프트를 쓰는 데서 피드백을 절차로 남기는 쪽으로 옮겨 갔습니다.

같은 말을 두 번째 할 때가 파일로 옮길 때입니다. 다만 규칙마다 언제 지울지도 함께 생각해야 합니다. 반드시 지켜야 하는 것은 실행으로 막고, 판단이 필요한 것만 글로 남기는 편이 낫습니다.

다음 단계

맡기는 범위가 넓어지면서 다른 문제가 생겼습니다. 대량 위임으로 이어집니다.

배포한 규칙이 실제로 읽히고 지켜지는지는 audit으로 파일 상태까지만 볼 수 있습니다. 행동까지 확인하는 방법은 뒤의 글에서 다룹니다.
