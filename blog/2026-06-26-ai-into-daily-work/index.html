AI2026.06.26

업무 투입: 스킬과 서브에이전트, MCP를 쓰기 시작하다

2026년 3월부터 6월 사이 AI 도구가 실제 업무 흐름으로 들어왔습니다.

(2026년에 돌아보며 쓴 글입니다.)

도구를 시험하던 시기가 지나고, 2026년 봄에 AI를 실제 업무 안으로 넣기 시작했습니다. 2026년 4월 프롬프트 수는 Codex 719건, Claude 503건으로 1월의 66건, 147건보다 크게 늘었습니다.

왜 시작했나

2026년 2월에 기존 슬롯의 슈퍼 보너스를 AI와 함께 개발하고, 기획 분석부터 서버, 클라이언트, 리뷰까지 어떻게 진행했는지 보고서를 써서 팀에 공유했습니다. 3월에는 서버 개발 대화를 원문 그대로 남기게 해 제 의도와 피드백을 기록했습니다. 요청에 이렇게 썼습니다.

압축하거나 요약하지말고 프롬프트는 왠만하면 그대로 나의 의도를 파악하여 넣는게 중요

무엇을 시도했나

날짜 처음 쓴 기능
5월 13일 Claude 스킬
6월 16일 Codex 서브에이전트
6월 17일 MCP
6월 26일 Claude 병렬 에이전트
컨텍스트 파일로 세션을 잇기잘못된 가정을 즉시 교정피드백을 규칙으로 정리규칙을 스킬로 묶어 팀에 배포

2월 보고서에 남긴 패턴은 게임 레퍼런스와 컨텍스트 파일로 세션 사이를 잇는 것, 독립 작업은 병렬로 돌리는 것, 리뷰 결과를 바로 수정으로 잇는 것입니다. 잘못된 방향은 세 번 교정했는데, 그때 적은 교훈이 “AI가 잘못된 가정으로 진행할 때 즉시 교정하는 것”입니다.

어디서 막혔고 어떻게 바꿨나

3월 개발에서는 값 파일의 구조가 팀의 기존 코드와 달랐습니다. 저는 같은 실수가 반복되면 안 된다고 적고, 이렇게 피드백했습니다.

효율적인 코드도 좋지만 우리가 원래 만들던 코딩 스타일을 따라가는것도 많이 중요하단다

시뮬레이션에서도 비슷한 일이 있었습니다. 전체 수치만 보면 목표 근처였지만 세부 분포가 달랐고, 세부 지표를 추가해 대조하면서 구현 결함을 찾았습니다. 값을 먼저 고치지 않고 로직이 틀렸을 가능성부터 보는 원칙을 이때 세웠습니다.

이 피드백들을 대화에 흘려보내지 않고 규칙과 스킬로 옮겼습니다.

이전

같은 피드백을 세션마다 다시 말합니다.

이후

피드백을 교훈 표로 스킬에 넣고, 레퍼런스 문서가 없으면 실행을 막습니다.

6월에는 이 묶음을 플러그인으로 팀에 안내했습니다. setup은 규칙 파일 전체를 덮어쓰지 않고 관리 영역과 공유 문서만 추가하고, audit은 문서 상태를 OK, MISSING, DRIFT로 나눠 보여 줍니다. 슬롯 작업에 필요한 기준 문서도 함께 넣었습니다.

2월 보고서에는 의사결정 방식도 적어 두었습니다. AI가 옵션을 제시하면 제가 고르고, AI가 구현합니다. 용어가 틀리면 바로 고치고, 대안을 시도하기 전에 먼저 묻게 했습니다. 1월에는 실제 슬롯의 연출 기능 계획을 세우게 한 뒤 사람이 구현한다면 더 필요한 작업이 있는지 동료들에게 평가를 부탁하기도 했습니다.

배운 것

질문하고 답을 받는 도구에서, 정해진 절차를 맡기고 외부 도구까지 연결하는 쪽으로 쓰임이 바뀌기 시작했습니다. 제가 할 일도 프롬프트를 쓰는 데서 피드백을 절차로 남기는 쪽으로 옮겨 갔습니다.
