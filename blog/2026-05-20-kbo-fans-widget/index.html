KBO Fans 위젯: 오래된 점수를 숨기지 않기

Flutter 앱과 iOS 위젯이 데이터를 주고받는 구조, 갱신 지연 표시, 위젯에서 고친 오류를 코드 기준으로 정리했습니다.

문제 제기

KBO Fans는 내 팀 경기를 앱을 열지 않고 보려고 만든 야구 앱입니다. 수업 제출용 기획서에서 시작해 2026년 3월 30일에 Flutter 앱과 iOS 위젯 확장을 처음 추가했고, 처음 정한 React Native 대신 Flutter를 골랐습니다. 5월 19일부터 데이터를 안정화하며 본격적으로 개발했고, 5월 20일에 딥링크와 지연 표시를 붙였습니다.

배경과 분석 틀

위젯 데이터 문제를 저는 두 질문으로 나눕니다. 얼마나 자주 받을 수 있는가와, 받은 값이 언제 것인지 말해 주는가입니다. 앞은 플랫폼이 제한합니다. 뒤는 제가 정할 수 있습니다. 그래서 뒤쪽에 힘을 썼습니다.

같은 달에 쓴 데이터 갱신 설계에서는 모든 요청을 같게 다루지 않기로 하고 데이터를 네 종류로 나눴습니다.

종류 예 정책
Live 오늘 스코어보드, 현재 타석 네트워크 우선, 짧은 TTL, 오래된 값 대체 허용
Warm cache 오늘 일정, 경기 전 라인업 캐시 우선, 조용히 갱신
Persisted snapshot 지난 경기, 순위 스냅샷 우선, 요청 때 크롤링 안 함
Bundled bootstrap 순위와 기록의 기본값 실패할 때 앱 내장 자산 사용

근거 자료

설계 문서의 갱신 기준은 오늘 스코어보드와 진행 중 경기 상세가 8초, 진행 중 박스스코어가 60초입니다. 서버의 값이 이렇게 빨라도 위젯은 그 속도로 그려지지 않습니다. 코드는 다음 갱신을 .after(nextRefresh)로 요청할 뿐입니다.

서버 스코어보드 TTL 8초
진행 중 박스스코어 TTL 60초
위젯 지연 문구, 진행 중 120초

변경 기록에서 위젯 데이터와 관련한 항목을 뽑으면 이렇습니다.

문제 조치
원천 점수가 빈 경기를 0:0으로 보여 주고 득점 알림까지 계산 –와 점수 확인 중 상태 유지
요약 스코어보드의 0:0이 실제 득점 갱신을 막음 원천 결합 방식 수정
내 팀 미선택 상태의 null이 App Group으로 전달돼 앱 종료 전달 경로 차단
백그라운드 task id는 허용됐지만 handler 미등록으로 시작 직후 종료 등록 경로 수정

시도

Flutter 쪽 WidgetSyncService가 스코어보드를 받아 표시할 경기를 고르고, App Group 저장소에 값을 씁니다. Swift 쪽 WidgetKit은 그 값을 읽어 그리기만 합니다. 백그라운드에서는 Workmanager 작업이 같은 동기화를 실행합니다.

스코어보드 수신표시할 경기 선택App Group에 저장WidgetKit이 읽어 그림

iOS는 위젯 하나가 크기별로 다르게 그립니다. 소형, 중형, 대형과 잠금 화면 3종입니다. Android는 단일 경기 위젯과 오늘 경기 목록 위젯을 따로 등록했습니다.

판단이 바뀐 지점

WidgetKit의 갱신 시점은 앱이 정할 수 없고 요청만 할 수 있습니다. 야구 위젯에서 이것은 오래된 점수가 지금 점수처럼 보인다는 뜻입니다. 갱신을 앱이 보장할 수 없으니, 위젯에 찍힌 점수가 언제 값인지 알리기로 했습니다. 진행 중인 경기는 2분, 그 외에는 15분이 지나면 문구를 바꿉니다.

let ageMs = Int64(Date().timeIntervalSince1970 * 1000) - updatedAtEpoch
let thresholdMs: Int64 = statusKind == "live" ? 2 * 60 * 1000 : 15 * 60 * 1000
if ageMs > thresholdMs {
  return "업데이트 지연 \(updatedAt)"
}
return "업데이트 \(updatedAt)"

같은 이유로 모르는 값을 다른 값으로 바꾸지 않았습니다.

값을 채우면

투구 데이터가 없을 때 볼, 스트라이크, 아웃이 0으로 보이고, 원천 점수가 빈 경기는 0:0으로 보입니다.

지금

볼, 스트라이크, 아웃은 숨깁니다. 빈 점수는 –로 표시합니다.

CHANGELOG에 남은 위젯 오류 가운데 구조와 관련된 것이 둘 있습니다.

증상 조치
갱신이 잠시 실패한 뒤 같은 경기 정보로 다시 갱신되지 않음 위젯과 Live Activity 동기화가 끝난 뒤에 비교용 서명을 기록
아직 받지 못한 상태를 경기 없는 날로 표시 두 상태를 구분

첫 번째는 같은 내용이면 건너뛰려고 둔 서명이 실패까지 성공처럼 기억해서 생길 수 있는 문제입니다.

위젯 데이터 경로가 길다는 점도 오류의 원인이었습니다. 서버의 스코어보드, 앱의 동기화 서비스, App Group 저장소, 위젯 렌더링까지 값의 뜻이 네 번 옮겨 갑니다.

앱이 알 수 있는 것

언제 받았는지, 받은 값이 비어 있는지, 동기화가 끝났는지.

앱이 알 수 없는 것

시스템이 언제 위젯을 다시 그릴지, 사용자가 언제 볼지.

그래서 위젯에는 값과 함께 갱신 시각과 상태 종류를 저장합니다. 지연 문구는 이 값을 그리는 시점에 계산합니다. 저장할 때 계산하면 나중에 봐도 “방금”으로 남기 때문입니다. 서명 비교를 동기화 뒤로 옮긴 것도 같은 맥락입니다. 성공했다고 기록하는 시점이 실제 성공보다 앞서면 실패한 내용을 다시 시도하지 않습니다.

비슷한 처리는 Live Activity와 알림에도 필요했습니다. 위젯만 고치면 알림이 같은 빈 점수로 득점을 계산할 수 있기 때문입니다. 그래서 변경 기록에도 앱, 위젯, Live Activity를 함께 적은 항목이 많습니다. 표시 규칙을 화면마다 두지 않고 한 곳에서 판단하는 구조가 필요하다는 뜻입니다.

고찰

2분과 15분이라는 기준은 사용자 조사로 정한 값이 아닙니다. 경기 진행 중이면 2분도 길 수 있고, 지연이라는 말이 자주 보이면 앱이 고장 난 것처럼 보일 수 있습니다. 이 값이 적절한지는 아직 모릅니다.

지연 표시가 근본 해결도 아닙니다. 사용자가 원하는 것은 최신 점수이고, 표시는 받지 못한 상태를 정직하게 알릴 뿐입니다. 그럼에도 표시를 택한 이유는 틀린 점수를 맞는 값처럼 보여 주는 쪽이 더 나쁘다고 봤기 때문입니다. NN/g의 시스템 상태 가시성 원칙과 같은 방향이지만, 이 판단이 신뢰로 이어지는지는 측정하지 못했습니다. 제 해석입니다.

0을 숨긴 결정은 비용이 작지 않았습니다. 앱, 위젯, Live Activity, 알림 계산까지 같은 뜻을 지켜야 했고, 변경 기록을 보면 비슷한 오류가 여러 번 나왔습니다. 모름을 타입으로 강제했다면 일찍 막았을 것이라고 생각합니다.

이 판단을 첫 위젯 작업에서 모두 한 것은 아닙니다. 0:0 표시와 같은 문제는 여러 경로에서 다시 나왔고 그때마다 고쳤습니다. 글에서는 원칙처럼 정리했지만 실제로는 오류를 보고 배운 순서입니다.

일반화한 교훈

사용자에게 보이는 값이 믿을 만한지를 화면에서 정직하게 말하는 방식을 여기서 처음 코드로 적었습니다. 2026년 10월의 PC Supporter 규칙 엔진에서 모르면 unknown으로 답하게 한 것과 같은 판단입니다. 나중에 쓴 앱 기획 문서에도 연결 상태 화면이 실제 서버 전달 성공을 뜻하지 않는다고 구분해 적었습니다.

갱신을 보장할 수 없는 화면에는 값과 함께 시점을 보여 줍니다. 값이 없는 것과 0은 끝까지 다른 상태로 다룹니다. 데이터마다 갱신 정책을 나누면 요청을 줄이면서도 어떤 값이 얼마나 오래된 것인지 말할 수 있습니다.
