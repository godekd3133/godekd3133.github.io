슬롯 개발에서 서버와 클라이언트를 맞춘 과정

화면의 금액과 서버 정산이 어긋날 때 어느 층의 문제인지 가려낸 과정을 정리했습니다.

슬롯 게임에서 플레이어가 믿는 것은 화면에 보이는 금액입니다. 그런데 정산은 서버가 하고 화면은 클라이언트가 그립니다. 서버와 클라이언트를 함께 맡아 온 저는 둘이 어긋나는 문제를 자주 만났습니다. 2026년 5월에 쓴 개발 회고의 결론은 “slot 작업은 한 레이어만 고쳐서는 끝나지 않는다”였습니다.

무엇을 시도했나

보너스 하나를 만들 때 서버 결과에 있는 필드가 Schema.json에 없거나, Schema.json에는 있는데 Schema.txt에 빠지는 일이 반복됐습니다. 2026년 2월 작업에서도 리뷰가 잡은 가장 큰 항목이 Schema 미등록이었고, 저는 그때 “Schema는 txt도 바꿔야해”라고 교정했습니다. 서버가 다른 값을 내려줘서 디버그 설정이 클라이언트까지 오지 않은 적도 있습니다. 그래서 하나의 묶음으로 보고 서버부터 순서대로 고치기로 했습니다.

서버 응답Schema.jsonSchema.txt클라이언트 데이터 경로화면 표시

이 순서는 이후 Response Schema를 바꿀 때의 완료 기준이 됐습니다.

어디서 막혔고 어떻게 판단을 바꿨나

숫자가 다르면 먼저 틀린 쪽부터 가렸습니다.

보드 금액의 합과 결과 팝업이 다르다는 QA 티켓이 수정 후 다시 열린 적이 있습니다. 화면만 보면 팝업이 의심스러웠지만, 서버 응답을 계산해 보니 총액은 맞았고 보드의 표시 값이 따라가지 못하고 있었습니다. AI 에이전트와 함께 같은 응답을 강제로 재생하는 재현 경로를 만들었고, 수정 뒤 보드 합계와 팝업이 일치하는 것을 확인해 리뷰로 넘겼습니다.

다른 보너스의 QA 티켓에서는 잭팟 심볼에 배수가 붙어 정산되어 보였습니다. 서버는 잭팟 금액과 일반 금액을 나눠 계산하고 있었고, 클라이언트만 전체 합계에서 금액을 되짚어 계산하고 있었습니다. 클라이언트가 서버와 같은 기준을 쓰도록 고쳤습니다.

코드가 아니라 빌드가 원인일 때도 있었습니다. 릴 설정을 조정한 뒤 화면이 맞지 않아 보인 일입니다. 소스에는 새 값이 들어 있었지만 서버가 실제로 읽는 생성 파일에는 이전 값이 남아 있었습니다. 파일을 다시 생성하자 값이 일치했고, 이 조건은 문서에 적어 두었습니다.

배운 것

지금은 티켓에도 빌드 통과와 실제 화면 확인을 나눠 적습니다. 빌드가 통과했다고 플레이어가 보는 화면까지 확인된 것은 아니기 때문입니다. 원인, 수정, 결과를 나눠 적으면 QA가 바로 읽을 수 있고, 아직 조사만 한 티켓도 그렇게 표시할 수 있습니다.
