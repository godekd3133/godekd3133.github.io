경력과 회고2026.11.02

슬롯 개발에서 서버와 클라이언트를 맞춘 과정

화면의 금액과 서버 정산이 어긋날 때 어느 층의 문제인지 가려낸 과정을 정리했습니다.

슬롯 게임에서 플레이어가 믿는 것은 화면에 보이는 금액입니다. 그런데 정산은 서버가 하고 화면은 클라이언트가 그립니다. 서버와 클라이언트를 함께 맡아 온 저는 둘이 어긋나는 문제를 자주 만났습니다. 2026년 5월에 쓴 개발 회고의 결론은 “slot 작업은 한 레이어만 고쳐서는 끝나지 않는다”였습니다.

문제 제기

화면의 금액이 틀려 보일 때 어느 층을 먼저 의심해야 할까요. 처음 고른 곳이 틀리면 고친 뒤에도 같은 티켓이 다시 열립니다. 이 글은 제가 겪은 사례를 분류하고, 확인 순서가 어떻게 도구로 옮겨졌는지 정리합니다. 게임 이름과 수치는 공개 범위에 맞춰 뺐습니다.

배경과 분석 틀

서버와 클라이언트 사이에는 값이 지나가는 층이 여러 개 있습니다. 각 층에 물을 질문을 하나씩 정했습니다.

층 묻는 질문 확인 방법
서버 응답 계산 결과가 맞는가 응답 값을 직접 계산
스키마 필드가 전달되는가 Schema.json과 Schema.txt 비교
데이터 경로 클라이언트가 같은 값을 읽는가 필드 경로 추적
표시 값 화면이 그 값을 그리는가 같은 응답을 재생해 화면 확인
빌드 상태 실행 중인 파일이 최신인가 생성 파일과 소스 비교

이 방식은 계약 테스트와 비슷한 생각입니다. 마틴 파울러는 외부 서비스와의 약속을 따로 검사하는 테스트를 계약 테스트라고 설명합니다. 제 경우에는 아직 자동 검사가 아니라 사람과 에이전트가 따르는 절차에 가깝습니다.

근거 자료

  • 2026.05 개발 회고에 한 레이어만 고쳐서는 끝나지 않는다고 기록
  • 2026.06 서버 응답과 스키마 기준을 담은 워크플로 플러그인 설치 안내를 팀에 공유
  • 2026.07 응답 재생 도구 Runtime Lab 첫 버전
  • 2026.09 재생과 증거 수집을 재사용하는 게임별 테스트 구조를 팀에 제안

무엇을 시도했나

보너스 하나를 만들 때 서버 결과에 있는 필드가 Schema.json에 없거나, Schema.json에는 있는데 Schema.txt에 빠지는 일이 반복됐습니다. 2026년 2월 작업에서도 리뷰가 잡은 가장 큰 항목이 Schema 미등록이었고, 저는 그때 “Schema는 txt도 바꿔야해”라고 교정했습니다. 서버가 다른 값을 내려줘서 디버그 설정이 클라이언트까지 오지 않은 적도 있습니다. 그래서 하나의 묶음으로 보고 서버부터 순서대로 고치기로 했습니다.

이 순서는 이후 Response Schema를 바꿀 때의 완료 기준이 됐습니다.

어디서 막혔고 어떻게 판단을 바꿨나

숫자가 다르면 먼저 틀린 쪽부터 가렸습니다.

보드 금액의 합과 결과 팝업이 다르다는 QA 티켓이 수정 후 다시 열린 적이 있습니다. 화면만 보면 팝업이 의심스러웠지만, 서버 응답을 계산해 보니 총액은 맞았고 보드의 표시 값이 따라가지 못하고 있었습니다. AI 에이전트와 함께 같은 응답을 강제로 재생하는 재현 경로를 만들었고, 수정 뒤 보드 합계와 팝업이 일치하는 것을 확인해 리뷰로 넘겼습니다.

다른 보너스의 QA 티켓에서는 잭팟 심볼에 배수가 붙어 정산되어 보였습니다. 서버는 잭팟 금액과 일반 금액을 나눠 계산하고 있었고, 클라이언트만 전체 합계에서 금액을 되짚어 계산하고 있었습니다. 클라이언트가 서버와 같은 기준을 쓰도록 고쳤습니다.

코드가 아니라 빌드가 원인일 때도 있었습니다. 릴 설정을 조정한 뒤 화면이 맞지 않아 보인 일입니다. 소스에는 새 값이 들어 있었지만 서버가 실제로 읽는 생성 파일에는 이전 값이 남아 있었습니다. 파일을 다시 생성하자 값이 일치했고, 이 조건은 문서에 적어 두었습니다.

증상 처음 의심한 곳 실제 원인
보드 합계와 팝업 불일치 팝업 보드 표시 값
잭팟에 배수가 붙어 보임 정산 클라이언트의 금액 역산
릴 설정 후 화면 불일치 소스 값 다시 생성하지 않은 파일
이전

보이는 증상이 나온 층을 고칩니다.

이후

서버 응답, 표시 값, 빌드 상태를 차례로 가린 뒤 고칩니다.

배운 것

지금은 티켓에도 빌드 통과와 실제 화면 확인을 나눠 적습니다. 빌드가 통과했다고 플레이어가 보는 화면까지 확인된 것은 아니기 때문입니다. 원인, 수정, 결과를 나눠 적으면 QA가 바로 읽을 수 있고, 아직 조사만 한 티켓도 그렇게 표시할 수 있습니다.

이 작업들은 대부분 AI 에이전트와 함께 진행했습니다. 원인 판단과 최종 확인은 제가 했습니다. 층을 나눠 보는 이 습관이 스킬의 보고 형식과 Runtime Lab의 재현 경로로 들어갔습니다.

찾는 순서를 절차로 적기

표의 사례를 다시 보면, 틀린 쪽을 가리는 데 공통으로 쓴 순서가 있습니다.

  1. 서버 응답만 놓고 기대값을 계산합니다. 맞으면 서버를 고치지 않습니다.
  2. 응답의 필드가 두 스키마 파일에 있는지 봅니다. 없으면 클라이언트 코드까지 갈 필요가 없습니다.
  3. 클라이언트가 그 값을 그대로 쓰는지, 합계에서 되짚어 계산하는지 봅니다. 잭팟 사례가 여기에서 갈렸습니다.
  4. 같은 응답을 재생해 화면과 팝업을 함께 봅니다. 사람이 다시 돌려 볼 수 있게 재현 경로를 남깁니다.
  5. 소스와 실제 읽는 파일이 같은지 확인합니다. 릴 설정 사례가 여기에서 끝났습니다.

이 순서가 팀 도구로 옮겨지는 과정도 기록에 있습니다. 2026년 6월에 공유한 워크플로 플러그인의 점검 명령은 문서 상태를 정상, 누락, 차이로 나눠 보여 줍니다. 팀 기준 문서가 자리마다 달라지는 것도 같은 종류의 어긋남이라고 봤기 때문입니다.

2026년 9월 팀 논의에서는 Runtime Lab의 입력과 응답 재생, 검사, 증거 수집을 재사용하고, 그 위에 게임별 테스트 계약과 실행 수명 관리를 얹는 구조를 제안했습니다. 이때 AI에는 작업 의도 해석, 관련 코드 탐색, 테스트 초안, 수정과 실패 분석을 맡기기로 적었습니다. 이 구조는 제안 단계이고, 글을 쓰는 시점에 게임별로 돌고 있지는 않습니다.

사람이 고르는 재생

재현이 필요한 티켓에 사람이 응답을 골라 돌립니다. 빠르게 시작할 수 있지만 고른 경우만 확인합니다.

게임별 테스트 계약

게임마다 지켜야 할 조건을 적어 두고 반복해서 돌립니다. 계약을 만들고 유지하는 비용이 듭니다.

절차를 적어 둔 뒤의 티켓 형식도 달라졌습니다. 원인, 수정, 결과를 나누고, 빌드 통과와 실제 화면 확인을 다른 줄에 적습니다. 조사만 끝난 경우에는 그렇게 표시합니다. QA가 어디까지 믿고 다시 시험할지 정할 수 있게 하려는 형식입니다. 에이전트에게 맡길 때도 같은 형식을 요구합니다. 다만 보고 형식이 좋아졌다고 판단이 맞는 것은 아니어서, 원인 판단과 최종 확인은 제가 합니다.

고찰

표의 세 사례 모두 처음 의심한 곳과 원인이 달랐습니다. 세 건만으로 일반적인 비율을 말할 수는 없습니다. 제 해석으로는 화면에 증상이 보이면 그 근처를 먼저 고치고 싶어지기 때문에, 순서를 미리 정해 두는 것이 도움이 됐습니다.

반론도 있습니다. 모든 티켓에서 다섯 층을 다 확인하면 작은 표시 버그에도 시간이 듭니다. 그래서 금액, 잭팟, 응답 필드가 걸린 경우에만 전체 순서를 적용하는 편이 현실적이라고 봅니다. 응답 재생에도 한계가 있습니다. 기록한 응답은 그 조건만 재현하므로, 서버 계산이 바뀌면 재생 데이터가 오래된 값이 될 수 있습니다.

이 글에서 확인한 것

사례별 원인과 수정 후 일치, 절차가 도구로 옮겨진 순서입니다.

확인하지 못한 것

이 절차로 재발이 얼마나 줄었는지입니다. 전후 수치를 재지 않았습니다.

일반화한 교훈

  • 증상이 나타난 곳과 원인이 있는 곳을 분리해서 적습니다.
  • 값이 지나가는 층마다 확인 방법을 하나씩 정해 두면, 사람이 바뀌어도 같은 순서로 찾을 수 있습니다.
  • 생성 파일은 원인 후보에 포함합니다. 소스만 보면 놓칩니다.
  • 빌드 통과, 실제 화면 확인, 조사만 한 상태를 서로 다른 말로 적습니다.

다음에 할 것

같은 응답을 재생해 확인하는 일을 사람이 고르지 않아도 게임별 테스트로 돌게 하는 구상이 남아 있습니다. 어떤 층의 오류가 어느 단계에서 잡히는지도 벤치마크로 재 보고 싶습니다.
