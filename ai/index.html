슬롯 개발 워크플로

스킬: 에이전트가 따르는 작업 절차 문서. 신규 슬롯 제작을 단계별 스킬로 나눈 흐름입니다. 제작 스킬은 순서와 통과 조건만 정하고, 방법은 각 단계 스킬이 맡습니다.

  1. 1기획 분석·질문 확정

    기획서를 구조화된 명세로 옮기고 불명확한 점을 질문으로 확정합니다.

  2. 2서버 로직·수학 작성

    기본 게임은 참고만 하고 기획서에서 로직과 수학 값을 새로 작성합니다.

  3. 3시뮬레이션

    시뮬레이터를 돌려 수학 값과 보너스 지표를 확인합니다.

  4. 4모듈 복제·피처 이식

    기본 게임의 클라이언트 모듈을 복제하고 피처를 빼거나 가져옵니다.

  5. 5Response Schema 동기화

    서버 응답부터 클라이언트 데이터 경로까지 이름과 구조를 맞춥니다.

  6. 6클라이언트 흐름 구현

    상태 그래프와 연출 컨트롤러를 만들고 아트 자리에 자리표시자를 둡니다.

  7. 7아트 장착

    납품마다 차이만 확인해 교체하고, 확인 안 된 항목은 자리표시자로 둡니다.

  8. 8런타임 플레이 검증

    GS Unity로 Editor를 다루고 Runtime Lab으로 재현·판정·캡처합니다.

  9. 9문서·인계

    기획, 서버, 클라이언트 레퍼런스 문서와 작업 기록을 남깁니다.

시도와 배운 점

  1. 2025.08

    도구 탐색

    풀려던 것
    Codex와 Claude Code가 실제 일에 쓸 만한지 시험했습니다.
    알게 된 것
    몰아서 써 보고 멈추기를 반복해, 아직 일상 작업 방식은 아니었습니다.
    그래서 한 일
    2026년 봄부터 실제 업무에 넣기 시작했습니다.

  2. 2026.05

    스킬 흐름

    풀려던 것
    팀의 슬롯 개발 업무를 스킬의 흐름으로 자동화하고, 같은 기준으로 시작하고 싶었습니다.
    알게 된 것
    규칙 파일의 범위가 디렉터리마다 달라, 파일을 통째로 덮지 않고 자동 갱신 영역만 고치는 방식으로 표준을 배포했습니다. 다만 스킬은 터미널에서 직접 불러야 합니다.
    그래서 한 일
    스킬을 팀의 진입점으로 만들 앱을 설계했습니다.

  3. 2026.06

    개인 에이전트 AgentB

    풀려던 것
    코딩 도구 밖의 일까지 슬랙에서 에이전트에게 맡기고 싶었습니다.
    알게 된 것
    슬랙 안에서는 태그해야 움직인다는 플랫폼 제한이 가장 아쉬웠습니다.
    그래서 한 일
    스킬, 세션 이동 도구, 통화, 로컬 모델 연결을 시도했습니다.

  4. 2026.07

    GS App

    풀려던 것
    2026년 7월 무렵부터 업무 전반을 AI에 맡기기 시작했습니다. 게임 정보, 이슈, 룰 문서, AI 작업을 잇고, 스킬 단위로 작업을 시작하게 하려 했습니다.
    알게 된 것
    일주일 뒤 패키지 앱을 점검해 보니 문제는 기능 부족이 아니었습니다. 기능이 화면 단위로 쌓여 사용자가 맥락을 매번 다시 조립해야 했습니다.
    그래서 한 일
    준비, 실행, 검증, 인계를 하나의 작업 흐름으로 잇는 쪽으로 다시 설계했습니다.

  5. 2026.07

    Runtime Lab

    풀려던 것
    코드와 빌드 검사를 통과해도 실제 화면의 연출과 상태는 확인되지 않았습니다.
    알게 된 것
    녹화 응답 재생, 규칙 판정, 구간 캡처를 직접 만들었습니다. 정적 검사와 런타임 확인을 나눠 보고하는 규칙도 유지했습니다.
    그래서 한 일
    재생 결과는 개발 환경의 증거로만 두고, 런타임 버그 재현 스킬에 연결했습니다.

  6. 2026.09

    GS Unity 활용

    풀려던 것
    에이전트가 Unity Editor를 안정적으로 다룰 경로가 필요했습니다. 도구는 동료가 만든 Rust CLI입니다.
    알게 된 것
    Editor 제어는 동료의 도구를 쓰고, 저는 그 위의 검증 절차와 재현 도구에 집중했습니다. 앱, 스킬, 벤치마크에 연결하고 작은 수정에 기여했습니다.
    그래서 한 일
    플레이 검증 스킬의 진입, 스핀, 상태 확인 절차를 이 CLI 기준으로 썼습니다.

  7. 2026.10

    스킬 재정리

    풀려던 것
    스킬이 많아졌고 신규 제작의 진입점도 여러 갈래였습니다.
    알게 된 것
    순서와 통과 조건을 맡는 스킬과 방법을 맡는 스킬을 나눴습니다. 스킬을 통합하거나 없애 절반 수준으로 줄였고, 손으로 쓴 통과 표시는 인정하지 않기로 했습니다.
    그래서 한 일
    단계마다 서브에이전트를 쓰는 제작 파이프라인 스킬로 묶었습니다.

  8. 2026.10

    벤치마크

    풀려던 것
    스킬과 지침을 바꿔도 결과가 좋아졌는지 말할 근거가 없었습니다.
    알게 된 것
    초기 문제는 대부분 채점기와 에이전트 실행 환경에 있었습니다. 작은 비교 실험은 표본이 적어 판단할 수 없었고, 스킬 문서가 정답 파일을 미리 드러낸 문제도 찾았습니다.
    그래서 한 일
    채점기 자체 점검과 통계 규칙을 넣었습니다. 본 비교 실험은 보류 중입니다.

  9. 2026.10

    개인 제품

    풀려던 것
    기획부터 배포까지 맡는 개인 제품에도 같은 방식을 쓰기 시작했습니다.
    알게 된 것
    브라우저와 시뮬레이터로 화면을 확인하는 일까지 도구에 맡기게 됐습니다.
    그래서 한 일
    제품에서도 자동 검사로 확인한 것과 사람이 확인해야 할 것을 나눠 적습니다.

지금까지 배운 것

완료를 한 단어로 말하지 않기

서버, Data Schema, 클라이언트, 런타임, 인계를 나눠 보고하게 했습니다. 빌드 통과는 화면이 맞다는 뜻이 아닙니다.

기록은 증거가 아니다

에이전트가 쓴 진행 기록과 통과 표시는 믿지 않고 최종 상태와 실제 실행 로그로 판정합니다.

도구도 먼저 의심하기

벤치마크 초기 문제는 대부분 채점기에 있었습니다. 정답을 채점해 보고, 일부러 넣은 결함이 커질수록 점수가 내려가는지 확인해 도구부터 점검합니다.

약점: 검증 누락

문제: AI에 많이 맡길수록 수정 뒤 검증을 빠뜨리는 일이 잦았습니다. 조치: 완료 조건을 말이 아니라 실행 결과로 바꿨습니다. 변화: 어디까지 실행해 확인했고 무엇이 남았는지 나눠 보고합니다.
