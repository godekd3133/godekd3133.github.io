How Far Can Agent Results Be Trusted? A Benchmark

I built a benchmark that has agents rebuild released slots and scores the results, and the first thing to doubt was the scorer.

The problem

Whenever I changed skills or instructions, I had no basis for saying things improved. Nor could I say how cutting skills in half affected results. So in October 2026 I built a slot development agent benchmark. The goal isn’t 100 points. It’s explaining in numbers how much and why scores shift when models, skills, or instructions change.

Background and framing

This benchmark borrows its frame from SWE-bench, which pairs real issues with the changes that fixed them. I adapted it to released slots. There are 10 tasks: 6 that build a whole game and 4 that add a feature.

The statistics document’s judgment rules report three axes together: accuracy, cost, and time.

What's never merged

Different task versions, runtimes, models, settings, or tool fingerprints don't share a cell.

When I say significant

Only when a 95% interval, resampling tasks and runs, excludes 0. At least 5 repeats are recommended.

Evidence

These are October 2026 records of selfcheck, which puts the answer through the scorer. Game tasks didn’t reach 100, so causes were being traced, and some values changed afterward.

4 feature tasks: 100 each
Game task A: 91.4
Game task B: 89.7
Game task C: 88.3

The debug feature task’s early baseline was answer 100, no change 0, partial answer 75. These values came after fixing the gate points given to no-change runs. A run goes in this order.

python3 setup.py <task>             # create start state
python3 score.py --selfcheck <task> # check scorer with answer
python3 run.py <task> --condition no-skills --model <model>
python3 score.py <run ID>
python3 compare.py --case <task>

Early defects in the work log include 15 external connectors left open to agent runs. Checking current skill documents found 19 places mentioning task answer files, and I added a check that records them.

Attempts

I roll a released slot’s code back to just before the answer went in and have an agent rebuild it. It runs without human input in a copy with no history, and results are compared to the shipped implementation.

Create start state from code just before the answerScore the answer to check the scorerRun the agentRe-judge from final state
Principle Details
Scoring Prefer deterministic checks like build, simulation, diff, and schema comparison. Don’t trust the agent’s progress notes.
Isolation Running agents can’t read the answer key. Worktrees share history with the answer branch, so I didn’t use them.
Comparison Different run conditions don’t mix in statistics. A single score difference doesn’t count as evidence.

Where my judgment changed

Most early problems were in my tools, not the agents.

  • Misaligned path settings cost any agent a fixed number of points.
  • Some tasks didn’t score near full even with the answer. Some were path-handling false positives.
  • Runs that changed nothing were getting some points.
  • Resource use was undercounted.
  • External connectors were open during agent runs, so conditions weren’t isolated.
First thought

Build a tool to measure agents.

Changed order

Measure the tool first. The answer should score nearly 100, no change should score low, and scores should fall as injected defects grow.

Did skills help?

I finished one small experiment: a task adding a debug feature, run with and without skills. Analysis suggested skill wording may have induced failure. But as my log says, a 3:3 sample can’t decide it. I also found a skill document introducing answer files as though they already existed.

I made run conditions explicit too. Turning skills or features on and off is a condition, so their value can be compared, and each result package includes video, code, structure visualizations, and a setup guide for a person to review. The same task runs on either Claude or Codex.

Comparison metrics aren’t a single average score either. Results shift under the same conditions, so repeats are needed, and short averages can be fooled by one good run. So the document sets what to check before judging.

Metric Question it answers
pass@1 What’s the chance of success in one run?
pass^k Does it succeed k times in a row?
Cost and time What did the same score cost?
Normalized score Where between no change and the answer?
Minimum detectable difference How small a difference can these repeats show?

There are questions this benchmark can’t answer. It doesn’t measure time against human developers, ability to read design intent, or coordination with teammates. Because it rolls back from a point when the answer went in, it covers only situations where the design is already organized. The hardest part of real work may be left out.

Reflection

Scorer problems aren’t unique to my benchmark. The UTBoost paper found 36 SWE-bench tasks with insufficient tests and reported 345 wrong patches labeled as passing. Rankings changed after correction. If a widely used benchmark has this, I have no reason to trust my scorer. Google’s mutation testing also breaks code on purpose to see whether tests catch it. My idea of comparing planted defects with scores has the same structure.

My design has limits too. With the shipped implementation as the answer, a better different implementation can lose points. A false positive where a distractor regex matched the answer actually occurred. Nothing guarantees shipped code is the best either. So scores should be read for comparing conditions, not as absolute quality.

Holding the main experiment is a fact. If I give one reason, a comparison run while the scorer still moves would need rerunning. But that’s my interpretation looking back now. I may also be putting off the experiment by polishing measurement.

I’m also careful about making benchmark scores a team goal. Goodhart’s law says a measure loses value when it becomes a target, which is also why the goal isn’t 100.

Sampling remains a problem. The 10 tasks are a subset of released slots that I picked, and may favor skills that know my team’s way of working. Each run’s cost and disk use are also large, so filling recommended repeats isn’t easy. I have to accept that small differences may never be visible.

General lessons

I can now say I can’t answer, with evidence. Not trusting agents’ completion reports had to apply equally to measuring tools. A scorer is code and can be wrong, and if it’s wrong, every comparison on top is wrong. So the statistics document says to fix the rules first when a baseline check warns.

Before a comparison experiment, I first test the measuring tool with the answer, no change, and deliberately broken results. Answer isolation must cover indirect paths like skill documents, not only file permissions. And rules against concluding from small samples should come first.

Next steps

I put the main comparison on hold, so I still can’t say how much skills change results. The runtime path is verified on only one task, and scorer checks for some tasks are in progress. Next is an experiment with fixed conditions after those checks finish.

In November I plan to tie the runtime path to Runtime Lab and check the debugging process as well. I also want to make it easier to connect the production skill and the benchmark.
