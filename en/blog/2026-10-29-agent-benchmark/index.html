How Far Can Agent Results Be Trusted? A Benchmark

I built a benchmark that has agents rebuild released slots and scores the results, and the first thing to doubt was the scorer.

Whenever I changed skills or instructions, I had no basis for saying things improved. Nor could I say how cutting skills in half affected results. So in October 2026 I built a slot development agent benchmark. The goal isn’t 100 points. It’s explaining in numbers how much and why scores shift when models, skills, or instructions change.

What I tried

I roll a released slot’s code back to just before the answer went in and have an agent rebuild it. It runs without human input in a copy with no history, and results are compared to the shipped implementation.

Principle Details
Scoring Prefer deterministic checks like build, simulation, diff, and schema comparison. Don’t trust the agent’s progress notes.
Isolation Running agents can’t read the answer key. Worktrees share history with the answer branch, so I didn’t use them.
Comparison Different run conditions don’t mix in statistics. A single score difference doesn’t count as evidence.

Where I got stuck and how my judgment changed

Most early problems were in my tools, not the agents.

  • Misaligned path settings cost any agent a fixed number of points.
  • Some tasks didn’t score near full even with the answer. Some were path-handling false positives.
  • Runs that changed nothing were getting some points.
  • Resource use was undercounted.
  • External connectors were open during agent runs, so conditions weren’t isolated.
First thought

Build a tool to measure agents.

Changed order

Measure the tool first. The answer should score nearly 100, no change should score low, and scores should fall as injected defects grow.

Did skills help?

I finished one small experiment: a task adding a debug feature, run with and without skills. Analysis suggested skill wording may have induced failure. But as my log says, a 3:3 sample can’t decide it. I also found a skill document introducing answer files as though they already existed.

I made run conditions explicit too. Turning skills or features on and off is a condition, so their value can be compared, and each result package includes video, code, structure visualizations, and a setup guide for a person to review. The same task runs on either Claude or Codex.

What I learned

I can now say I can’t answer, with evidence. Not trusting agents’ completion reports had to apply equally to measuring tools. A scorer is code and can be wrong, and if it’s wrong, every comparison on top is wrong. So the statistics document says to fix the rules first when a baseline check warns.

What’s next

I put the main comparison on hold, so I still can’t say how much skills change results. The runtime path is verified on only one task, and scorer checks for some tasks are in progress. Next is an experiment with fixed conditions after those checks finish.
