Bright Burn: Collision Handling and Release

Notes on collision handling, map construction, exhibitions, and release for Bright Burn, a vertical-scrolling platformer action game I worked on for six months.

(Written in 2026, looking back.)

While I was repeating 12-hour game jams in high school, Bright Burn was the first game I worked on for a long stretch and took all the way to release. I founded the game development team Oh! Rock and ran two projects with six teammates. Bright Burn is a vertical platform action game we built over six months. I handled the player, shop, enemies, UI, and Google and AdMob integration.

In my self-introduction back then I called a collaborative game an “artwork” and wrote that my final goal was to carry the title of someone who made a game anyone would have heard of at least once.

The question

In a game jam it was enough for a game to run for a few hours. Bright Burn had to hold up when strangers played it at exhibitions, and then it had to ship. This post looks at how I made collisions reliable in a fast platform action game, and how much of the release was integration work outside the game.

Background and framework

I split the collision problem into three questions. Did it touch? Which side touched? Did it pass through between frames? Collider placement answered the first two, and checking the movement path answered the third. The source is not in a public repository, so I rely on my portfolio’s descriptions and code excerpts.

The code that picks the upper map avoids the two maps in use. With fewer than three candidates this loop would never end, so the starting pool size has to be kept. I noticed this while rereading the code now, and there is no record of it actually causing a problem back then.

What I tried

To manage collisions with four-way platforms and enemies, I didn’t use a single Collider. I attached Left, Right, Top, and Bottom child objects around the player, plus one in the center, to tell which side had been touched.

Maps were tilemap pieces joined together. I managed only three slots around the player, Main, SubUp, and SubDown, and picked the next map at random on reaching the end. Redrawing so that a map in use doesn’t come up again looks like this.

do
{
    i_SubUp = Random.Range(0, Maps.Count);
} while (i_SubUp == i_Main || i_SubUp == i_SubDown);
SubUp = Maps[i_SubUp];
SubUp.transform.position = new Vector3(0, 100 * (PlayerMapIndex + 1), 0);

Normal maps joined the candidates when the score passed 2000, and Hard maps past 3000. I managed Game Speed separately for slow motion, showed day and night with a Diffuse shader and Light, and reduced draw calls with atlas images.

Where I got stuck and what I changed

A fast object can pass through a thin one between frames without a collision registering. This is called Bullet Through Paper. Splitting Colliders doesn’t stop it, so I used BoxCast for player and object collisions.

Before

Collisions register only when Colliders overlap. At high speed an object slips through between frames.

After

BoxCast sweeps the movement path ahead of time, so the hit is caught regardless of the frame.

What I learned

The same self-introduction described my temperament. I wrote that I pursue perfection without the slightest error, and called it a double-edged sword: getting stuck on small things costs time, so I try to keep perfectionism from going too far. A six-month team project with a release at the end was a place to practice that restraint.

How it differed from a game jam

Even in the same Unity, a six-month project meant carrying a chosen structure for a long time. Comparing what I handled with game jams shows the difference.

Item 12-hour jam Bright Burn
Role Often everything from design to code Player, shop, enemies, UI, Google and AdMob

Time Engine default Separate Game Speed for slow motion
Visuals Fixed art Diffuse shader and Light for day and night, atlas

A separate Game Speed is small but has lasting effect, because code decides which movements the multiplier applies to during slow motion. Reducing draw calls with an atlas was also performance work ahead of exhibition and release. There is no record of how far the draw calls fell.

The team differed too. I founded Oh! Rock, and we ran two projects. I handled both player and enemies, so I could keep collision rules matched on both sides. That is a guess from the role list, and I have no material proving it actually helped.

I also handled Google and AdMob integration on Ttang-pa-seo that same year, reusing integration I had done once in the next release. Joining map pieces for endless scrolling also appears in both games.

Reflection

The facts are that I used five Colliders together with BoxCast. In my interpretation, this combination solved two separate problems: side detection and pass-through prevention. The records don’t show whether I designed it that way from the start or added to it as problems appeared.

As a counterargument, trying an engine feature such as continuous collision detection first might have reduced the code I had to manage. On the other hand, platform action needs precise landing and wall checks, so explicit checks may have been better. I did not measure a comparison, so I can’t say which was better.

Exhibitions and release also need to be read apart. The exhibition history is fact, but I have no material on the reviews from those events or on player response after release. So I don’t claim results for the game here, only what I implemented and when.

General lessons

  • A bug that looks like one problem may need different tools once split into questions.
  • When retrying a random draw in a loop, check the exit condition first.
  • Put non-game work such as ads and account integration into the release schedule from the start.
