Worklog: Career Center MVP

The day I built the first version of AI mock interviews and aptitude test practice, along with the gaps that a later check exposed.

I built the MVP of an AI mock interview and aptitude practice app. It started from the problem that when you practice alone before an interview, nobody tells you where your answers are weak. I also wrote up the same problem as a worksheet for an Innovation and Entrepreneurship class.

Context of the day

I was also writing class worksheets organizing customer personas and hypotheses. The first version aimed to provide the partner you lack when practicing alone, and I wanted to confirm one interview flow ran to the end before widening features. The latter part of this description is my interpretation.

  • 10.15 AI mock interview and aptitude MVP
  • 10.16 Growth journey and real-interview preparation features
  • 10.18 Job posting choice, device sync, group discussion, class worksheets, fixes from the technical review
  • 10.19-20 Virtual customer interviews played by AI

What I did

Layer Contents
packages/core AI response schema, Korean speech analysis, personality test, generated aptitude test, multiple-choice onboarding
apps/server APIs for company value and past question research, question generation, answer evaluation, summaries
apps/web Onboarding, experience cards, document upload, voice interview room, reports, aptitude screens, PWA

The voice interview room has question reading, captions, follow-up questions, and hands-free. Reports have document consistency, retry comparison, and trends.

Judgment

  • I didn’t lock in one AI provider, bundling four including subscription CLIs, the Claude API, and a trial mode behind one interface. All answer in the same JSON schema.
  • Speech metrics are calculated in core rather than left to AI.
  • Shared platform logic sits in core, leaving room for desktop and mobile apps later.

Where I got stuck

10.15 MVP10.16 Added goal stage and job-posting gap diagnosis10.18 Technical check after apps and sync10.20 Virtual customer interviews

Gaps appeared a few days later. The MVP lacked a goal stage and job-posting gap diagnosis. The October 18 technical check fixed data loss in sync and saving, microphone cleanup, accessibility, and server security issues, and before going public I added subscription CLI blocking and internal address blocking (SSRF).

Weaknesses found after the first version

Here are the October 18 technical review fixes, as weakness, action, and change.

Weakness Action Change
Possible data loss in sync and save Fixed save paths Those loss paths blocked
Screen waiting endlessly on AI Stop, time limit, retry You can leave during a wait
Accessibility gaps Fixed menu focus, contrast, text zoom Reviewed items fixed
Risky providers and addresses when public Blocked subscription CLI, blocked internal addresses Stopped in public configuration

The virtual interviews recorded their method too. Part one asks only about past behavior with no product talk, and part two shows a description with pros and cons. Since AI still answered, the next step is asking people the same questions.

Grouping four providers was also about cost: subscription CLI during development, the API when public, and a keyless mode for trials. In exchange, response quality may vary by provider. A shared JSON schema guarantees only format, and I did not compare content quality that day.

In short, the day’s result was a working first version, and the review and virtual interviews came days later.

Basis for judgment and results

I calculate speech metrics in core so the same values come out whichever provider is used. Here are some of the fields in the type.

fillers: FillerHit[];
fillerTotal: number;
fillerPerMin: number;
repetitions: string[];
longPauses: number;
shortPauses: number;
longestPauseSec: number;
startLatencySec: number;
hedgeCount: number;

The boundary is that even if a model writes the evaluation text, code decides the numbers. Whether these numbers relate to real interview outcomes remains unchecked. The virtual interview record has recommendation scores, but AI played those values, so I don’t present them as evidence here.

The internal address blocking added before going public addresses the same kind of risk as OWASP’s SSRF prevention guidance. Not having it on day one was a weakness, and the technical review turned it into a condition for going public.

What’s next

The MVP only confirmed that features ran. I later checked questions with AI virtual personas, and the document’s first line says these aren’t results confirmed with real customers but assumptions to recheck in real interviews. Real user validation hasn’t happened yet. How I closed the loop afterward is in Getting Users to Answer the Same Question Again, and the skill side continues in the skill flow post.
