Keeping the Slot Server and Client in Agreement

How I worked out which layer was wrong when on-screen amounts and server settlement disagreed.

In a slot game, what the player trusts is the amount on screen. But the server settles while the client draws. Having handled both, I often ran into the two disagreeing. A development retrospective from May 2026 concluded that slot work doesn’t end by fixing one layer.

The question

When an amount on screen looks wrong, which layer should you suspect first? If the first pick is wrong, the same ticket reopens after the fix. This post classifies the cases I ran into and shows how the checking order moved into tools. Game names and figures are left out to stay within what can be published.

Background and framework

Between server and client, a value passes through several layers. I set one question for each.

Layer Question How to check
Server response Is the calculated result right? Calculate from the response values
Schema Is the field delivered? Compare Schema.json and Schema.txt
Data path Does the client read the same value? Trace the field path
Displayed value Does the screen draw that value? Replay the same response and look
Build state Is the running file current? Compare generated files with source

The idea resembles contract testing. Martin Fowler describes a contract test as one that separately checks your agreement with an external service. In my case it is still less an automated check than a procedure people and agents follow.

What I tried

When building a bonus, fields in the server result were repeatedly missing from Schema.json, or present in Schema.json but missing from Schema.txt. In February 2026 too, the biggest review finding was an unregistered Schema entry, and I corrected it by pointing out that the txt also had to change. Once a debug setting never reached the client because the server sent a different value. So I decided to treat these as one bundle and fix them in order from the server.

Server responseSchema.jsonSchema.txtClient data pathScreen display

This order later became the completion standard for Response Schema changes.

Where I got stuck and how my judgment changed

When numbers disagreed, I first determined which side was wrong.

A QA ticket saying the board total and result popup differed reopened after a fix. Looking at the screen, the popup seemed suspect. But calculating the server response showed the total was right and the board’s displayed value was lagging. With an AI agent I built a reproduction path that forced replay of the same response, confirmed after the fix that board total and popup matched, and passed it to review.

In another bonus’s QA ticket, a jackpot symbol appeared to settle with a multiplier. The server calculated jackpot and regular amounts separately, while only the client worked backward from the overall total. I changed the client to use the server’s basis.

Sometimes the cause was the build, not code. After adjusting reel settings, the screen looked wrong. The source had the new values, but a generated file the server actually read still held old ones. Regenerating made them match, and I wrote this condition into the docs.

Symptom First suspect Actual cause
Board total and popup mismatch Popup Board display value
Jackpot appears multiplied Settlement Client back-calculation
Screen mismatch after reel settings Source values File not regenerated

What I learned

Tickets now separate build passes from real screen checks, because a passing build doesn’t confirm what the player sees. Separating cause, fix, and result lets QA read it directly, and a ticket only investigated so far can be marked that way too.

I did most of this work with AI agents. Judging causes and the final check were mine. This layered habit went into skills’ reporting format and Runtime Lab’s reproduction path.

Writing the search order as a procedure

Looking at the table’s cases again, I used a common order to find the wrong side.

  1. Calculate the expected value from the server response alone. If it matches, don’t touch the server.
  2. Check that the response field is in both schema files. If not, there is no need to go as far as client code.
  3. Check whether the client uses that value directly or recalculates it from a total. The jackpot case split here.
  4. Replay the same response and watch the screen and popup together. Leave a reproduction path someone can rerun.
  5. Check that the source and the file actually read are the same. The reel setting case ended here.

Records also show this order moving into team tools. The check command in the workflow plugin I shared in June 2026 sorts document state into OK, missing, and drift. I saw team documents differing per seat as the same kind of mismatch.

In a September 2026 team discussion, I proposed a structure reusing Runtime Lab’s input and response replay, checks, and evidence collection, with per-game test contracts and run lifecycle management on top. I wrote that AI would handle interpreting intent, exploring related code, drafting tests, and analyzing fixes and failures. This is at the proposal stage and isn’t running per game as of this writing.

Replay chosen by people

People pick a response to run for tickets needing reproduction. It starts fast but checks only chosen cases.

Per-game test contracts

Conditions for each game are written down and run repeatedly. Building and maintaining contracts has a cost.

Ticket format changed too once the procedure was written. Cause, fix, and result are separate, and build passed and screen checked sit on different lines. When only investigation is done, it says so. This lets QA decide how far to trust a ticket and what to retest. I ask agents for the same format. A better report format doesn’t make the judgment right, so I still make the cause call and final check myself.

Reflection

In all three cases in the table, the cause differed from the first suspect. Three cases can’t support a general rate. In my interpretation, you want to fix whatever is near the visible symptom, so deciding the order in advance helped.

There is a counterargument. Checking all five layers for every ticket costs time even on a small display bug. So applying the full order only when amounts, jackpots, or response fields are involved seems realistic. Replay has limits too. A recorded response reproduces only that condition, and if the server calculation changes, the replay data can go stale.

Confirmed in this post

The causes of each case, agreement after the fix, the order in which the procedure moved into tools.

Not confirmed

How much this procedure reduced recurrence. I did not measure before and after.

General lessons

  • Write down where a symptom appears and where the cause lies as separate things.
  • Set one way to check each layer a value passes through, so the same order works when people change.
  • Include generated files among the suspects. Reading only the source misses them.
  • Use different words for build passed, screen checked, and investigated only.

What’s next

A plan remains to have replay checks run as per-game tests without a person selecting them. I’d also like to measure with the benchmark which layer’s errors get caught at which stage.
