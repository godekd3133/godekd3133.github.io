Trying to Automate My Team's Work as a Flow of Skills

How I bundled slot development work into agent skills, and why I cut the number of skills back after building many.

I wanted to automate my team’s slot development work as a flow of skills. Colleagues had already started a plugin repository for the team, and in May 2026 I added a slot development workflow plugin to it. The goal is in the first line of its README: start new slots and bonus features from the same baseline.

The flow

New slot production now runs in this order:

  1. Turn the design document into a structured spec, and settle unclear points through questions.
  2. Write the server logic and math values fresh from the design document.
  3. Check the math with simulation.
  4. Clone a base game’s client module, remove features the design doesn’t need, and import the ones it lacks.
  5. Align the server response with the client’s data structures.
  6. Build state graphs and presentation controllers, with placeholders where art will go.
  7. Each time art arrives, integrate only what changed.
  8. Verify through actual play.
  9. Leave reference documents behind.

Why split it up

At first I bundled the project’s existing skills more or less as they were. I split them for three reasons.

  • To keep concerns apart: the production skill defines only the order and the pass conditions. Each stage’s skill owns the method, and copying content between them is not allowed.
  • To keep context clear: each stage runs in a subagent that reads only that stage’s skills. This keeps the documents and the actual work from falling out of step.
  • To avoid a vague “done”: reports must separate server, data schema, client flow, prefabs, runtime validation, and handoff.

What didn’t work

In August I collected my own feedback and looked back on it. Rather than treating every follow-up fix as an agent mistake, I separated direct misunderstandings, spec changes, defects that only appeared at runtime, and incomplete evidence. Reports that presented static checks or passing builds as a finished product were part of what I looked at.

The number of skills was a problem too. In October, when I gathered the entry point into a single production pipeline skill, merging and removing skills cut the number by about half. Now a table sets which skills and documents each stage reads.

I also revisited pass records. Now only the actual execution log of a command the tool ran counts as a pass, and a hand-written pass mark does not.

At this stage I couldn’t answer whether skills actually improve results. That question led to the benchmark.
