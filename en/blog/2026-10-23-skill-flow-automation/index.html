Trying to Automate My Team's Work as a Flow of Skills

How I bundled slot development work into agent skills, and why I cut the number of skills back after building many.

The problem

I wanted to automate my team’s slot development work as a flow of skills. Colleagues had already started a plugin repository, and in May 2026 I added a slot development workflow plugin. The aim, as its README’s first line says, was to start new slot and bonus development from the same baseline. It began with moving feedback into rules.

Background and framing

When looking at skill structure I separate three things: documents that set order, documents that describe method, and execution that decides passing. At first all three were mixed in one document. Most of the change in this post is pulling them apart.

Order

The production pipeline skill sets stages and pass conditions.

Method

Each stage skill explains how to do the work.

Judgment

Only logs of commands the tool ran count as passing.

Evidence

These are changes left in my team conversations and work records.

  • 2026.05 Added the slot development workflow plugin, wrote a retrospective
  • 2026.06 Shared the install guide with the team
  • 2026.07 Learned long instructions get cut or compressed on a new model, so I slimmed skills and instructions
  • 2026.08 Reviewed follow-up fixes in four categories
  • 2026.09 Moved the Unity CLI from a skill to top-level instructions
  • 2026.10 Unified entry points, reduced skills to about half

After moving the tool’s location in September, I wrote this to the team.

Putting it in top-level instructions instead of a skill connects pretty smoothly??

The same month had a decision in the other direction. Per-test-case debug automation kept trying to build impossible situations, so I removed it from the automatic stage and left it only as a skill called on request.

Nature of the content Where it went
Tool usage always needed Top-level instructions
Method needed only for certain work Stage skill
Automation that often fails Skill called on request
Judgment that must hold Execution log check

Attempts

New slot production now runs in this order.

Design doc to spec, unclear points to questionsWrite server logic and mathSimulationClone module and import featuresAlign response and client structureState graphs and presentationMount only art changesReal play verificationDocs handoff

At first I bundled project skills nearly as they were. I split them for three reasons.

Reason Method
So they don’t mix The production skill sets only order and pass criteria, and stage skills own method. Duplicating content is forbidden.
So context doesn’t blur Each stage uses a subagent that reads only that stage’s skill.
So completion isn’t lumped together Server, Data Schema, client flow, prefab, runtime verification, and handoff are reported separately.

Where my judgment changed

A development retrospective from May 2026 concluded that slot work doesn’t end by fixing one layer. Changing a server value carries through schema, client data paths, presentation, simulation, and work logs. That’s why I split skills by layer.

In August I gathered my feedback for another retrospective. Instead of calling all follow-up fixes agent mistakes, I split them four ways.

Category Meaning
Direct misunderstanding The agent misread a requirement
Spec change The requirement changed mid-build
Defect first appearing at runtime A problem static checks couldn’t see
Incomplete evidence Reported as done without finishing the check

I also looked at cases reporting static checks or build passes as product completion.

The number of skills was a problem too. The more I made, the more entry points appeared. In October I gathered entry into one production pipeline skill and merged or removed skills to about half. A table now sets which skills and docs each stage reads.

Before

Many skills and several starting points. Pass marks could be handwritten.

After

One entry point. Only actual execution logs of commands run by the tool count as passing.

I used a subagent per stage because of context. Making a long session read every rule blurs or compresses what it read earlier. If each stage reads only the documents it needs and passes on only results and evidence, scope gets small. In exchange, what passes between stages must be defined, and anything lost at the boundary is unknown to the next stage. Response structure alignment became its own stage because this problem came up most often at the server and client boundary.

Read stage skillDo the workLeave execution logsPass only results onward

Not accepting hand-written pass marks is part of this structure. Agents can write progress files, so only records of what the tool itself ran were used for judgment.

I should also note where the current flow fits. Stages fit new slots and bonuses that follow existing game structures. For new presentation structures or other genres with few existing references, the stage order can get in the way. And when a skill document mentions a specific game as an example, later work can be pulled toward that example. After finding this contamination in the benchmark, I’ve been replacing such examples with general patterns. Examples help understanding but can read like answers. As documents grow, I think a tool should do this check too. I also haven’t fully traced what disappeared along with the rules I cut. Whether old problems return after halving needs watching in the benchmark and real production.

Reflection

There’s no evidence that halving skills improved results. The facts stop at a single entry point and less duplicated content. Anthropic’s agent post recommends adding complexity only when results improve. I added complexity first, then removed it without knowing whether it had helped. That’s hard to call a good order.

The rule of reporting separately has costs too. Writing up several layers per slot adds reading burden. I judged it still better than one word for done, but that’s my interpretation. I didn’t separately ask the colleagues receiving it how they felt.

The whole flow hasn’t reached fully automatic running either. In October it was still under practical testing, and a person looked at each stage’s results. That’s why the title says attempt.

The four categories in the retrospective helped divide responsibility, but their edges are blurry. Whether a requirement changed or was misread from the start takes a person’s rereading. I also classified them myself, so I risk shrinking my own share. That’s why I used them as questions and produced no statistics. The retrospective’s purpose was fixing the next procedure, not scoring agents.

This flow is also fitted to my team’s slot production. There’s no evidence another team would get the same result by taking the stages as they are.

General lessons

Making more skills wasn’t progress in automation. Separating documents that own order from those that own method actually let me reduce them. Writing procedures also exposed my own standards, since feedback I repeated in slot work became the rules.

When moving repeated work into skills, I first ask about the nature of the content: always needed, sometimes needed, or must be enforced by execution? Skill count can’t measure progress.

Next steps

At this stage I couldn’t answer whether skills really improve results. That question led to the benchmark, and checks at the runtime layer are in Runtime Lab.

This led to comparing instruction and skill differences as benchmark conditions. The small experiment has no conclusion yet.
