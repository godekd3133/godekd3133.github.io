Into Daily Work: Starting to Use Skills, Subagents, and MCP

Between March and June 2026, AI tools moved into my actual work flow.

(Written in 2026, looking back.)

After the period of testing tools, in spring 2026 I began putting AI into actual work. My April 2026 prompt counts were 719 in Codex and 503 in Claude, well above January’s 66 and 147.

The problem

In February 2026 I developed a super bonus for an existing slot with AI and wrote the team a report on how it went, from design analysis through server, client, and review. In March I had a server development conversation kept verbatim to record my intent and feedback, asking that prompts not be compressed or summarized because capturing my intent mattered.

Background and framing

I read this period’s change by where feedback lives. In a conversation, it vanishes when the session ends. In a file, the next session reads it. In a plugin, the team uses it together.

Conversation

It stays for this session only.

Rules and skills

The next session starts from the same standard.

Plugin

The same standard is installed in colleagues' environments.

Evidence

The Codex session list grew quickly in this period. Subagent sessions may be mixed in, so it shouldn’t be read as sessions started by a person.

March: 75
April: 79

The install guide I shared with the team in June set these standards.

Standard Details
No overwriting Add only the managed section and shared documents, not the whole rule file
Check for drift Read the content and use the overwrite option only when drift exists
Separate reporting Report server response, schema, state graph, prefab, and runtime separately

A document-making skill guide from the same month said values aren’t adjusted arbitrarily and are calculated from the source.

Prompt counts also matter. Comparing January and April 2026, Codex went from 66 to 719 and Claude from 147 to 503. January had a high share of slash commands, so this isn’t a clean comparison of conversation volume.

The patterns in the February report were connecting sessions with game references and context files, running independent work in parallel, and feeding review findings straight into fixes. I corrected wrong directions three times, and my lesson was to correct immediately when AI proceeds on a wrong assumption.

Where my judgment changed

In March, the structure of a values file differed from the team’s existing code. I wrote that this mistake must not be repeated, and fed back that efficient code is good but following the coding style we already use matters a lot too.

Simulation had a similar story. Overall numbers looked near the target but detailed distributions differed, and I found implementation defects by adding detailed metrics to compare. That’s when I set the principle of suspecting the logic before changing values.

I moved this feedback into rules and skills instead of letting it disappear into conversations.

Before

Repeat the same feedback in every session.

After

Put feedback into a skill as a lessons table, and block execution if reference documents are missing.

In June I introduced this bundle to the team as a plugin. Setup adds only a managed section and shared documents rather than overwriting whole rule files, and audit shows document status as OK, MISSING, or DRIFT. Reference documents for slot work were included too.

The February report also recorded how decisions were made: AI offers options, I choose, and AI implements. Wrong terms get corrected immediately, and it asks before trying an alternative. In January I had it plan a presentation feature for a real slot, then asked colleagues to evaluate whether a human implementer would need anything more.

The feedback from this period falls into three kinds: telling team conventions like code style, telling the order of judgment as in simulation, and correcting misunderstandings such as terms. Each needed a different destination.

Feedback kind Example Where it went
Team convention Match value file structure to existing code Skill’s lessons table
Order of judgment Suspect logic before changing values Simulation procedure
Precondition Check reference documents Stop the run if missing

The simulation case shows this split well. The overall average was near the target and looked like a pass, but comparing detailed distributions revealed an implementation defect. Fixing values to match would have left the defect in place. So I wrote a procedure to check how a number came to be right, even when it was right.

The March request to keep conversations verbatim is also worth revisiting. Summaries read easily but erase my intent and mistakes. Verbatim records let me find how often the same feedback came up and lift sentences straight into rules. In exchange, records get long and sensitive content can stay in them, so I think they belong inside work documents and shouldn’t be published as they are. I also couldn’t know then whether the patterns in the super bonus report would work for other games. They came from one project, so they had to stay hypotheses even after becoming rules. The record that I corrected direction three times also means a person knew the structure, so it isn’t evidence that someone without that knowledge would get the same result.

Reflection

The facts stop at this: I moved feedback into rules and distributed them to the team. I didn’t measure how much of my colleagues’ time this saved.

The official docs make a similar split. Claude Code’s best practices say “If something has to happen every time, make it a hook.” Instructions are only instructions and can be set aside. Stopping a run when reference documents are missing is closer to that side.

There is a counterargument too. Rules get heavier as they accumulate, and a judgment that’s right now keeps applying after it turns wrong. A few months later I actually cut skills by about half. It’s my interpretation that this accumulation also created that burden.

The dates when I adopted MCP and subagents are only first uses on record. First use differs from settling into work, and it would be an exaggeration to read the table as mastering every feature at that time. This table also can’t show how much of the team followed along. Posting an install guide and colleagues using it are different things.

The numbers and dates in this post show changes in tool use, not the quality of the work.

General lessons

Use began shifting from a tool you ask questions to one you hand set procedures and connect to outside tools. My own work moved from writing prompts toward leaving feedback as procedures.

The second time I say the same thing is when it should move into a file. But each rule also needs a thought about when to delete it. What must always hold should be enforced by execution, and only what needs judgment should stay as text.
