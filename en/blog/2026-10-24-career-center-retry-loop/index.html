Career Center: Making You Answer the Same Question Again

The rule for picking one question to answer again from mock interview results, and the code that builds the reason sentence only from measured values.

The problem

Career Center is a job preparation app connecting job selection through interview review. Comparison reports existed from the MVP, but reports are easy to read and leave. The core loop in the roadmap is mock interview, report, weak-spot map update, and re-asking based on weak spots. So on October 24, 2026 I made retrying the first button on the results, today, and practice screens. Related rules are in packages/core/src/retry.ts.

Background and framing

I see the value of an interview practice app in three steps: knowing weak spots, trying again, and comparing whether things improved. The first report stayed at the first step. Like research on retrieval practice, I wanted to make answering again from memory, not reading, the app’s first action.

Where my judgment changed

If AI makes up why you should retry, it’s hard to trust. So the reason sentence is built from measurements. Below is the code with sentence parts shortened.

export function retryReason(a: AnswerRecord): string {
  const top = fillersCount(a) ? [...a.metrics.fillers].sort((x, y) => y.count - x.count)[0] : undefined;
  if (top && top.count >= 3) return /* "음"이 5번 나왔어요 */;
  if (!a.typed && a.metrics.timeStatus === 'over') return /* 제한 시간 초과 */;
  // 전달력, 내용, 적합도 점수 순으로 확인
  return '';
}

Quotes the AI picks are used only when found in the actual answer through quoteOf, with whitespace removed.

Now

Sentences come from measured values, and if nothing can be measured it returns an empty string.

speech.ts calculates speech metrics without AI. Browser dictation sometimes removes fillers like “um,” so habits and repeats are counted only for verbatim transcripts. Otherwise wordsMeasured is false and they stay out of the score.

Putting re-answering on the first button shrinks room for other features. I put this loop up front because I thought carrying one practice through to the end beat showing one more feature.

Report-centered

It tells a lot, but the user decides the next action.

Re-answer-centered

It gives one question and one reason and has you speak right away. Other weak spots get pushed back.

Re-answering happens inside the original interview result, so it lines up beside the first attempt. Comparing quotes with the original answer, even with spaces removed, comes from the same thought. If AI shows words not in an answer as the user’s, even a small mistake loses trust. The virtual interview’s opinion on wrong evaluations points the same way but, as noted, is weak evidence.

I’m also writing down in advance what validation would look at. First, whether users press re-answer. Second, whether measured values change after re-answering. Third, whether they return before real interviews. The first and third are behavior and relatively reliable, but the second can’t easily separate familiarity. A claim of improved skill can’t rest on these metrics alone. Asking about actual interview results could help, but samples are hard to gather and many other factors affect passing. So the first goal isn’t proving skill but checking whether the reason is convincing enough for users to answer again.

Reflection

The 80 threshold and 3-day window have no research or experimental basis. I set them while building the product. That re-answering leads to better interviews is also only an expectation today. Retrieval practice research mainly deals with memory of learned content, so it shouldn’t be moved directly to spoken interviews.

Part of picking weak spots still depends on AI evaluation. Reason sentences come from measured values, but AI scores decide which answer is weak. That’s why I added a button for saying the evaluation is wrong. The principle of speaking only about what can be measured has a boundary.

Similar responses among AI personas are risky too. Several saying the same thing doesn’t add evidence. One model may have said a similar thought several times. I think these interviews helped form questions, but that’s my interpretation.

Repeating questions isn’t always good. Scores may rise only from familiarity with the question. That’s also why answers from different days can be compared with the first try, but I don’t know if it’s enough.

Sometimes filler counting is off. Without a verbatim transcript it isn’t scored, so users get less feedback. Depending on browser environment, the same user gets a different range of feedback. Explaining this so users understand remains an open problem.

General lessons

The task plan added that same day uses the same principle. The change log says it’s built by rules without AI so no invented numbers get in. As with answering unknown in PC Supporter, not counting what can’t be measured has become a standard I repeat across products.

In virtual customer interviews, responses repeatedly said the score would rise with sharper questions. But these are opinions of personas played by AI, so I treat them only as assumptions.

Tie explanations AI writes to measured values. Without a value, don’t produce the sentence. Also give users a way to correct an evaluation. Keeping the boundary between measurement and generation visible in code also makes it easier to fix later.

Next steps

I still don’t know whether this loop actually improves interview skill. Questions were checked with AI virtual personas, and real user validation hasn’t happened. On October 31 I refined the direction toward a job manager connecting cover letter sentences through interviews, and real interviews come next.

In real interviews I’ll first ask whether people pressed re-answer and whether they came back when an interview was scheduled. Until then 80 and 3 days stay temporary values.
