The PC Supporter Rule Engine: Saying "I Don't Know" When It Doesn't

How the compatibility rule engine puts its reasoning and missing information into its results, explained with the actual code and verification results.

PC Supporter checks PC build compatibility using the Danawa parts catalog. A bare yes or no is hard to trust when buying, so every verdict carries its grounds. The first principle in the development docs says compatibility verdicts, data reliability, price, and real assembly verification are not collapsed into one state. The engine is in shared/domain/engine.ts.

What I tried

Rules leave results as findings: rule ID, severity, affected parts, verdict facts, and an action the user can take. Severity is blocker, warning, info, or unknown. addUnknown, used when information is missing, records the missing field as a verdict fact and attaches an action to check the spec.

A fully compatible verdict requires no unknowns either.

function isFullyCompatible(blockerCount: number, warningCount: number, unknownCount: number) {
  return blockerCount === 0 && warningCount === 0 && unknownCount === 0;
}

Without physical values or manufacturer evidence, nothing is promoted to an automatic pass. It’s the same judgment as not filling unknown values with 0 in the KBO Fans widget.

Where I got stuck and how my judgment changed

To check whether the engine could be trusted, on October 2 I ran 300 random part sets from the deployed catalog. Execution errors, consistency violations, and disagreements with independent judgment were all zero. But problems appeared elsewhere, like NVMe SSDs wrongly blocked as unfit. The document’s conclusion: the remaining problems are in the parser and data.

An engine that honestly reports unknown produces many unknowns when data is empty. So I chose to fill the data rather than loosen the rules.

Mounting conditions joined the verdicts too. In verification, a 27mm radiator in an H6 Flow came out unknown because the rear I/O install condition wasn’t confirmed, and 31mm came out blocker for exceeding the manufacturer’s 30mm limit.

What I learned

The rule engine’s accuracy and the quality of the answer a user gets were different problems. Even with an all-correct engine, empty input can only produce “needs checking.” So when a problem appears I first separate engine, parser, and data. It has the same structure as separating server, display, and build in my slot work.

What’s next

Empty cases remain in the table above, and this hasn’t reached the production database. The motherboard power rule rested on weak estimated coefficients, so two days later I changed how it judged.
