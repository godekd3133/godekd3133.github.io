The PC Supporter Rule Engine: Saying "I Don't Know" When It Doesn't

How the compatibility rule engine puts its reasoning and missing information into its results, explained with the actual code and verification results.

The problem

PC Supporter checks PC build compatibility using the Danawa parts catalog. A bare yes or no is hard to trust when buying, so every verdict carries its grounds. The first principle in the development docs says compatibility verdicts, data reliability, price, and real assembly verification are not collapsed into one state. The engine is in shared/domain/engine.ts.

Background and framing

The rule engine has four answers: compatible, warning, cannot fit, and needs checking. As in many-valued logic, not knowing is a value of its own between true and false. This also lets quality problems be viewed in three places.

Engine

Is judgment right when input is right? Checked with random samples and independent judgment.

Parser

Were values read correctly from product text? Checked with unit tests and cases.

Data

Do needed values exist? Checked by fill rate.

Evidence

The October 2 test sampled from 1,828 parts selectable in the picker, in a catalog of 7,380. I fixed the random seed so the same part sets could be drawn again, and judged 7 core rules separately from source specs to compare. The 233 engine and parser unit tests also passed.

But the 100 fit builds, drawn to match conditions, looked poor from a user’s view.

The rise in cannot fit isn’t a worse value. Of the 35 in round 2, 25 chose laptop memory for a desktop board, and were correctly blocked after the fix.

Attempts

Rules leave results as findings: rule ID, severity, affected parts, verdict facts, and an action the user can take. Severity is blocker, warning, info, or unknown. addUnknown, used when information is missing, records the missing field as a verdict fact and attaches an action to check the spec.

A fully compatible verdict requires no unknowns either.

function isFullyCompatible(blockerCount: number, warningCount: number, unknownCount: number) {
  return blockerCount === 0 && warningCount === 0 && unknownCount === 0;
}

Without physical values or manufacturer evidence, nothing is promoted to an automatic pass. It’s the same judgment as not filling unknown values with 0 in the KBO Fans widget.

Where my judgment changed

To check whether the engine could be trusted, on October 2 I ran 300 random part sets from the deployed catalog. Execution errors, consistency violations, and disagreements with independent judgment were all zero. But problems appeared elsewhere, like NVMe SSDs wrongly blocked as unfit. The document’s conclusion: the remaining problems are in the parser and data.

An engine that honestly reports unknown produces many unknowns when data is empty. So I chose to fill the data rather than loosen the rules.

Mounting conditions joined the verdicts too. In verification, a 27mm radiator in an H6 Flow came out unknown because the rear I/O install condition wasn’t confirmed, and 31mm came out blocker for exceeding the manufacturer’s 30mm limit.

Splitting sampling into three methods also mattered. random draws any parts to see that the engine doesn’t break. plausible draws believable combinations, and fit also matches specs.

Method (100 each, round 2) Cannot fit Needs checking Compatible
random 96 4 0
plausible 51 40 9
fit 35 56 9

Looking only at random, the engine would have seemed to block well. A sample closer to user builds revealed how often it couldn’t answer. In a VRM rule experiment, needs-checking fell from 298 to 30, but warnings appeared even on entry-level builds. Lowering a ratio alone didn’t make answers good.

The engine and data run on different schedules too. Engine rules can be fixed quickly with code and tests, but checking manufacturer sources takes time per item. Even with AI helping enrichment, skipping source checks lets unfounded values into judgments. So I organized case specs along with evidence documents from manufacturer sources.

Reflection

Zero errors should be read carefully. If I built the independent judgment with a similar understanding, it can share the same mistake. It isn’t real assembly either. So the documents separate engine judgment from real assembly checks.

The cost of unknown is also large. If over half of matched builds come back as needs checking, the answer is honest but not useful enough. Users end up looking it up themselves. Martin Fowler warns that rule engines can get hard to reason about because of rule interactions. In my case data blocked me before rules did, but this risk grows with more rules.

I didn’t loosen rules anyway because PC part purchases are a hassle to undo. I judged one wrong compatible verdict to cost more than several needs-checking results. But I’ve never studied which real users find worse, so it’s my interpretation. The random sample also differs from real users’ build distribution.

The case spec table covers only 56 cases too. It doesn’t mean motherboards or power supplies are filled to the same level. Enrichment was based on manufacturer sources but isn’t yet in operating data, so what users get today may differ from the table’s enriched values.

These values are as of early October 2026.

General lessons

The rule engine’s accuracy and the quality of the answer a user gets were different problems. Even with an all-correct engine, empty input can only produce “needs checking.” So when a problem appears I first separate engine, parser, and data. It has the same structure as separating server, display, and build in my slot work.

A judgment system should treat not knowing as a formal result. Quality metrics should separate accuracy from the rate at which it can answer. Even if engine checks pass, empty input is the same as no answer for users.

Next steps

Empty cases remain in the table above, and this hasn’t reached the production database. The motherboard power rule rested on weak estimated coefficients, so two days later I changed how it judged.

After applying enrichment to operating data, I want to rerun with the same seed to see whether needs-checking really falls. The same test should also run on real build samples.
