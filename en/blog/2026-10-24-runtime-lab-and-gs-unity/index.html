Runtime Lab and GS Unity: Verification After the Build Passes

How the verification stage of the workflow uses a runtime replay tool I built and a Unity control tool a colleague built.

The last layer of the skill flow is runtime verification, because passing code and data checks doesn’t tell you whether presentation plays correctly on screen. I use two tools to close this gap. One I built, and a colleague built the other.

Tool Built by My part
Runtime Lab Me Design, implementation, later fixes
GS Unity A colleague Use, raising practical-use discussion, a small fix

The problem

Reproducing a particular spin result or complex situation in Unity meant playing until the condition came up. If agents couldn’t run the same scenario, verification couldn’t be delegated.

Background and framing

Seen as layers, verification costs more and covers more as it goes up. Martin Fowler’s test pyramid post makes a similar split. In my case I also had to write down the scope of the evidence.

Static checksFixed-input regressionEditor replayBuild playReal environment

Evidence

The test automation design I wrote in September separates AI judgment from machine judgment. It’s a design document, and new commands and sessions weren’t implemented at that time. It proposed this result format.

verdict: PASSED / FAILED / BLOCKED / NOT_RUN
validity: CURRENT / STALE / UNVERIFIED
cleanup: COMPLETED / REQUIRED / NOT_REQUIRED
evidence: source / generated / Unity / wallet, each

I avoided a single success: true because an old success record or generated file shouldn’t count as verifying the latest code. Other rules from the same document follow.

Rule Reason
Separate current wiring from expected behavior If a wrong structure is read to create answers, tests go wrong with it
Attach observers before the first action Don’t miss behavior that ends within a frame
Compare with the observer on and off Confirm that observing doesn’t change game state
Don’t auto-edit expected values to match results Prevents wrong results from becoming answers

Cautions found in that design also generalize. Running child graphs are clones of the original, so subscribing only to the original can miss real runs. Behavior that starts and ends in one frame can be missed by later polling. Some code that reads an ID for observation changes the object, so I decided to check that results match with and without observing.

Runtime Lab: what I built

I began on July 31, 2026, and added an agent command-line client and a runtime bug reproduction skill the same day.

Replay recorded server responsesJudge game state with rulesCapture set sections frame by frame

I set boundaries too. Playback runs only when a scenario is explicitly enabled; otherwise the normal path applies. Replay results are development-environment evidence only and don’t replace real server, payment, or device verification. Since Unity handles one job at a time, it first checks whether another job holds it before changing state.

GS Unity: what I use and slightly fixed

GS Unity is a Rust CLI for agents to control the Unity 2022.3 Editor, built by a colleague. My start was raising with the team whether the existing bridge was really practical, and the colleague led development.

  • I wrote the play verification skill’s entry, spin, and state check procedures around this CLI.
  • I connected it to the runtime paths of GS App and the benchmark.
  • During cloning, importing fonts marked unsaveable sub-assets as modified and the operation was rejected. I excluded only this item from the check, while other changes stay rejected. I found this while building the benchmark start state.

Where my judgment changed

While tuning the verification pipeline in September 2026, I told the team channel that verifying with a local Mac build play rather than Editor play felt more natural.

A plan that same month divided roles: code and fixed test data decide what runs and what passes, while AI handles interpreting intent, test drafts, and failure analysis.

AI handles

Interpreting intent, exploring code, test drafts, fixes and failure analysis.

Code and data decide

What runs and what conditions pass.

Play verification now operates the Editor with GS Unity and reproduces situations with Runtime Lab. On the benchmark runtime path I confirmed real entry, spins, and video. In late October I found and fixed a hold marker left behind after a capture ended normally, which blocked other jobs.

Runtime Lab’s position kept changing afterward. At one point I decided to retire it, then on November 2, 2026 I told the team I would bring it back. The reason was seeing agents actively use it for debugging during benchmark and production skill trials.

Original scope

One tool handles replay, judging, and section capture.

November plan

Keep only video capture, on-the-spot debug spins, and the E2E test route, with capture absorbed into GS Unity.

I should also note why I state tool ownership. If a résumé or post speaks of every tool as mine, readers misjudge what I can do. So the table separates who built it from my share. This isn’t only for writing. It also decides who to consult when something breaks and where to send a fix.

Reflection

I don’t see dropping a tool and reviving it as failure. But the fact that the retirement decision was wrong should stay on record. I saw agents debugging with this tool only after deciding to retire it. That a tool inconvenient for people can suit agents is my interpretation, and the cases are still few.

Building procedures on a colleague’s tool has limits too. Changes to that tool affect my procedures, and my contribution stops at small fixes. So I don’t call GS Unity itself my achievement.

Video sharing wasn’t measured either. My November note says video would be faster than checking work directly every turn, but no timing comparison exists. Video can be watched quickly, but a person must still judge whether the desired situation was captured. Anthropic’s post also notes that automation misses screen elements it can’t see.

The September note that a local Mac build felt more natural is also an observation. I didn’t measure which differences from the Editor it reduced. Running builds takes longer than the Editor, so applying them to every fix raises round-trip cost. Where to stop should depend on risk, and I haven’t fully written that standard down yet.

General lessons

Dividing what to build from what to use from a colleague let me focus on verification procedures above Editor control. Even reproduction evidence needed a stated range: correct in a development environment and correct in the real environment are different claims.

Automated results should state what was checked, on which version, and in which environment, not only pass or fail. Whether the observing tool changes results is itself a test subject. And a tool’s value needs another look when the user changes.

Next steps

Whether to keep Runtime Lab was discussed again in the team in October 2026. Measuring whether changing procedures improves results moves on to the benchmark.

What remains is applying the designed result format and session lifecycle to one real game. I also need to check whether Unity Test Framework’s command-line runs and result files can serve as a base.
