Runtime Lab and GS Unity: Verification After the Build Passes

How the verification stage of the workflow uses a runtime replay tool I built and a Unity control tool a colleague built.

The last layer of the skill flow is runtime verification, because passing code and data checks doesn’t tell you whether presentation plays correctly on screen. I use two tools to close this gap. One I built, and a colleague built the other.

Tool Built by My part
Runtime Lab Me Design, implementation, later fixes
GS Unity A colleague Use, raising practical-use discussion, a small fix

Why I started

Reproducing a particular spin result or complex situation in Unity meant playing until the condition came up. If agents couldn’t run the same scenario, verification couldn’t be delegated.

Runtime Lab: what I built

I began on July 31, 2026, and added an agent command-line client and a runtime bug reproduction skill the same day.

Replay recorded server responsesJudge game state with rulesCapture set sections frame by frame

I set boundaries too. Playback runs only when a scenario is explicitly enabled; otherwise the normal path applies. Replay results are development-environment evidence only and don’t replace real server, payment, or device verification. Since Unity handles one job at a time, it first checks whether another job holds it before changing state.

GS Unity: what I use and slightly fixed

GS Unity is a Rust CLI for agents to control the Unity 2022.3 Editor, built by a colleague. My start was raising with the team whether the existing bridge was really practical, and the colleague led development.

  • I wrote the play verification skill’s entry, spin, and state check procedures around this CLI.
  • I connected it to the runtime paths of GS App and the benchmark.
  • During cloning, importing fonts marked unsaveable sub-assets as modified and the operation was rejected. I excluded only this item from the check, while other changes stay rejected. I found this while building the benchmark start state.

Where my judgment shifted

While tuning the verification pipeline in September 2026, I told the team channel that verifying with a local Mac build play rather than Editor play felt more natural.

A plan that same month divided roles: code and fixed test data decide what runs and what passes, while AI handles interpreting intent, test drafts, and failure analysis.

AI handles

Interpreting intent, exploring code, test drafts, fixes and failure analysis.

Code and data decide

What runs and what conditions pass.

Play verification now operates the Editor with GS Unity and reproduces situations with Runtime Lab. On the benchmark runtime path I confirmed real entry, spins, and video. In late October I found and fixed a hold marker left behind after a capture ended normally, which blocked other jobs.

What I learned

Dividing what to build from what to use from a colleague let me focus on verification procedures above Editor control. Even reproduction evidence needed a stated range: correct in a development environment and correct in the real environment are different claims.

What’s next

Whether to keep Runtime Lab was discussed again in the team in October 2026. Measuring whether changing procedures improves results moves on to the benchmark.
