Verification and Running in Parallel: Making Run Results the Completion Condition

Verification kept getting skipped, so I made run results the completion condition, and built personal products using two tools together.

From around July 2026, delegating work broadly to AI made missed verification common. This post covers how I dealt with that and how the same approach spread to personal products.

The problem

There were individual judgments, like not marking device push as done on KBO Fans’ first TestFlight. But with many sessions running, things slipped when a person checked them one by one. So I changed the completion condition itself to execution results.

Background and framing

“Done” mixed three different statements: the agent said it finished, a command passed, and the result suits the user. Each is harder to check than the one before. This post records separating the first two, and the third is still in progress.

Where my judgment changed

Before

The agent reports done. A build pass reads as completion.

After

Done requires execution results, with how far each layer was checked written separately.

Some areas more verification commands couldn’t solve. Reactor Rush passed checks but couldn’t be called fun, and the Rune Breaker review had zero errors only in a headless environment. So in products I write separately what automated checks confirmed and what a person must confirm.

Judge completion by execution resultsReport execution range separatelySeparate automated and human checksCheck the tools too

I also changed how checks run. In September I moved slot verification from Editor play to running a local Mac build, and in personal products I delegated on-screen checks through browsers and simulators to tools.

Test commands rose from 3,879 to 21,981 in September, a value I think repeat automation influenced heavily. So this post favors session share over call counts. Checking methods also differ by product type.

Product type What can be checked automatically What a person must check
Slots Server simulation, schema, replay scenarios Feel of presentation, real environment
Web and apps Tests, browser, simulator screens Ease of use, reason to use
Games Headless simulation, error counts Fun
Data judgment Comparison with independent judgment Actual purchase and assembly

My completion report today takes roughly this form: what changed, which commands ran, what happened, and what wasn’t run. The last column matters most. Writing what wasn’t run shows immediately where a person should look.

Column Example
Change Fixed server values and client data paths
Run Type check, simulation, replay scenario
Result Pass or the point of failure
Not run Real device, real server, human play

This format doesn’t eliminate wrong reports. Execution records and content can diverge, so re-judging the final state, as the benchmark does, is also needed. Using the same format for slots and personal products changes the layer names. Slots split into server, schema, client, and runtime. Apps split into tests, screens, real devices, and users. The form is the same but the checking cost differs widely, so which columns stay empty depends on risk.

Reflection

Reading only the improved numbers misleads. Even in October, 48% of Codex edit sessions and 57% of Claude’s had no test or build record after the last edit. Sessions checked on screen are mixed in, which may make this look worse than it is, but it’s hard to call it enough.

The verification command share also dropped as I moved to Claude. Turns where I mentioned verification differ too: 14.1 per 100 turns on Codex, 3.4 on Claude. It may be a shift to UI checks as personal product work grew, but that’s my interpretation, and I couldn’t measure it separately.

Rework turns didn’t fall. So I can’t say results improved because verification commands rose. If running test commands becomes the goal, then as Goodhart’s law says, the value can rise while its meaning shrinks.

Anthropic’s best practices separate deterministic means for judging done, such as tests, type checks, Stop hooks, and CI. I’ve applied these in only some projects, not everywhere.

Growing the left column of the table above leaves the right column as it was. I spent more time growing the left, because its results are visible and tools can solve it. I think deferring the right is the biggest gap in my products today. That’s also my interpretation, but it fits the fact that most real user validation remains.

These numbers are also one person’s records. Edit sessions count the same regardless of size, so a small wording fix and a large feature carry equal weight.

General lessons

This was when I built products like PC Supporter, Career Center, and Rune Breaker. Using the same approach on products I handle from planning to deployment carried standards set at work into honest labels in the product: answering unknown when unsure, and not counting what can’t be measured.

A completion report states the commands run and their scope. Metrics are for direction only, alongside the checks measurement misses. And a check needed every time is better moved from human habit to a tool’s block.

Next steps
