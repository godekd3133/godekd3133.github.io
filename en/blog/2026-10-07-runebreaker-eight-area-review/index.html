Worklog: Rune Breaker Eight-Area Review

A record of reviewing eight areas first without touching code, collecting about 170 findings, and applying them starting with the highest-priority groups.

Rune Breaker is a 3D top-down hack-and-slash roguelite that runs in the browser. On this day I reviewed features overall and fixed priority bundles first. It’s solo development using AI agents.

Context of the day

Features had been growing quickly, so I needed to know the current state before adding more. Finding problems while fixing them mixes findings with changes, so I separated review from fixes. The latter part of that reasoning is my interpretation.

What I did

I reviewed eight areas in parallel: combat (player), combat (enemies and world), progression, BM and lobby, modes, progress and story, a full wording pass, real screens, and unused resources. The review stage only read code, and every finding carried a file and line number. For real screens I captured 162 mobile and desktop images with headless Chromium. Findings came to about 200, or about 170 after merging duplicates.

Gear probability disclosure differed from actual slots and sets Fixed the wording
On mobile, aim fixed at 7m or guidance mentioning “R key” Fixed for mobile

I also deleted about 530 lines of overwritten old weapon and ultimate code and 285 unused CSS rules.

Where I got stuck

  • A cleanup committed in an intermediate state removed live style rules, which I restored separately.
  • Wording cleanup and code deletion ran at once and created overlapping blocks. I held off deleting some old ultimate code mixed with other work’s changes.

Judgment

I didn’t delete all unused content. Six shared spells came back as single-use rune scrolls. Items needing a direction, like duplication among ten modes, went into a separate restructuring bundle, and I ran only the four I chose. I had the agents do the finding, and chose the direction myself.

How the eight areas were divided

Area Scope as I summarize it
Combat (player) Weapons, ultimates, controls
Combat (enemies, world) Patterns, boss phases, effects
Progression Gear, stats, currency flow
Monetization, lobby Odds disclosure, shop, lobby guidance
Modes, progress, story Mode overlap, progress conditions
Full text pass Guidance text, match with real values
Real screens Mobile and desktop captures
Unused resources Code, CSS, sound effects

This split revealed where one area’s findings clashed with another’s. Keeping the six shared spells, when “delete unused code” met the judgment to revive content, is an example. Dropping 25 of 46 sound effects from loading is similar. The rest lived on as UI accents, so the decision wasn’t deletion alone.

Including monetization and odds disclosure text in scope mattered because the text differed from actual gear slots and set counts. Wrong disclosure misleads players, so I matched the text to reality. The priorities I would state are: does it reach players, does the label match reality, and is it safe to delete. That ordering is my interpretation. Items code can’t settle, like the ten overlapping modes, were kept out of agents’ fixes. The zero errors recorded that day came from a headless integration run, and the installed app path remained separate.

In short, the day’s results were the findings list, fixes by batch, and a separate set of direction decisions. Not every finding’s outcome was verified, so the remainder needs checking in later batches.

I intend to keep this separation for the next batch.

Basis for judgment and results

The final bar’s 285 exceeds 200, so it is capped at 100%.

Requiring a file and line number on each finding made facts easy to check. Still, the number of findings is not a quality metric, and since agents did the review, wrong findings may be mixed in. The records have no full re-verification, so I can’t state accuracy. Deleting unused code also causes accidents when it overlaps with concurrent work. Restoring live styles that day is the example, and I plan to keep deletion separate from other changes.

What’s next

The final integration run had zero errors, but in a headless environment. I didn’t check the installed app (simulator and TestFlight) that day. Fun wasn’t verified by this review either, the same limit as what happened with Reactor Rush that same day.
