Worklog: Rescue Meal Usability Fixes

A record of the day I fixed the home, meal plan, and shopping flows at each moment of use.

Rescue Meal is an ingredient app that tells you which ingredients to use first. It upgrades class work, aimed at one- or two-person households who gave up on management apps because registering food was tedious. On this day I fixed friction by moment of use and tidied the TestFlight release flow. As in checking the launched GS App, I went by the order of use rather than the feature list.

Context of the day

The document I wrote that day opens with the service’s promise. It doesn’t make you manage all your food every day, and it helps with the decision you need today. So I looked at screens through a flow of four questions rather than by feature.

What do I have at home?What can I make?What else do I need to buy?How much did I use?

What I did

Moment of use What I fixed
First registration Name, quantity, and storage location only, no receipt
Home Tapping fridge, freezer, or pantry counts opens that list directly
Choosing meals Strict time limits. Before, picking 10 minutes could still show longer recipes
Recommendation score Registering one ingredient in parts pushed the match rate past 100%; now calculated per recipe ingredient
Purchase registration No saving before choosing storage, and decimals like 1000.5g save as entered

Where I got stuck

The stricter time condition broke shopping recalculation for previously saved meal plans. Allowing the saved actual cooking time when recalculating the same saved recipe resolved it. A separate review flagged inventory freshness and this compatibility issue; I fixed both and passed re-review.

New recommendations

The time limit is enforced strictly.

Recalculating saved plans

The recipe was already chosen, so the saved actual cooking time is allowed.

What I checked

Tests for recommendation, meal plan, shopping, and stock-in flows plus regression tests for the new screens confirmed this change. The purchase path was checked with real requests and the detail screen. Existing failures in broader API tests were separated for later.

Changes the earlier table left out

The document for the day lists more items beyond the earlier table.

Moment of use Previous burden Change
After choosing a menu Long scrolling to find save and cooking steps Moved under the ingredient summary. Saving doesn’t change quantity, only finishing cooking deducts
Adding to shopping Easy to miss what you have at home Shows records with the same normalized name by quantity and location
Another device changes during shopping Old stock shown as current Refresh also updates stock, hides the hint on failure
Trial mode Guest looks like a real account Trial label and reset notice

The last two connect directly to the promise of showing only correct information. When stock couldn’t load, I hid the hint instead of showing old values, and kept the input draft in progress. Screen records were kept separately before and after. All of this was confirmed on a separate local test API and database.

My basis for judgment was the one decision a user makes at that moment. For example, the storage location count on Home clears earlier search and filters and shows only that location, since a leftover filter makes the count and list look different. Saving and finishing cooking are also separate. You might not cook a saved menu, so quantity is deducted only on finishing. A counterargument is that this takes one more input. The audience gave up on management apps, so added steps could clash with the promise. This tension can’t be judged before trying it with real users.

In short, the day’s results were fixes by moment of use, passing related tests, and a tidier TestFlight release flow. Existing failures in the wider API tests are not recorded as solved.

I plan to review this judgment during the next real-device check.

Basis for judgment and results

The document sets a completion condition for each moment of use. For example, a 10-minute request must not return a 15-minute menu, and splitting the same total into entries must not inflate the score. Passing test counts are below. The bars treat 63 as 100%, and since the kinds differ, more does not mean better quality.

Not assuming similar names are the same product, and not merging units arbitrarily, was also decided that day. Merging is convenient, but users can hardly notice when it is wrong. I don’t know whether this is actually less tedious, because I have run no user tests. That assessment is my interpretation.

What’s next

Device camera and OCR accuracy, push delivery, production deployment, and real users’ return visits and food savings weren’t covered. The next day I fixed PC Supporter’s power delivery verdict.
