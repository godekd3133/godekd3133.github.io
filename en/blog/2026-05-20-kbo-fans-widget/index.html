The KBO Fans Widget: Not Hiding Stale Scores

How the Flutter app and the iOS widget exchange data, how update delays are shown, and the widget bugs I fixed, based on the code.

The problem

KBO Fans is a baseball app I built to follow my team’s games without opening the app. It began as a class planning document. On March 30, 2026 I added the Flutter app and iOS widget extension, choosing Flutter over the React Native I’d first planned. Serious development with stabilized data began on May 19, and deep links and delay labels followed on May 20.

Background and framing

I split the widget data problem into two questions: how often can it receive data, and does it say when received values are from? The platform limits the first. The second is mine to decide, so I put my effort there.

In a data refresh design from the same month, I stopped treating all requests alike and split data into four kinds.

Kind Example Policy
Live Today’s scoreboard, current at-bat Network first, short TTL, stale fallback allowed
Warm cache Today’s schedule, pre-game lineup Cache first, quiet refresh
Persisted snapshot Past games, standings Snapshot first, no crawling at request time
Bundled bootstrap Default standings and records App assets on failure

Evidence

The design doc’s refresh values are 8 seconds for today’s scoreboard and live game details, and 60 seconds for a live box score. Even with a server this fast, the widget doesn’t draw at that speed. The code only requests the next refresh with .after(nextRefresh).

Attempts

On the Flutter side, WidgetSyncService receives the scoreboard, picks the game to show, and writes values to App Group storage. On the Swift side, WidgetKit only reads and draws them. In the background, a Workmanager task runs the same sync.

Receive scoreboardPick game to showSave to App GroupWidgetKit reads and draws

On iOS one widget draws differently by size: small, medium, large, and three lock screen styles. Android registers a single-game widget and a today’s-games list widget separately.

Where my judgment changed

An app can’t decide when WidgetKit refreshes, only request it. For a baseball widget, this means an old score can look current. Since the app can’t guarantee refreshes, I decided to say when the score on the widget is from. Text changes after 2 minutes for live games and 15 minutes otherwise.

let ageMs = Int64(Date().timeIntervalSince1970 * 1000) - updatedAtEpoch
let thresholdMs: Int64 = statusKind == "live" ? 2 * 60 * 1000 : 15 * 60 * 1000
if ageMs > thresholdMs {
  return "업데이트 지연 \(updatedAt)"
}
return "업데이트 \(updatedAt)"

For the same reason, I didn’t replace unknown values with other values.

Filling in values

Without pitch data, balls, strikes, and outs would show 0. A game with an empty source score would show 0:0.

Now

Balls, strikes, and outs are hidden. An empty score shows as –.

Two widget bugs in the CHANGELOG relate to structure.

Symptom Fix
After a brief refresh failure, it wouldn’t refresh again with the same game info Record the comparison signature after widget and Live Activity sync finish
A not-yet-received state showed as a no-game day Separate the two states

The first can happen when a signature meant to skip identical content remembers a failure as if it had succeeded.

The long widget data path also caused errors. The meaning of a value moves four times: server scoreboard, app sync service, App Group storage, widget rendering.

What the app can know

When it received data, whether values are empty, whether sync finished.

What the app can't know

When the system will redraw the widget, when the user will look.

So the widget stores the update time and state kind along with values, and the delay notice is computed at draw time. Computing at save time would leave “just now” on screen later. Moving signature comparison after sync follows the same logic. If success is recorded before actual success, failed content isn’t retried.

Similar handling was needed for Live Activity and notifications. Fixing only the widget could leave alerts computing scores from the same empty values. That’s why many changelog items name the app, widget, and Live Activity together. It means display rules should be judged in one place, not per screen.

Reflection

The 2-minute and 15-minute thresholds didn’t come from user research. Two minutes may be long during a game, and seeing “delayed” often can make the app look broken. I don’t yet know whether these values are right.

The delay notice isn’t a root fix either. Users want the latest score, and the notice only says honestly that it wasn’t received. I chose it anyway because I thought showing a wrong score as if correct was worse. It points the same way as NN/g’s visibility-of-system-status heuristic, but I couldn’t measure whether this judgment builds trust. That’s my interpretation.

Hiding zeros wasn’t cheap. The app, widget, Live Activity, and alert calculations all had to keep the same meaning, and the changelog shows similar errors several times. I think enforcing unknown in the types would have stopped this earlier.

I didn’t make all these judgments in the first widget work. Problems like 0:0 came back through several paths and got fixed each time. This post tidies them into principles, but in reality I learned them in order from errors.

General lessons

Here is where I first wrote into code the idea of saying honestly on screen whether a value can be trusted. It’s the same judgment as answering unknown in the PC Supporter rule engine in October 2026. A later app spec also notes that a connection status screen doesn’t mean delivery from the server succeeded.

On screens that can’t guarantee refresh, show the time along with the value. Treat no value and 0 as different states all the way through. Splitting refresh policy by data reduces requests and still lets you say how old each value is.

Next steps

Before release, I want to check how real users read the delay notice, and adjust the thresholds using usage records.
