Worklog: Solo CEO Staging Deployment

The day I defined the scope of personal data requests and put the staging backend on a single GCP VM. External integrations are stubbed, and the service is unreleased.

Solo CEO is a grant and tax preparation back office for small business owners that began as a class business plan. On this day I put the staging backend on GCP. It isn’t a released service yet.

Context of the day

By the previous day I had fixed export scope and data isolation, and now I needed a server to try the pilot on. The API refuses to report ready in staging and production without real provider adapters. To pass that condition with no external accounts, I used a stand-in implementing each provider’s HTTP contract on one port.

Reject bad privacy scopesLock dependencies, audit the imageFull stack on one VMRole probe fails, then fix

What I did

I finished privacy work first: rejecting invalid request scopes, splitting exports by scope, locking API dependencies, and auditing runtime images in the build. Then I put all of staging on one Compute Engine VM.

Needed Used on staging
TLS and entry point Caddy
Queue ElasticMQ (SQS FIFO compatible)
File storage S3-compatible storage
Notifications, business lookup, malware check, payment verification Stand-in servers built with the standard library

Where I got stuck

The operational role check failed. The cause was the PostgreSQL init script. Inserting runtime search_path in %L string format stored all of pg_catalog, public as one schema name, leaving current_schemas(false) empty. I changed it to set a list of identifiers.

Judgment

  • I drew boundaries so stand-ins don’t look like real integrations. The malware stand-in only finds the EICAR marker, the business stand-in only calculates a number checksum, and receipt verification is always verified=false since there’s no real store.
  • I postponed real payment provider integration. With the payment backend off in production config, runtime payment attempts are rejected.
  • Pilot grant collection starts with one source, and the rest get evaluated after the pilot.
What stand-ins answer

Format, checksum, and markers.

What they don't

Real payment, real business status, or whether a file is really malicious.

The contracts the stand-in server covers

The stand-in server imitates each integration’s HTTP format on one port.

Path Imitates How it decides
/notify Notification gateway Checks auth
/nts/status Business status lookup Number checksum
/malware/scan Malware scan Detects the EICAR marker
/billing/verify Receipt verification Always rejects
/checkout Payment page and webhook Completes payment on a stub page

The checkout stand-in also sends a webhook so subscription code actually runs. No money moves.

Gathering the stand-ins in one file serves running the whole flow during a pilot with no external accounts. The issue is that stand-in responses can diverge from real providers. When real contracts arrive, the stand-in formats need checking first.

In short, the day’s result was staging up and the role probe passing, with real integrations and release out of scope. Starting posting collection with one source also keeps the pilot narrow.

Basis for judgment and results

This is the init script after fixing the role probe failure.

-- search_path must be an identifier list, not a string literal: the %L form
-- stores '"pg_catalog, public"' as ONE schema name, which empties
-- current_schemas(false) and trips the managed-role probe.
SELECT format(
  'ALTER ROLE %I IN DATABASE %I SET search_path = pg_catalog, public',
  :'runtime_user',
  current_database()
)

This error surfaced because I actually brought staging up and ran the role probe.

The risk with stand-ins is mistaking a staging pass for integration verification. So receipt verification always returns verified=false, and the API turns that into an error. A single VM also doesn’t verify the production structure. By the Twelve-Factor dev/prod parity principle the gap is large, and it was a trade I accepted to check the whole pilot flow cheaply. That assessment is my interpretation.

What’s next

Staging isn’t release. A real payment provider, store billing, legal review, and external API contracts remain. The scope stays the same too: collecting and exporting documents, not filing on someone’s behalf. These stand-in boundaries return as verdict boundaries in the rule engine in the next post.
