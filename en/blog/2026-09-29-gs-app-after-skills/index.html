GS App: Why I Built an App After the Skills

I designed a desktop app to make skills the entry point for team work, and within a week I had to rethink its screen structure.

GS App is a desktop app that connects game information, AI runs, issue collaboration, simulation, and verification records for slot development. I wrote its design document and started implementation on July 8, 2026. Design and implementation were mine.

Why an app

Even after dividing procedures into skills, something was still in the way. The design document targeted the whole team: server, client, math, and PMs. But skills are called from a terminal with a repository open, so people had to match which skill to use for which game and task each time. To make skills the team’s entry point, there had to be a starting place outside the terminal.

What I tried

Decision Reason
A skill launcher, not free chat Things get made only by following production skills. The task list comes from scanning the skill folder, so new skills appear in the app.
No shared backend To avoid running infrastructure, code, metadata, and issues stay in their existing systems. On mismatch the app warns rather than resolves.
Progress display It reads progress files left by skills and shows them as stages.

Where I got stuck and how my judgment changed

On July 14 I launched the packaged app and checked each screen. The conclusion was that features weren’t lacking. They had piled up screen by screen, so users reassembled their working context every time. Switching to the AI tab lost the selected game, and the simulation screen had no way out when there was no task to connect.

First week

Features were added as screens and tabs.

After the check

Don't add tabs. Connect prepare, run, verify, and hand off into one work flow.

PrepareRunVerifyHand off

I drew up a plan to move export and diagnostics, which had been separate screens, into the flow.

Remaining problems and actions

Problem Action Now
Procedure terms like evidence, gate, and receipt appeared on screen Made a separate scorecard for fixing wording In progress
Writes going outside Require preview and confirmation, with AI run permissions kept separate Applied
Measuring effect Haven’t measured how much faster team work became Not measured

In August I added AI settings, team schedules, and onboarding checks, and in September kept shipping 1.0-series versions. First-run setup offers the full environment setup rather than forcing users into a role.

What I learned

This problem surfaced once I launched the packaged app and checked each screen. The app gathered context, but didn’t answer whether what got built was correct.

I carried this kind of check over to personal products. Fixing screens by moment of use in Rescue Meal’s usage flow a few days later was the same approach.

What’s next

Checking whether results are correct led to Runtime Lab, and checking whether skills really help led to the benchmark. Measuring effect is still to do.
