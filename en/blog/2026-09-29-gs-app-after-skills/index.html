GS App: Why I Built an App After the Skills

I designed a desktop app to make skills the entry point for team work, and within a week I had to rethink its screen structure.

GS App is a desktop app that connects game information, AI runs, issue collaboration, simulation, and verification records for slot development. I wrote its design document and started implementation on July 8, 2026. Design and implementation were mine.

The problem

Even after dividing procedures into skills, something was still in the way. The design document targeted the whole team: server, client, math, and PMs. But skills are called from a terminal with a repository open, so people had to match which skill to use for which game and task each time. To make skills the team’s entry point, there had to be a starting place outside the terminal.

Background and framing

I evaluate the app on two axes: whether the feature exists, and whether users can avoid reassembling context. For the first week I built looking only at the first. The packaged review showed the second was empty.

The current capabilities document lists what’s implemented and what external conditions it needs, area by area. For example, AI sessions need a local CLI and login, and simulation needs a configured repository. The document exists to separate “implemented” from “works anywhere.”

For the procedural-term problem I made a separate scorecard. Five items score 0 to 2, and work ends only when all are 2.

Item What it checks
Words people use Internal procedure terms removed from screens and screen reader names
The task is obvious The screen’s purpose and main button come first
Calm layout Fewer decorations, status badges, and nested cards
Consistency across screens Same hierarchy of titles and buttons
Accurate meaning and accessibility Permissions and outcomes keep their meaning after rewording

Attempts

Decision Reason
A skill launcher, not free chat Things get made only by following production skills. The task list comes from scanning the skill folder, so new skills appear in the app.
No shared backend To avoid running infrastructure, code, metadata, and issues stay in their existing systems. On mismatch the app warns rather than resolves.
Progress display It reads progress files left by skills and shows them as stages.

Where my judgment changed

On July 14 I launched the packaged app and checked each screen. The conclusion was that features weren’t lacking. They had piled up screen by screen, so users reassembled their working context every time. Switching to the AI tab lost the selected game, and the simulation screen had no way out when there was no task to connect.

Features were added as screens and tabs.

Don't add tabs. Connect prepare, run, verify, and hand off into one work flow.

I drew up a plan to move export and diagnostics, which had been separate screens, into the flow.

In August I added AI settings, team schedules, and onboarding checks, and in September kept shipping 1.0-series versions. First-run setup offers the full environment setup rather than forcing users into a role.

Here is what changes when moving from screen-based to work-flow-based structure.

Question Screen-based Work flow
Where to start Choose a feature tab Choose a game and a task
Where context lives In the user’s head In the work item
What’s next User decides The stage guides
How to get out Differs by screen Back to the previous stage

The preview and confirmation before external writes come from the same reasoning. Issue comments and document publishing are hard to undo, so AI execution permission and external write permission aren’t tied to one switch. Electron’s official security docs also recommend limiting how far app screens can reach local resources.

I handled this app’s design and implementation, but many tools and data inside it were made by colleagues. The app’s job is connecting them into work context. So talking about the app by its feature count misses its actual value. Being its heaviest user is also a bias. A flow that doesn’t bother me isn’t guaranteed to suit server or PM roles, and doing early reviews with only my own eyes may have made this worse. The next review should watch someone from another role use it for the first time and note where they stop. The long external-conditions column in the capabilities doc is itself evidence of setup burden.

Reflection

I still think skipping a shared backend was right, but it has a cost. With several sources of truth, the app can only warn when they diverge, and a person resolves it. It reduces operating burden by handing some of it to users.

I added the last scorecard item because gentle wording can blur facts. Writing something not yet run as if it were finished reads easily but is a wrong screen. NN/g’s visibility-of-system-status heuristic also says to tell users the current state. Easy wording and accurate state sometimes collided, and I put accuracy first.

The biggest limit is not measuring the effect. There’s no evidence that starting skills from the app beats the terminal, or that colleagues got faster. I may also have overstated the entry barrier because I wanted to build an app. That’s my interpretation, and I won’t conclude until it’s measured.

Choosing a skill launcher over free chat has two sides as well. It keeps production procedures followed, but work without a skill is hard to start in the app, and low-quality skills show through directly. The first setup that doesn’t force people into roles is simple, but may show settings that math or PM people don’t need. I don’t yet have data on where real users stop.

General lessons

This problem surfaced once I launched the packaged app and checked each screen. The app gathered context, but didn’t answer whether what got built was correct.

I carried this kind of check over to personal products. Fixing screens by moment of use in Rescue Meal’s usage flow a few days later was the same approach.

A growing feature list looks like progress but may be cutting the flow of use. It’s better to run the packaged app from start to finish early. And a standard for easy wording must include accurate meaning.

Next steps

Checking whether results are correct led to Runtime Lab, and checking whether skills really help led to the benchmark. Measuring effect is still to do.

If I measure this, I could first pull lead time for changes and failure recovery from history, like DORA’s metrics. But slot work varies in size, so a direct before-and-after comparison of adopting the app is hard. Defining the unit of comparison comes first.
