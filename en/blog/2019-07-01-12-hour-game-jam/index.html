What I Learned from 12-Hour Game Jams

Centered on the split viewport in What Up Buddy, a look at which implementations kept recurring across the games I finished in 12 hours.

(Written in 2026, looking back.)

In my high school self-introduction I wrote that I had grown tired of playing inside fixed frames and rules, and became curious whether a game I made and played myself would be more fun.

That curiosity took me to a high school with a game development major, and I kept entering AppJam, Highthon, the Korea Youth Game Jam, and my school’s jam. Teams of three or four had to finish a game in 12 hours. At the same time I was writing frameworks from scratch in DirectX 9 in the skills club, so game jams were more like my practice ground for finishing things in Unity.

The question

Rereading my game jam records, I asked one thing. With only 12 hours, what did I build myself, and what did I leave to the engine? A list of finished games cannot answer that, so I put each game’s production time next to its implementation notes.

Background and framework

My sources are the implementation notes in my portfolio and the play videos. The source code from these jam games is not in a public repository, so I could not review the code itself. I split the analysis into constraints (time and people), choices (engine feature or my own code), and repetition (methods I reused in the next game).

According to the Unity docs, a camera with targetTexture set renders to the whole texture instead of the screen. That means another camera has to show the texture on screen. The snippet below is a sketch to explain the structure, not the original code.

leftCamera.targetTexture = leftTexture;
rightCamera.targetTexture = rightTexture;
// The main camera films the surface holding both textures.

What I tried

My 12-hour projects include What Up Buddy, Santa Overslept!, and a Cookie Run clone for personal study.

What Up Buddy (July 2019) is a quarter-view co-op game. Two people control one game, so the screen had to be split.

One camera per playerPoint each camera's Target Texture at a Left or Right render textureA main camera films a scene with the two textures side by side

The rest stayed simple too. Items were an enum that separated their effects, and CarSpawner picked a random direction and position, then checked that nothing would overlap before spawning.

Santa Overslept! (December 2019) is a side-scrolling casual arcade game. One array of gift boxes handled both spawning and input.

Where my judgment shifted

The decision I made when first needing a feature looked similar from game to game. For split screen I didn’t look for a way to draw it myself and used render textures, an engine feature. In the Cookie Run clone I updated only objects visible to the camera and left maps to the tilemap. Around then the skills club had me parsing obj files by hand, so I was choosing differently what to build and what to delegate depending on the tool.

What I learned

With a fixed deadline, you combine a few methods you already know rather than deliberating over a new structure. This was also when I gained experience sharing code with other people. Unlike the solo skills club, a jam meant merging code in the same project.

The same approach with a little more time produced Ttang Pa Seo Don Na Oh Nya?!, built in 20 hours and released in 2020. I split level design into several pieces and joined the ends so it kept scrolling.

Rereading each game

Rereading my portfolio notes game by game, the problem that came first differs in each one.

In What Up Buddy, two people sharing one screen came first. Without a screen layout, the co-op rule itself doesn’t hold. Next were the cars on the road: CarSpawner picked a direction and position at random, then checked for overlaps. Pairing random spawning with an overlap check resembles the later Bright Burn code that avoids drawing the same map again.

In the Cookie Run clone, objects kept piling up during the run, so I updated only those visible to the camera. This project also used bitmap fonts for score effects. I met bitmap fonts again at work, when dealing with jackpot board performance.

Santa Overslept! processes a row of gift boxes against input, so with the row as one array, spawning and input checks shared an index. Objects that appear and vanish often went into an Object Pool.

Ttang-pa-seo had eight more hours. Notably, that time went to the feel of digging with TrailRenderer, dirt debris with ParticleSystem, and Google and AdMob integration. It is a record of what I added first when given more time.

Reflection

This is my interpretation. Choosing render textures in a 12-hour project looks like a sign that I leaned toward finding existing parts. But Unity can also split the viewport with a camera’s rect, and no record shows that I compared the two. So I have no basis to call it the better choice.

There is a counterargument too. Singletons and plain arrays are fast within 12 hours, but in a long-lived project they tend to hide dependencies. The Game Programming Patterns book also treats Singleton with caution. I don’t think these repeated jam choices should become general design rules.

The limit of this post is that its only sources are descriptions I wrote. Teammates’ memories or the source code would have made the division of roles more accurate.

What I confirmed is the implementation notes and production time of each game. Why I could build quickly is my interpretation.

General lessons

  • When a deadline is short, limit new things to learn to one and fill the rest with methods you know.
  • Write down the conditions a shortcut was made under. If they change, you can judge it again.
  • Plain data structures are easier to read when your code gets merged with someone else’s.

What came next

After repeating short jams I moved on to a six-month team project, recorded in Bright Burn. Jams continued afterward: I took first place in the entertainment category at the 20th AppJam in 2022, and kept joining in-house game jams after starting work.
