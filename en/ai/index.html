Slot Development Workflow

Skill: a document describing the work procedure an agent follows. New slot production is split into a flow of skills, one for each stage. The production skill defines only the order and pass conditions, and each stage's skill owns the method.

  1. 1Design analysis and questions

    Turn the design document into a structured spec and settle unclear points through questions.

  2. 2Server logic and math

    Write logic and math values fresh from the design, using the base game only as reference.

  3. 3Simulation

    Run the simulator to check math values and bonus indicators.

  4. 4Module cloning and feature import

    Clone a base game's client module, then remove or import features.

  5. 5Response Schema sync

    Align names and structures from the server response through to client data paths.

  6. 6Client flow

    Build state graphs and presentation controllers, with placeholders where art will go.

  7. 7Art integration

    Swap in only what changed in each delivery, and keep placeholders for anything unconfirmed.

  8. 8Runtime play verification

    Operate the Editor with GS Unity, and replay, judge, and capture with Runtime Lab.

  9. 9Docs and handoff

    Leave design, server, and client reference documents and a work log.

What I tried and learned

  1. 2025.08

    Trying the tools

    The problem
    I tested whether Codex and Claude Code were useful for real work.
    What I learned
    I used them in bursts and then stopped, so this wasn't yet a daily way of working.
    What I did next
    From spring 2026 I started putting them into actual work.

  2. 2026.05

    Skill flow

    The problem
    I wanted to automate my team's slot development work as a flow of skills and start from the same baseline.
    What I learned
    Rule files apply differently by directory, so I distributed the standard by updating only an auto-updated section instead of overwriting whole files. But skills still have to be called from a terminal.
    What I did next
    I designed an app to make skills the team's entry point.

  3. 2026.06

    AgentB, a personal agent

    The problem
    I wanted to hand agents work beyond coding tools, from inside Slack.
    What I learned
    The biggest limit was the platform: inside Slack it only moved when tagged.
    What I did next
    I tried skills, session handoff, calls, and local model routing.

  4. 2026.07

    GS App

    The problem
    Around July 2026 I began handing most of my work to AI. I wanted to connect game information, issues, rule documents, and AI work, and have work start from a skill.
    What I learned
    A week later, reviewing the packaged app showed the problem wasn't missing features. Features had piled up screen by screen, so users kept reassembling their context.
    What I did next
    I redesigned toward connecting prepare, run, verify, and hand off into one work flow.

  5. 2026.07

    Runtime Lab

    The problem
    Passing code and build checks didn't confirm the presentation and state on the actual screen.
    What I learned
    I built response replay, rule-based judging, and section capture. I also kept the rule of reporting static checks and runtime checks separately.
    What I did next
    I kept replay results as development-environment evidence only and connected them to a runtime bug reproduction skill.

  6. 2026.09

    Using GS Unity

    The problem
    Agents needed a reliable way to operate the Unity Editor. The tool is a Rust CLI built by a colleague.
    What I learned
    I use my colleague's tool for Editor control and focus on the verification procedures and replay tooling above it. I connected it to the app, skills, and benchmark, and contributed a small fix.
    What I did next
    I wrote the play verification skill's entry, spin, and state-check procedures around this CLI.

  7. 2026.10

    Reorganizing skills

    The problem
    Skills had multiplied, and new production had several entry points.
    What I learned
    I separated skills that own order and pass conditions from skills that own method. Merging and removing skills cut the number by about half, and hand-written pass marks stopped counting.
    What I did next
    I gathered them under a production pipeline skill that uses a subagent for each stage.

  8. 2026.10

    Benchmark

    The problem
    When I changed skills or instructions, I had no basis for saying results had improved.
    What I learned
    Most early problems were in the scorer and the agent run environment. A small comparison had too few runs to judge, and I also found a skill document exposing answer files ahead of time.
    What I did next
    I added self-checks for the scorer and statistical rules. The main comparison experiment is on hold.

  9. 2026.10

    Personal products

    The problem
    I began using the same approach on personal products where I handle everything from planning to deployment.
    What I learned
    I now also delegate on-screen checks through browsers and simulators.
    What I did next
    In these products too, I write down separately what automated checks confirmed and what a person still has to check.

What I have learned so far

Don't say "done" in one word

Reports now separate server, Data Schema, client, runtime, and handoff. A passing build doesn't mean the screen is right.

A record isn't evidence

Agent progress notes and pass marks aren't trusted. Judgment comes from the final state and actual execution logs.

Doubt the tools first

Most early benchmark problems were in the scorer. I now check the tools first by grading the answer itself and confirming that the score drops as deliberately planted defects get bigger.

Weakness: missed verification

Problem: the more I delegated to AI, the more often verification after edits got skipped. Action: I changed the completion condition from a claim to an actual run result. Change: I now report separately what was actually run and what remains.
