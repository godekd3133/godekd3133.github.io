Sorting QA Bug Tickets by Root Cause

Situation
QA on a bonus feature left me with several assigned bug tickets at once, mixing wrong-looking amounts with presentation glitches.
What I did
For each ticket I first separated bad server values from bad on-screen display, fixed the display bugs, and wrote the cause, fix, and result on the ticket so QA could read it directly.
Outcome
Fixed tickets were source-checked and built, with on-screen confirmation tracked as a separate open item. One skip-animation ticket was recorded as investigation only.

Closing Gaps Between Server Responses and the Response Schema

Situation
Fields in the server result kept going missing from the Schema files, and in some cases the server sent a different value, so settings never reached the client.
What I did
I set a working order that treats the server response, Schema.json, Schema.txt, and client display as one unit, starting with the server.
Outcome
This check became the definition of done for later changes to the server-client response format.

Reproducing and Fixing a Board vs. Result Popup Mismatch

Situation
A QA ticket reporting that the amounts on the board did not add up to the result popup was reopened after a fix.
What I did
I worked through the server response and confirmed the total was right while the board display lagged behind. With an AI agent, I built a repro path that forces the same response to replay, then fixed the display side.
Outcome
In the forced repro, the board total matched the popup, and the fix passed review and QA.

Tracing a Screen Mismatch After a Reel Config Change

Situation
After I adjusted the bonus reel configuration, the game screen looked out of step with the new settings.
What I did
I compared the source values with the generated file the server actually reads, found old values left in the generated file, and regenerated it.
Outcome
Source and generated values matched and the server response test passed. The regeneration requirement was written into the docs.
