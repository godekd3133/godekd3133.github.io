슬롯 게임 개발

2021.12 ~ 2026.10

시작한 계기

슬롯 제작 도구를 고치는 일로 시작해 2022년 1월부터 슬롯을 담당했습니다. 담당 슬롯은 서버 로직부터 클라이언트까지 게임플레이 전체를 구현했습니다.

  3. 2023

  6. 2026

UniTask 전면 도입

필요했던 이유
코루틴 기반 피처 코드는 플라잉이나 연출 대기 처리가 번거롭고, 멈춤이나 해제 누락을 점검하기도 어려웠습니다.
한 일
입사 후 UniTask 사용을 꾸준히 제안하고 예제를 공유했습니다. 공통 기반 적용은 동료 개발자가 맡았고, 저는 신규 슬롯 적용과 규격 검토 항목 추가를 맡아 정착을 도왔습니다.
효과
다음 슬롯부터 UniTask를 쓰기로 팀이 결정했고, 플라잉과 연출 대기 코드가 단순해졌습니다.

비주얼 스크립팅에서 스크립트 중심 개발로 전환 추진

필요했던 이유
NodeCanvas 그래프가 처음 의도와 다르게 개발자 중심으로 쓰여 효율이 떨어진다고 판단했습니다. 그래프는 코드 리뷰와 비교, 테스트, AI 분석도 어려웠습니다.
한 일
심볼 동작을 스크립트 기반으로 리팩터링하고, 피처 로직을 UniTask 기반 스크립트 컨트롤러로 옮기도록 추진했습니다. 2026년에는 FSM을 코드로 바꾸는 프로젝트를 시작했습니다.
효과
신규 피처를 스크립트 컨트롤러로 작성하는 방식이 자리 잡았습니다.

만들고 활용한 도구

Unity Bridge

필요했던 이유
AI 에이전트가 게임 흐름 파일을 텍스트로 직접 고치면 Unity 자산이 깨지기 쉬워서, 에디터 안에서 안전하게 조작할 방법이 필요했습니다.
한 일
직접 만든 도구는 아니고 사내에서 만든 브릿지를 슬롯 개발에 활용했습니다. 2026년 2월 슈퍼 보너스 개발에 적용했고, 3월에는 자주 쓰는 호출을 묶어 스킬로 만들었습니다.
효과
에이전트가 자산 파일을 직접 편집하던 방식에서 도구로 흐름을 조작하는 방식으로 바꿀 수 있었습니다. 수치로 측정한 효과는 없습니다.

AI Bug Reporter

필요했던 이유
Unity에서 오류가 났을 때 그 순간의 화면과 게임 상태가 남지 않으면 원인을 찾거나 이슈로 넘기기 어려웠습니다.
한 일
오류 시점의 화면, 영상, 로그, 게임 오브젝트 구조, 서버 응답을 자동으로 저장하는 에디터 도구를 만들었습니다. 사람이 보는 리포트와 AI가 읽는 증거 묶음을 함께 만들고 Jira로 넘길 수 있게 했습니다.
효과
오류가 난 순간의 증거를 사람과 AI가 같은 자료로 확인하고 이슈로 넘길 수 있게 되었습니다.

Runtime Lab

필요했던 이유
특정 스핀 결과나 복잡한 상황을 Unity에서 재현하려면 원하는 조건이 나올 때까지 직접 플레이해야 했습니다.
한 일
기록해 둔 서버 응답을 재생해 원하는 스핀 시나리오를 바로 실행하고 결과와 화면을 함께 확인하는 개발 전용 도구를 만들었습니다. 명령줄에서도 실행할 수 있게 했습니다.
효과
같은 조건을 반복해서 재현하고 AI 에이전트도 같은 시나리오를 실행할 수 있게 되었습니다. 이후 2026년 10월에는 도구를 계속 유지할지 팀에서 다시 논의했습니다.

GS Unity CLI

필요했던 이유
기존 브릿지가 실무에서 정말 쓸 만한지, 아니라면 어떻게 실용적으로 만들지 논의가 필요하다고 팀에 제기했습니다.
한 일
CLI 개발은 동료가 주도했습니다. 저는 실사용 측면의 논의를 제기하고 개발 항목의 지속적인 추적을 요청했으며, 자산 복사 오류 수정 1건을 기여했습니다.
효과
동료의 기록에 따르면 에이전트가 플레이 모드 진입, 게임 진입, 스핀, 디버그 스핀을 직접 수행할 수 있게 되었고, 팀 슬롯 잼에도 쓰기로 했습니다.

맡은 일

  • 데스크톱 앱의 설계, 메인 프로세스, 화면, 배포를 혼자 맡았습니다.
  • AI 에이전트용 슬롯 개발 워크플로를 만들었습니다.
  • 출시된 슬롯을 다시 구현시켜 평가하는 벤치마크를 만들었습니다.

협업과 라이브 대응 사례

이 작업들은 대부분 AI 에이전트와 함께 진행했고, 원인 판단과 최종 확인은 제가 했습니다.

기획자와 메쓰를 만들고 검증하기

상황
슈퍼보너스가 늘면서 메쓰 설계와 수정, 검증을 빠르게 반복해야 했습니다. 기획자의 수정 요청을 실제 서버 결과로 바로 확인할 필요도 있었고, 외주 메쓰는 일정 손실을 일으킨 적이 있었습니다.
한 일
AI 에이전트와 함께 기획서를 분석해 메쓰 모델과 문서를 만들고 실제 서버 시뮬레이션으로 검증했습니다. 기획자가 값을 조정하면 서버 시뮬레이터로 돌려 비교하는 도구와, 시뮬레이션을 고르고 실행하는 데스크톱 앱도 만들었습니다.
결과
메쓰부터 서버, 클라이언트까지 한 흐름으로 진행했고, 기획자의 조정 요청을 시뮬레이션으로 확인해 서버에 반영하는 협업 방식을 만들었습니다. 다만 운영 메쓰의 최종 승인은 기획 검토를 거칩니다.

QA 버그 티켓을 원인별로 나눠 함께 해결

상황
보너스 기능 QA에서 제가 담당한 버그 티켓 여러 건이 한꺼번에 열렸고, 금액이 다르게 보이거나 연출이 어긋나는 증상이 섞여 있었습니다.
한 일
티켓마다 서버 값이 틀린 것인지 화면 표시가 틀린 것인지 먼저 가린 뒤 표시 오류를 고쳤고, QA가 바로 읽을 수 있게 원인, 수정, 결과를 나눠 티켓에 남겼습니다.
결과
수정한 티켓은 코드 확인과 빌드까지 마쳤고, 실제 화면 확인은 남은 항목으로 분리했습니다. 스킵 연출 티켓은 원인 조사까지만 진행했다고 기록했습니다.

서버 응답과 Response Schema의 어긋남 정리

상황
서버 결과에는 있는 필드가 Schema 파일에 빠져 있거나, 서버가 다른 값을 내려주어 설정이 클라이언트까지 닿지 않는 일이 반복됐습니다.
한 일
서버 응답, Schema.json, Schema.txt, 클라이언트 표시를 하나의 묶음으로 보고 서버부터 순서대로 고치도록 작업 방식을 정했습니다.
결과
이 점검 순서가 이후 서버와 클라이언트 응답 형식을 바꿀 때의 완료 기준이 됐습니다.

보드 금액과 결과 팝업 차이 재현과 수정

상황
보드에 보이는 금액의 합과 결과 팝업의 금액이 다르다는 QA 티켓이 수정 후 다시 열렸습니다.
한 일
서버 응답을 직접 계산해 총액은 맞고 보드의 표시 값이 따라가지 못한다는 점을 확인했습니다. AI 에이전트와 함께 같은 응답을 강제로 재생하는 재현 경로를 만들어 표시 쪽을 고쳤습니다.
결과
강제 재현에서 보드 합계와 팝업 금액이 일치하는 것을 확인했고, 리뷰를 거쳐 QA를 통과했습니다.

릴 설정 조정 후 화면 불일치 원인 찾기

상황
보너스 릴 설정을 조정한 뒤 게임 화면이 새 설정과 맞지 않아 보이는 문제가 있었습니다.
한 일
소스의 값과 서버가 실제로 읽는 생성 파일을 비교해, 생성 파일에 이전 값이 남아 있는 것을 찾아 다시 생성했습니다.
결과
소스와 생성 파일의 값이 일치했고 서버 응답 테스트도 통과했습니다. 다시 생성해야 한다는 조건은 문서에 남겼습니다.
