Rescue MealAI

먼저 써야 할 재료부터 알려 주는 식재료 관리와 식단 도우미

개발 중, 서비스, 2026년 9월 ~ 10월

실행하기GitHub 저장소 열기

서버 없이 예시 재료와 영수증으로 체험합니다. 새로고침하면 처음으로 돌아갑니다.

풀려던 문제

유통기한과 실제 보관 상태는 다릅니다. 표시 날짜와 보관 이력을 구분해 음식 안전을 지키면서 버리는 재료를 줄이는 것을 목표로 합니다.

식재료 등록이 번거로워 관리를 포기하고, 먼저 먹을 재료를 놓치는 1~2인 가구를 위한 앱입니다.

주요 기능

영수증, 바코드, 라벨 등록

사진과 PDF 영수증을 읽어 후보를 만들고, 사용자가 확인한 내용만 재고에 넣습니다.

먼저 살펴볼 재료

표시 날짜, 보관 위치, 개봉 여부를 바탕으로 살펴볼 순서를 정합니다.

있는 재료로 식단 제안

시간과 인원에 맞춰 재료를 쓰는 식단을 고르고, 부족한 재료는 장보기로 넘깁니다.

보관 이력

옮김, 개봉, 냉동, 일부 사용을 기록하고 김치냉장고 같은 내 보관 위치도 만듭니다.

제가 한 일

  • 영수증, 바코드, 라벨로 식재료 등록
  • 먼저 써야 할 재료 중심의 식단 제안
  • CodeQL과 복구 훈련을 CI에 포함

현재 상태

  • 2026년 10월 기준 TestFlight 배포 흐름까지 준비했고, 실제 사용자 검증은 아직 하지 않았습니다.

구조

모바일 웹 앱과 API를 나누고, 무거운 OCR은 별도 워커로 분리했습니다.

  1. 클라이언트: React, Vite PWA
  2. API: FastAPI, PaddleOCR 워커, 식단 계산
  3. 데이터: PostgreSQL(SQL 이관 파일로 관리), 로컬 SQLite 어댑터

설계 판단

먹어도 되는지는 판정하지 않기
상품명이나 사진만으로는 개별 제품의 상태를 알 수 없습니다. 그래서 입력, 보관 이력, 우선순위까지만 돕고 안전 판정은 하지 않습니다.
표시 날짜와 추정값을 분리
포장일, 소비기한, 추정 우선순위는 뜻이 다릅니다. 출처와 종류를 함께 저장하고 추정값이 소비기한으로 바뀌지 않게 했습니다.
영수증은 검토 후 입고
OCR이 날짜, 수량, 할인을 잘못 읽을 수 있어 초안, 검토, 확정 단계를 나눴습니다. 식당 영수증은 재고에서 제외합니다.
같은 상품도 구매 건별로 관리
구매일과 보관 상태가 다르고 일부만 냉동할 수도 있어 상품 정보와 재고 묶음을 나눴습니다.

어려웠던 점과 해결

저장에 실패하면 먹은 기록만 남거나 재고가 어긋날 수 있었습니다.
식단 완료, 영수증 확정 같은 작업을 한 단위로 묶어 실패 시 복원하고, 다시 시도할 수 있는 오류로 돌려줍니다.
네트워크가 흔들리면 같은 요청이 두 번 들어와 재고가 중복될 수 있었습니다.
재시도 키를 기록하는 공용 모듈을 두어 같은 요청은 한 번만 처리합니다.
